### 🏗️ Как на самом деле работает Self-Hosted Runner (а не колхоз)

Если утрировать, то GitHub/GitLab — это пульт управления, а твой сервер — это руки, которые выполняют работу. Главный архитектурный нюанс, который показывает, что ты разбираешься в теме: **Сам runner (его менеджер) не выполняет твой код. Он лишь создаёт для него безопасную «песочницу» (изолированную среду).** А менеджер просто просит новые задания у GitLab и отправляет логи обратно[](https://blog.ippon.fr/2026/01/21/gitlab-runners-maitrisez-les-differents-executors-pour-optimiser-vos-pipelines-ci-cd/).

Твоя задача — сделать эту «песочницу» максимально тесной и не протекающей. Мы с тобой как раз идём по самому правильному пути – использовать **Docker executor in NON-privileged mode**.

**Твой будущий сетап:**

1. **Твой сервер (в Яндекс Облаке или даже у тебя дома на старом ноуте).** У него есть IP-адрес и доступ в интернет.
    
2. **На сервере установлен GitLab Runner.** Это такой фоновый процесс-менеджер.
    
3. **В конфиге раннера (`config.toml`) ты пропишешь магию:**
    
    toml
    
    [[runners]]
      name = "my-awesome-sec-runner"
      executor = "docker"       # <-- Это важно!
      [runners.docker]
        image = "alpine:latest" # Базовый образ
        privileged = false      # <-- ЭТО ГЛАВНОЕ ДЛЯ БЕЗОПАСНОСТИ!
        volumes = ["/cache"]
    
4. **В GitLab (или GitHub) ты регистрируешь этот runner и даёшь ему теги**, например, `ios-sec` и `sec-scanner`. Теперь, когда в твоём `.gitlab-ci.yml` будет указан этот тег, задание уйдёт на выполнение на ТВОЙ сервер.

### ⚠️ Сырая правда: Риски и твоя защита (Разбор для собеседования)

Ты спросил, не выебут ли тебя. Если ты настроишь рантер кое-как (через `shell` executor или с `privileged = true`), то да, технически подкованный лид или сеньор спросит: «А ты понимаешь, что любой, кто сделает коммит в репозиторий, получит полный доступ к твоему серверу и сможет украсть все секреты?»[](https://idocdown.com/app/articles/blogs/detail/17348)[](https://docs.gitlab.cn/docs/runner/security/). И это будет правильный вопрос.

Но если ты покажешь, что понимаешь эти риски и знаешь, как их закрыть, то ты будешь на голову выше других кандидатов.

Вот **таблица рисков и защит**, которую ты должен выучить как «Отче наш». Это твой будущий ответ на собеседовании.

|---|---|---|
|**1. Ядро проблемы: Запуск любого кода на твоём сервере**|Любой, у кого есть доступ пушить код в репозиторий, может написать зловредный `.gitlab-ci.yml`, который выполнит `rm -rf /` или замайнит крипту на твоём сервере[](https://docs.gitlab.cn/docs/runner/security/)[](http://gitlab.cn/docs/runner/security/).|**Решение:** Никогда не используй **`shell` executor** для untrusted (недоверенных) проектов[](https://docs.gitlab.cn/docs/runner/security/)[](http://rdc.hand-china.com/gitlab/rdc_hip/gitlab-ci-multi-runner/raw/fb7dfe8d7da1f208b230174116a55c3dacb88402/docs/security/index.md). **Мой выбор:**Только **Docker executor в не-привилегированном режиме (`privileged = false`)**. Каждое задание стартует в новом, чистом контейнере[](https://docs.gitlab.cn/docs/runner/security/)[](https://blog.ippon.fr/2026/01/21/gitlab-runners-maitrisez-les-differents-executors-pour-optimiser-vos-pipelines-ci-cd/).|
|**2. Побег из контейнера (Container Escape)**|Если ты включишь **`privileged = true`** (нужно для Docker-in-Docker), код из контейнера получает полный доступ к хосту. Это 100% путёвка к компрометации всей твоей ВМ[](https://docs.gitlab.cn/docs/runner/security/)[](https://idocdown.com/app/articles/blogs/detail/17348)[](http://rdc.hand-china.com/gitlab/rdc_hip/gitlab-ci-multi-runner/raw/fb7dfe8d7da1f208b230174116a55c3dacb88402/docs/security/index.md).|**Решение:** Избегать `privileged = true`. |**3. Кража секретов (Secrets)**|Твой токен регистрации (`registration-token`) или переменные окружения (`CI_JOB_TOKEN`) могут быть скомпрометированы. Использовать **токены проектов**, а не публичные. Никогда не хардкодить в `.gitlab-ci.yml`[](https://github.com/Mattrachwal/gitlab-runner).|
|**4. Кража данных других проектов**|Runner может использоваться для нескольких проектов. Зловредный код из проекта А может украсть код проекта Б из директории `/builds`, так как runner имеет к ним доступ[](https://docs.gitlab.cn/docs/runner/security/)[](http://gitlab.cn/docs/runner/security/).|**Решение:** **Залочить runner (`locked=true`) и отключить untagged jobs (`run_untagged=false`) **[](https://github.com/Mattrachwal/gitlab-runner). Это закрепит runner за конкретным проектом и заставит явно указывать теги.|
|**5. Атака через образы (`Pull Policy`)**|Если использовать политику `pull_policy = "if-not-present"`, злой пользователь может загрузить образ с вредоносным кодом под тем же именем, что и легитимный, и раннер, найдя его локально, запустит его вместо настоящего[](https://docs.gitlab.cn/docs/runner/security/)[](http://gitlab.cn/docs/runner/security/)[](http://rdc.hand-china.com/gitlab/rdc_hip/gitlab-ci-multi-runner/raw/fb7dfe8d7da1f208b230174116a55c3dacb88402/docs/security/index.md).|**Решение:** **Всегда использовать `pull_policy = "always"`** для недоверенных окружений. Гарантирует, что образ всегда будет свежим.|

### 🛡️ Как это собрать воедино и что сказать на собеседовании

Братик, забудь про «колхоз». Построй систему, за которую тебя будут хвалить.

1. **Регистрируй раннер с умом:**  
    Используй скрипт или команду с правильными флагами. Проект типа [`Mattrachwal/gitlab-runner`](https://github.com/Mattrachwal/gitlab-runner) — отличный пример для изучения, как это делать профессионально[](https://github.com/Mattrachwal/gitlab-runner).
    
    bash
    
    sudo gitlab-runner register \
      --non-interactive \
      --url "https://gitlab.com/" \
      --registration-token "$YOUR_TOKEN" \
      --executor "docker" \
      --docker-image "alpine:latest" \
      --docker-privileged false \
      --tag-list "ios-sec,mobsf,semgrep" \
      --run-untagged false \
      --locked true
    
2. **Защищай свой сервер (Harden it):**
    
    - Создай отдельного пользователя `gitlab-runner` без прав суперпользователя (sudo).
        
    - Настрой файрвол (UFW), разреши только нужные порты.
        
    - Используй техники из systemd hardening, чтобы ограничить, что может делать процесс runner'а[](https://github.com/Mattrachwal/gitlab-runner).

## Суть подхода: Self‑Hosted Runner с Docker executor

**Принцип работы:**

- GitHub/GitLab — «пульт управления»: хранит код, запускает пайплайны, раздаёт задания.
    
- Self‑hosted runner на вашем сервере — «исполнитель»: забирает задания, запускает их визолированной среде, возвращает результаты.
    
- Ключевой момент: runner не выполняет код напрямую, а создаёт «песочницу» (контейнер) длякаждого задания.
    

**Оптимальная конфигурация:** Docker executor в не‑привилегированном режиме (`privileged = false`).

## Пошаговая настройка

### Шаг 1. Подготовка сервера

- Платформа: любое окружение с доступом в интернет (VPS, облако, локальная машина).
    
- ОС: Linux (например, Ubuntu 22.04).
    
- Ресурсы: минимум 2 CPU, 4 GB RAM, 20 GB диска (зависит от задач).
    

### Шаг 2. Установка GitLab Runner

bash

```bash
# Скачать и установить бинарник
curl -LJO "https://gitlab-runner-downloads.s3.amazonaws.com/latest/binaries/gitlab-runner-linux-amd64"
chmod +x gitlab-runner-linux-amd64
sudo mv gitlab-runner-linux-amd64 /usr/local/bin/gitlab-runner


# Создать пользователя и настроить сервис
sudo useradd --comment 'GitLab Runner' --create-home gitlab-runner --shell /bin/bash
sudo gitlab-runner install --user=gitlab-runner --working-directory=/home/gitlab-runner
sudo gitlab-runner start


### Шаг 3. Регистрация runner’а

Используйте команду с безопасными флагами:

bash

```bash
sudo gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.com/" \
  --registration-token "$YOUR_TOKEN" \
  --executor "docker" \
  --docker-image "alpine:latest" \
  --docker-privileged false \
  --tag-list "ios-sec,mobsf,semgrep" \
  --run-untagged false \
  --locked true


**Ключевые флаги:**

- `--executor "docker"` — запуск заданий в контейнерах.
    
- `--docker-privileged false` — запрет привилегированного режима (защита от ContainerEscape).
    
- `--tag-list` — теги для явного назначения заданий.
    
- `--run-untagged false` — запрет выполнения заданий без тегов.
    
- `--locked true` — закрепление runner’а за проектом.
    

### Шаг 4. Настройка `config.toml`

Пример конфигурации:

toml

```toml
[[runners]]
  name = "my-awesome-sec-runner"
  url = "https://gitlab.com/"
  token = "YOUR_TOKEN"
  executor = "docker"

  [runners.docker]
    tls_verify = false
    image = "alpine:latest"
    privileged = false
    disable_entrypoint_overwrite = false
    oom_kill_disable = false
    disable_cache = false
    volumes = ["/cache"]
    shm_size = 0
    pull_policy = "always"  # всегда скачивать свежий образ


**Важный параметр:** `pull_policy = "always"` — защита от атак через подмену образов.

### Шаг 5. Защита сервера (Harden it)

- **Пользователь:** создайте отдельного пользователя `gitlab-runner` без прав `sudo`.
    
- **Файрвол:** настройте UFW, разрешив только нужные порты (например, 22 для SSH, 80/443 еслинужно).
    
- **systemd hardening:** ограничьте возможности процесса runner’а через настройки сервиса(например, `NoNewPrivileges=yes`, `ProtectSystem=strict`).
    
- **Обновления:** регулярно обновляйте ОС и Docker.
    
- **Мониторинг:** настройте логирование и алертинг на подозрительную активность.

- **Ограничение ресурсов:** в `config.toml` задайте лимиты CPU/RAM для контейнеров, чтобыпредотвратить DoS.
    
- **Аудит:** регулярно проверяйте логи runner’а и Docker на подозрительную активность.
    
- **Резервное копирование:** сохраняйте `config.toml` и секреты в безопасном месте.
    
- **Тестирование:** перед запуском в продакшн протестируйте пайплайн на тестовом репозитории.
    

Этот подход соответствует лучшим практикам безопасности CI/CD и демонстрирует глубокоепонимание рисков — что критически важно для инженера по безопасности.
