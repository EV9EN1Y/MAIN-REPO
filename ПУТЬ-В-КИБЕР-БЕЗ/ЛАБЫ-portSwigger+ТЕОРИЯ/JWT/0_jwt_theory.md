
**JWT (JSON Web Token)** — это, по сути, цифровая JSON записка, которую сервер выдаёт клиенту. В ней лежат данные о пользователе (claims): имя, роль, айдишник, срок годности. 
Главная фишка: всё это хранится у клиента, а сервер просто проверяет подпись, и когда нужно выдает новый токен, рефреш токена...

#### работа JWT на примере моего приложения MeetWay
Короч, отправляем серверу запрос на получение jwt токена и сессионного токена, отправляя ему наш id (и необходимые даные) - далее сервер обрабатывает это все согласно свеой логике и выдает JWT /или не выдает новый JWT . и в этот jwt токен нужен потом для работы прилоэжения, например, в моем приложении MEETWAY (соц сеть) - там каждое сетевое действие требует в своем сопровождении не просроченный JWT (для доступа к системе аунтетификации, для просмотра чужих профилей, для отправки смс, для выполнения поиска юзеров по бд внутри приложения, добавление поста в ленту или коммента, или при изменении своих данных в аккаунте, также для отправки реакций итд, в общем - почти для всех дейсквий - сервер требует этот самый JWT : и каждые n минут - токен устаревает - и приложение запрашивает новый токен, сервер проверяет запрос - и далее от условий - выдает или не выдает новый JWT)

Это удобно для распределённых систем, где много бэкенд-серверов
Им не надо лазить в общую базу сессий — вся инфа уже в токене.

#### Header (Заголовок) — base64url от JSON. Там обычно:

```json
{
    "alg": "HS256",      // алгоритм подписи
    "typ": "JWT"         // тип
}
```

#### Payload (Полезная нагрузка) — тоже base64url JSON. Тут лежат claims  - требуемые - передаваемые данные:


```json
{
    "iss": "portswigger",
    "exp": 1648037164,
    "name": "Carlos Montoya",
    "sub": "carlos",
    "role": "blog_author",
    "email": "carlos@carlos-montoya.net",
    "iat": 1516239022
}
```

#### Signature (Подпись) — создаётся так:

```
HMACSHA256(
    base64UrlEncode(header) + "." + base64UrlEncode(payload),
    secret
)
```

 header и payload — это просто base64 данные, их может прочитать и изменить любой, у кого есть токен. 
 Вся безопасность держится ==только на подписи==- токене. Не на том, что данные зашифрованы, а на том, что они подписаны секретным ключом

##  JWS vs JWE

 JWS (JSON Web Signature) — подписанный токен. Данные внутри видны всем, но подпись гарантирует, что их не меняли

**JWE (JSON Web Encryption)** — это когда содержимое ещё и шифруется
Встречается реже, в основном для особо чувствительных данных

##  🔴 как ломают JWT 

Ты можешь изменять payload как хочешь, но без валидной подписи сервер тебя пошлёт на другие три буквы
Поэтому все атаки сводятся к одному из трёх:

1. Заставить ==сервер не проверять подпись== вообще
   
2. ==Узнать/подобрать секретный ключ== и подписать свой токен
   
3. Подменить ключ проверки своим

# 🟢  АТАКИ JWT 

### 1.  Принимаем произвольные подписи (Accepting arbitrary signatures)

самая тупая ошибка разработчика: использовать метод `decode()` вместо `verify()`

например в Node.js библиотеке `jsonwebtoken` есть два метода:

- `verify()` — проверяет подпись
   
- `decode()` — просто декодирует base64
   

если разработчик поставил `decode()`, то подпись вообще не проверяется. Ты можешь вставить любой говнокод в payload, и сервер поверит
(но это все всплывет (скорее всего) сразу же на этапе первичного тестирование самим же програмистом при настройске работы этой системы как раз...)

пример атаки:
был токен:

```json
{"username": "carlos", "isAdmin": false}
```

ты меняешь на:

```json
{"username": "administrator", "isAdmin": true}
```

вуаля — ты админ

-----
### 2.  Алгоритм none (Accepting tokens with no signature)

В заголовке `alg` может стоять значение `none`. Это значит "без подписи"
По спецификации, если `alg: none`, то часть с подписью должна быть пустой (просто точка . в конце)

разработчики обычно блокируют такие токены. Но фильтрацию можно обойти:

обфускация

- `Alg: NoNe` (смешанный регистр)
   
- `alg: None` с пробелами
   
- нестандартные кодировки
   

если обошёл — подпись не проверяется, payload меняешь как хочешь

-----
### 3.  Брутфорс секретного ключа (Brute-forcing secret keys) жестко 😨😬

для симметричных алгоритмов типа HS256 (HMAC-SHA256) секретный ключ — это просто строка 
если ключ слабый (типа `secret`, `password`, `key123`), его можно подобрать

как подбирать:  
берем валидный JWT, загоняешь в hashcat:

```bash
hashcat -a 0 -m 16500 eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c /usr/share/wordlists/rockyou.txt
```

почему это быстро? 
Потому что hashcat работает локально, не долбит сервер 
миллионы попыток в секунду

### 4.  Инъекции в заголовки JWT (JWT header parameter injections)

самый интересный раздел  - в  заголовке JWT могут быть параметры, которые влияют на выбор ключа для проверки подписи

основные параметры:

- `jwk` (JSON Web Key) — встраивает публичный ключ прямо в токен
    
- `jku` (JSON Web Key Set URL) — URL, откуда сервер должен скачать набор ключей
    
- `kid` (Key ID) — идентификатор ключа, если их несколько
    

атакующий может использовать эти параметры, чтобы подсунуть свой собственный ключ

####  атака через jwk (Injecting self-signed JWTs via the jwk parameter)

если сервер доверяет ключу, который приходит в `jwk`, то можно:

1. сгенерировать свою пару RSA-ключей
    
2. подписать токен своим приватным ключом
    
3. вставить публичный ключ в параметр `jwk` заголовка
    

сервер увидит ключ в токене и использует его для проверки подписи -
а подпись-то сделана твоим ключом — значит, всё сойдётся

в Burp Suite для этого есть расширение ==JWT Editor:==

- Заходим в JWT Editor Keys
    
- Создаём новую RSA-пару
    
- В Repeater на вкладке JSON Web Token правим payload
    
- Жмём "Sign" и выбираешь "Don't modify header" (чтобы оставить свой `jwk`)
    

####  Атака через jku (Injecting self-signed JWTs via the jku parameter)

то же самое, но публичный ключ не встраивается прямо в токен, а загружается по URL из `jku`. Ты можешь:

1. хостить на своём сервере JSON с JWK-набором, содержащим твой публичный ключ
    
2. вставить URL своего сервера в `jku`
   
3. сервер скачает твой ключ и использует для провер
   

важно: URL должен быть валидным и доступным 
иногда серверы проверяют, что URL ведёт на доверенный домен, но это часто обходится через открытые редиректы

####  атака через kid (Injecting self-signed JWTs via the kid parameter)

`kid` — это идентификатор ключа. Сервер ищет ключ с таким ID в своей базе. Ты можешь:

- Если сервер хранит ключи в файловой системе, попробуй path traversal: `"kid": "../../../../dev/null"`
    
- Если сервер использует SQL, попробуй SQLi: `"kid": "key' UNION SELECT 'mykey'"`
    
- Если ключи берутся из окружения, можно попробовать угадать имя переменной
    

иногда `kid` вообще игнорируется, и сервер берёт любой ключ, лишь бы подпись сошлась

### 5.  Algorithm confusion attacks

самая сложная, но и самая жирная атака!
Суть: перепутать симметричный и асимметричный алгоритмы

контекст:

- ==Симметричные алгоритмы (HS256)==: один секретный ключ и для подписи, и для проверки.
    
- ==Асимметричные (RS256, ES256)==: пара ключей. Приватный подписывает, публичный проверяет.
    

сервер знает свой публичный ключ. Если ты изменишь `alg` с `RS256` на `HS256`, сервер может попытаться использовать свой **публичный ключ** как **секретный** для HMAC

как это работает:

1. сервер ожидает RS256 и имеет публичный ключ (например, в виде PEM-файла)
   
2. ты меняешь заголовок на `"alg": "HS256"`
   
3. сервер думает: "Ага, теперь я должен использовать симметричный алгоритм. Где же мой секретный ключ? А дай-ка я возьму содержимое публичного ключа и использую его как секрет!" скуяли так ?
   
4. подписываешь свой поддельный токен, используя публичный ключ как HMAC-секрет
   
5. сервер проверяет — подпись сходится
   

как добыть публичный ключ:

- иногда сервер отдаёт его на `/jwks.json` или в метаданных OIDC
   
- можно вытащить из старого, легитимного токена, если там был `jwk` (но тогда это другая атака)
   
- в некоторых реализациях ключ лежит в открытом доступе
   

##  Защита от JWT-атак (по версии OWASP и здравого смысла)

OWASP даёт такие рекомендации:

#### 1. Проверяй подпись всегда, везде, неукоснительно

Никаких `decode()` вместо `verify()`. Никаких `alg: none`. Даже если токен прилетел из "доверенного" источника

#### 2. Строго валидируй заголовки

- Отключи поддержку `jwk` и `jku`, если они не нужны нафиг
    
- Если нужны — проверяй, что URL из `jku` ведёт на белый список доверенных хостов, и что соединение идёт по HTTPS
    
- Валидируй `kid` — он не должен содержать path traversal или SQLi
    

#### 3. Используй сильные ключи и храни их безопасно

- Для HS256 ключ должен быть длинным и случайным (не `secret123`)
    
- Регулярно меняй ключи
    
- Не храни ключи в коде или в публичных репозиториях
    

#### 4. Защищайся от algorithm confusion

- Явно указывай, какие алгоритмы разрешены. Лучше всего — только один
    
- Никогда не используй публичный ключ для HMAC-проверки
    

#### 5. Устанавливай короткие сроки жизни токенов

- Используй `exp` (expiration) и проверяй его строго
    
- Для долгих сессий используй refresh tokens, а не долгоживущие JWT
    

#### 6. Используй проверенные библиотеки и обновляй их

- Не пиши свою криптографию
    
- Следи за обновлениями библиотек — в них часто правят именно такие дыры

##  Итог

JWT — это мощный, но опасный инструмент. Ошибки в его реализации могут стоить  всего приложения. главное:

- **Подпись — это всё**. Если её можно обойти или подделать — ты лох
    
- **Не доверяй тому, что приходит в заголовках**. Особенно `alg`, `jwk`, `jku`, `kid`
    
- **Ключи должны быть секретными и сильными**. Слабый ключ = смерть
    
- **Тестируй всё**. Даже если библиотека "проверенная", разработчик мог настроить её неправильно
