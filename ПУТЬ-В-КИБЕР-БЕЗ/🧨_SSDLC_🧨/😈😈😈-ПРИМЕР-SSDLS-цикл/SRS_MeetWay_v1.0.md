## 1. Цель проекта

Мобильная социальная сеть для общения: профили, посты, чаты, поиск людей.

Цели безопасности проекта:
- Защита персональных данных пользователей (PII) на всех этапах жизненного цикла.
- Соответствие законодательству РФ (152-ФЗ) и GDPR для пользователей из ЕС.
- Минимизация рисков компрометации аккаунтов, утечек данных и злоупотреблений.
- Встраивание безопасности в процесс разработки (shift-left, принципы SSDLC).

## 2. Область применения и ограничения

- Система: мобильные приложения (iOS, Android), серверная часть (API), админ-панель.
- Вне области: веб-версия (позже), корпоративные интеграции.
- Ограничения: только официальные магазины приложений (App Store, Google Play), бэкенд размещается в Yandex Cloud (регион РФ), поддержка старых ОС ограничена (iOS 15+, Android 10+).

## 5. Функциональные требования

### FR-1. Регистрация и авторизация

- FR-1.1: Регистрация по email + пароль и по номеру телефона (SMS-код).
- FR-1.2: Вход по email/телефону + паролю.
- FR-1.3: Восстановление пароля через email/SMS.
- FR-1.4: Выход из аккаунта на всех устройствах (удалённый logout).
- FR-1.5: Смена пароля (с подтверждением старого).
- FR-1.6: Подключение двухфакторной аутентификации (TOTP-приложение или SMS-код).

### FR-2. Профиль пользователя

- FR-2.1: Просмотр и редактирование профиля (имя, фото, bio, город).
- FR-2.2: Просмотр профилей других пользователей.
- FR-2.3: Настройки приватности (кто видит профиль/посты).
- FR-2.4: Удаление аккаунта (полное удаление данных, право на забвение).
- FR-2.5: Экспорт своих данных (скачивание архива).

### FR-3. Посты и лента

- FR-3.1: Создание, редактирование, удаление постов (текст + фото).
- FR-3.2: Лента постов (свои + друзей), пагинация.
- FR-3.3: Лайки и комментарии.
- FR-3.4: Жалобы на контент (модерация).

### FR-4. Чаты

- FR-4.1: Личные чаты (1-на-1) и групповые чаты.
- FR-4.2: Отправка текста, фото, геолокации.
- FR-4.3: Уведомления о новых сообщениях (push).
- FR-4.4: Удаление сообщений (для себя и для всех).

### FR-5. Поиск людей

- FR-5.1: Поиск по имени/фамилии/городу.
- FR-5.2: Фильтры (возраст, город, интересы).

### FR-6. Администрирование

- FR-6.1: Админ-панель для модерации контента и жалоб.
- FR-6.2: Блокировка пользователей и устройств.
- FR-6.3: Просмотр журнала безопасности (аудит-лог).

## 6. Нефункциональные требования

### NFR-1. Производительность

- NFR-1.1: Время загрузки ленты < 500 мс (p95).
- NFR-1.2: Поддержка 100 000 одновременных пользователей.
- NFR-1.3: Время ответа API < 300 мс (p95), кроме тяжёлых операций (поиск, загрузка медиа).

### NFR-2. Доступность и отказоустойчивость

- NFR-2.1: Доступность сервиса 99.9% (SLA).
- NFR-2.2: Автоматическое восстановление после сбоя Cloud Functions/БД не более 15 минут.
- NFR-2.3: Отсутствие единой точки отказа в критических компонентах.

### NFR-3. Масштабируемость

- NFR-3.1: Горизонтальное масштабирование серверной части без даунтайма.
- NFR-3.2: Масштабирование БД (шардирование/репликация) при росте нагрузки.

### NFR-4. Надёжность

- NFR-4.1: Гарантированная доставка сообщений (retry, idempotency).
- NFR-4.2: Целостность данных при сбоях (транзакционность, консистентность).

### NFR-5. Совместимость

- NFR-5.1: iOS 15+ (iPhone), Android 10+ (API 29+).
- NFR-5.2: Поддержка устройств без Google Play Services (Yandex AppMetrica вместо Firebase, при необходимости).

### NFR-6. Наблюдаемость

- NFR-6.1: Логирование ключевых операций (логин, регистрация, платежи, удаление данных).
- NFR-6.2: Метрики доступности, ошибок 4xx/5xx, задержек (OpenTelemetry).
- NFR-6.3: Алерты на аномалии (всплеск ошибок аутентификации, rate-limit срабатывания).

### NFR-7. Безопасность (кратко, детально – раздел 7)

- NFR-7.1: Пароли хранить только в виде хэшей (bcrypt/argon2).
- NFR-7.2: Весь трафик – TLS 1.2+.
- NFR-7.3: Доступ к API только по JWT (access + refresh).

## 7. Требования безопасности (SEC)

> Каждое требование: **ID**, описание, **обоснование (угроза)**, **критерий приемки**, приоритет, ссылка на стандарт (OWASP ASVS / MASVS / NIST SP 800-218 SSDF).

### SEC-1. Идентификация и аутентификация

- **SEC-1.1**: Минимальная длина пароля – 8 символов, проверка по списку распространённых паролей (breached passwords). Приоритет: Must.
  - Угроза: подбор паролей, credential stuffing.
  - Приёмка: тест регистрации с паролем из списка – отклоняется. Соответствие: ASVS 2.1, NIST SP 800-63B.
- **SEC-1.2**: Поддержка MFA (TOTP / SMS-OTP) для всех пользователей, обязательная – для админов. Приоритет: Must.
  - Угроза: компрометация пароля.
  - Приёмка: включение 2FA, повторный вход требует OTP. Соответствие: ASVS 2.5, MASVS V3.
- **SEC-1.3**: Ограничение попыток входа (rate limiting): не более 5 неудачных попыток за 15 минут на аккаунт/IP, далее временная блокировка + CAPTCHA. Приоритет: Must.
  - Угроза: brute-force, credential stuffing.
  - Приёмка: 6-я неверная попытка блокируется, приходит алерт. Соответствие: ASVS 2.2.1, 2.2.6.
- **SEC-1.4**: Верификация номера телефона/email при регистрации и восстановлении (OTP, срок жизни кода 5 минут, 5 попыток ввода). Приоритет: Must.
  - Угроза: захват чужих аккаунтов, SMS-бомбинг.
  - Приёмка: код не принимается после истечения срока/попыток.
- **SEC-1.5**: Автоматическая блокировка подозрительной активности: вход с нового устройства/гео требует подтверждения (OTP на email/SMS). Приоритет: Should.
  - Угроза: захват аккаунта при утечке пароля.
  - Приёмка: первый вход с нового устройства требует подтверждения.

### SEC-2. Управление сессиями и токенами

- **SEC-2.1**: JWT access token – срок жизни не более 15 минут; refresh token – ротация при каждом использовании, срок жизни 30 дней, отзыв при смене пароля. Приоритет: Must.
  - Угроза: кража токена, переиспользование украденного refresh.
  - Приёмка: проверка сроков, ротация refresh, чёрный список при logout. Соответствие: ASVS 3.1, 3.2.
- **SEC-2.2**: Хранение токенов на клиенте только в Keychain (iOS) / EncryptedSharedPreferences+Keystore (Android), НЕ в UserDefaults/SharedPreferences. Приоритет: Must.
  - Угроза: извлечение токенов из бэкапов/рутнутого устройства.
  - Приёмка: статический анализ кода, тест на рутнутом устройстве. Соответствие: MASVS V8 (Resilience), OWASP Mobile Top 10 M3.
- **SEC-2.3**: Logout на всех устройствах (инвалидация всех refresh-токенов пользователя). Приоритет: Must.
  - Угроза: компрометация одного устройства => доступ ко всем.
  - Приёмка: после logout старые токены дают 401. Соответствие: FR-1.4, ASVS 3.2.2.
- **SEC-2.4**: Защита от CSRF для всех state-changing запросов (анти-CSRF токен, SameSite cookies, или бесcookie-схема на JWT в заголовке). Приоритет: Should.
  - Угроза: CSRF-атаки (если используются cookies).
  - Приёмка: тест CSRF-сценариев, проверка заголовков. Соответствие: ASVS 5.5.

### SEC-3. Авторизация и контроль доступа

- **SEC-3.1**: Ролевая модель (RBAC): user, moderator, admin. Принцип наименьших привилегий. Приоритет: Must.
  - Угроза: эскалация привилегий.
  - Приёмка: проверка прав на каждый эндпоинт (матрица доступа). Соответствие: ASVS 4.1.
- **SEC-3.2**: Защита от IDOR: проверка владения ресурсом на сервере для каждого запроса (посты, чаты, профили). Приоритет: Must.
  - Угроза: доступ к чужим данным подменой ID.
  - Приёмка: pen-test сценарий: запрос чужого ID -> 403/404. Соответствие: ASVS 4.2, OWASP Top 10 A01.
- **SEC-3.3**: Контроль доступа к медиа-файлам (S3): выдача временных подписанных URL (presigned), проверка прав перед выдачей. Приоритет: Must.
  - Угроза: прямой доступ к приватным файлам по ссылке.
  - Приёмка: приватный файл недоступен без подписи, срок ссылки ограничен.
- **SEC-3.4**: Разделение обязанностей: админ-операции недоступны обычным пользователям и наоборот; отдельные роли для модерации. Приоритет: Must.
  - Угроза: конфликт интересов, злоупотребления.
  - Приёмка: аудит прав, тесты доступа.

### SEC-4. Защита данных

- **SEC-4.1**: Шифрование канала: TLS 1.2+ везде (API, WebSocket, S3), запрет TLS < 1.2 и слабых шифров; certificate pinning на мобильных клиентах (опционально, с механизмом обновления). Приоритет: Must.
  - Угроза: перехват трафика (MITM).
  - Приёмка: сканирование SSL Labs, mitmproxy-тест. Соответствие: ASVS 9.1, MASVS V5.
- **SEC-4.2**: Шифрование данных at rest: БД (YDB) – шифрование на уровне платформы; файлы S3 – SSE (server-side encryption). Приоритет: Must.
  - Угроза: утечка данных при краже носителей/бэкапов.
  - Приёмка: проверка конфигурации хранилищ. Соответствие: NIST SP 800-53 SC-28.
- **SEC-4.3**: Классификация данных: PII (телефон, email, геолокация, фото) помечаются и обрабатываются по усиленным правилам (минимизация, маскирование в логах). Приоритет: Must.
  - Угроза: утечка PII, штрафы регуляторов.
  - Приёмка: аудит логов – отсутствие PII в открытом виде.
- **SEC-4.4**: Маскирование/псевдонимизация PII в аналитических и тестовых окружениях (тестовые данные – синтетические). Приоритет: Should.
  - Угроза: утечка данных через тестовые среды.
  - Приёмка: проверка тестовых БД.
- **SEC-4.5**: Шифрование чувствительных полей на клиенте (если применимо): локальные данные – Keychain/Keystore, AES-256-GCM с ключом в Keystore. Приоритет: Should.
  - Угроза: извлечение данных с устройства.
  - Приёмка: тест на рутнутом устройстве (frida-скрипты). Соответствие: MASVS V6.

### SEC-5. Валидация ввода и защита от OWASP Top 10

- **SEC-5.1**: Валидация всех входных данных на сервере (типы, длины, форматы, whitelist-подход); параметризованные SQL-запросы для YDB. Приоритет: Must.
  - Угроза: SQL/NoSQL-инъекции.
  - Приёмка: SAST + ручные инъекционные тесты. Соответствие: ASVS 5.1, 5.2; OWASP Top 10 A03.
- **SEC-5.2**: Защита от XSS: экранирование вывода на сервере, CSP-заголовки, запрет опасного HTML. Приоритет: Must.
  - Угроза: кража сессий через stored/reflected XSS.
  - Приёмка: DAST-тесты, проверка заголовков. Соответствие: ASVS 5.1.1, 5.4.
- **SEC-5.3**: Защита от SSRF: запрет запросов сервера к внутренним адресам (169.254.169.254, localhost, внутренние сети), валидация URL. Приоритет: Should.
  - Угроза: доступ к метаданным Yandex Cloud через SSRF.
  - Приёмка: тест с подменой URL. Соответствие: ASVS 5.5.4.
- **SEC-5.4**: Безопасная загрузка файлов: проверка типа (magic bytes), размера (лимит 20 МБ), переименование, хранение вне веб-корня, сканирование антивирусом (опционально). Приоритет: Must.
  - Угроза: загрузка вредоносных файлов, RCE через загрузку.
  - Приёмка: тесты загрузки с подменой расширения. Соответствие: ASVS 12.4.
- **SEC-5.5**: Защита от десериализации: не принимать сериализованные объекты от клиента, использовать безопасные форматы (JSON + schema validation). Приоритет: Should.
  - Угроза: RCE через десериализацию.
  - Приёмка: статический анализ. Соответствие: ASVS 5.6.
- **SEC-5.6**: Защита от OWASP Top 10 A04 (Insecure Design): запрет бизнес-логических уязвимостей (негативные сценарии, лимиты операций, анти-автоматизация). Приоритет: Should.
  - Угроза: злоупотребление функциями (фрод, спам, парсинг).
  - Приёмка: abuse-case тесты, threat modeling.

### SEC-6. Безопасность API

- **SEC-6.1**: Rate limiting на уровне API: аутентификация (см. SEC-1.3), поиск, отправка сообщений, создание постов, отправка SMS. Приоритет: Must.
  - Угроза: DoS, SMS-бомбинг, спам.
  - Приёмка: нагрузочные тесты, проверка лимитов. Соответствие: ASVS 13.2.
- **SEC-6.2**: Корректные коды ошибок без раскрытия внутренней информации (стектрейсы, версии, пути). Приоритет: Must.
  - Угроза: разведка (recon).
  - Приёмка: проверка ответов API на ошибки. Соответствие: ASVS 7.4.
- **SEC-6.3**: Версионирование API (/v1/) и политика устаревания (deprecation) с планом миграции. Приоритет: Should.
  - Угроза: breaking changes и незакрытые старые уязвимые версии.
  - Приёмка: проверка маршрутизации.
- **SEC-6.4**: Безопасность WebSocket (чаты): аутентификация при handshake, валидация сообщений, rate limit, шифрование (WSS). Приоритет: Must.
  - Угроза: подмена соединения, спам, прослушивание.
  - Приёмка: тесты соединений, проверка WSS.

### SEC-7. Управление паролями

- **SEC-7.1**: Хэширование паролей: bcrypt (cost 12+) или argon2id; соль уникальная на пароль; запрет хранения в открытом виде/обратимых алгоритмах (MD5/SHA1 без соли). Приоритет: Must.
  - Угроза: утечка БД => компрометация паролей.
  - Приёмка: код-ревью, проверка хэшей. Соответствие: ASVS 2.4, NIST SP 800-63B.
- **SEC-7.2**: Запрет отправки паролей по email/SMS в открытом виде; восстановление пароля – через одноразовую ссылку/код, не через сброс на «старый пароль». Приоритет: Must.
  - Угроза: перехват паролей, фишинг.
  - Приёмка: тест сценария восстановления. Соответствие: ASVS 2.3.
- **SEC-7.3**: Принудительная смена пароля при подозрении на компрометацию (утечка в breached-списках). Приоритет: Should.
  - Угроза: использование украденных паролей.
  - Приёмка: тест сценария.

### SEC-8. Приватность и согласия

- **SEC-8.1**: Согласие на обработку ПДн при регистрации (чекбокс, версия политики конфиденциальности, дата согласия хранится). Приоритет: Must.
  - Угроза: нарушение 152-ФЗ, GDPR.
  - Приёмка: юридическая проверка, аудит хранения согласий.
- **SEC-8.2**: Право на удаление данных (FR-2.4): полное удаление PII из всех систем (включая бэкапы в течение установленного срока) по запросу. Приоритет: Must.
  - Угроза: нарушение GDPR (право на забвение).
  - Приёмка: тест сценария удаления, проверка БД.
- **SEC-8.3**: Экспорт данных (FR-2.5): выдача архива данных пользователя в машиночитаемом формате не позднее 30 дней. Приоритет: Should.
  - Угроза: нарушение GDPR (право на переносимость).
  - Приёмка: тест сценария экспорта.
- **SEC-8.4**: Настройки приватности по умолчанию: профиль «виден друзьям», геолокация не публикуется без явного согласия. Приоритет: Should.
  - Угроза: нежелательное раскрытие PII.
  - Приёмка: проверка дефолтных настроек. Соответствие: Privacy by Design.
- **SEC-8.5**: Обработка запросов на доступ к данным (DSAR) с подтверждением личности (OTP). Приоритет: Should.
  - Угроза: раскрытие данных третьим лицам.
  - Приёмка: тест сценария.

### SEC-9. Мобильная безопасность (iOS / Android)

- **SEC-9.1**: Хранение секретов (токены, ключи шифрования) только в Keychain / Android Keystore; запрет хранения в SharedPreferences, UserDefaults, файлах, логах. Приоритет: Must.
  - Угроза: извлечение секретов с устройства.
  - Приёмка: MobSF + ручной анализ (frida). Соответствие: MASVS V6, OWASP Mobile Top 10 M5.
- **SEC-9.2**: Защита от отладки и реверса: обфускация кода (obfuscator), проверка на jailbreak/root (с мягким/жёстким режимом), защита от Frida-подключения (опционально, с учётом стоимости). Приоритет: Should.
  - Угроза: реверс, обход клиентских проверок.
  - Приёмка: MobSF, тесты на jailbreak-устройстве. Соответствие: MASVS V8.
- **SEC-9.3**: Запрет хранения чувствительных данных в открытых бэкапах (iCloud/Google Drive) – исключение через настройки Keychain (kSecAttrAccessibleWhenUnlockedThisDeviceOnly / non-backup). Приоритет: Should.
  - Угроза: утечка через облачные бэкапы.
  - Приёмка: анализ бэкапа устройства.
- **SEC-9.4**: Безопасная обработка push-уведомлений: не выводить чувствительные данные в уведомлениях на заблокированный экран (опционально). Приоритет: Should.
  - Угроза: подглядывание (shoulder surfing).
  - Приёмка: проверка настроек уведомлений.
- **SEC-9.5**: Защита от клипборд-утечек: не копировать чувствительные данные (пароли, коды) в системный буфер обмена. Приоритет: Should.
  - Угроза: кража данных из буфера обмена другими приложениями.
  - Приёмка: ручной тест.

### SEC-10. Инфраструктура и конфигурация

- **SEC-10.1**: Управление секретами (ключи, пароли БД, JWT_SECRET) только через секрет-менеджер (Yandex Lockbox / env через CI); запрет секретов в коде, репозиториях, логах. Приоритет: Must.
  - Угроза: утечка секретов => полная компрометация.
  - Приёмка: git-secrets / gitleaks сканирование, аудит репозитория. Соответствие: NIST SSDF PW.4, ASVS 6.4.
- **SEC-10.2**: Сетевые правила: Cloud Functions/БД доступны только из внутренней сети, публичный доступ к БД запрещён, Security Groups настроены. Приоритет: Must.
  - Угроза: прямой доступ к БД из интернета.
  - Приёмка: проверка конфигурации, внешний скан портов. Соответствие: NIST SP 800-53 SC-7.
- **SEC-10.3**: Минимальные права сервисных аккаунтов (IAM): принцип наименьших привилегий, раздельные аккаунты для сред (dev/stage/prod). Приоритет: Must.
  - Угроза: lateral movement при компрометации.
  - Приёмка: аудит IAM-политик. Соответствие: NIST SSDF PS.2.
- **SEC-10.4**: Контейнеры/образы: сканирование образов на уязвимости (trivy), запрет запуска от root, read-only FS (если применимо). Приоритет: Should.
  - Угроза: уязвимые зависимости в рантайме.
  - Приёмка: скан образов в CI. Соответствие: NIST SSDF PW.4.
- **SEC-10.5**: Разделение окружений: dev/stage/prod изолированы, в prod запрещены debug-режимы и тестовые данные. Приоритет: Must.
  - Угроза: утечка через тестовые среды.
  - Приёмка: проверка конфигурации сред.

### SEC-11. Логирование, мониторинг и аудит

- **SEC-11.1**: Аудит-лог безопасности: логин/логаут, смена пароля, включение 2FA, удаление аккаунта, действия админов; логи хранятся не менее 1 года (регуляторный минимум), защищены от изменения (append-only). Приоритет: Must.
  - Угроза: отсутствие следов инцидента, расследование невозможно.
  - Приёмка: проверка логов, тест сценариев. Соответствие: ASVS 7.2, NIST SSDF SR.1.
- **SEC-11.2**: Запрет логирования PII и секретов в открытом виде (маскирование телефонов, email, токенов, паролей). Приоритет: Must.
  - Угроза: утечка PII через логи.
  - Приёмка: аудит логов, SAST-правила. Соответствие: ASVS 7.3.
- **SEC-11.3**: Мониторинг аномалий: всплеск неудачных логинов, подозрительные гео-переходы, аномальный трафик API; алерты в SIEM/мессенджер дежурной смены. Приоритет: Should.
  - Угроза: незамеченная атака.
  - Приёмка: тест алертов, проверка дашбордов. Соответствие: NIST SSDF SR.2.
- **SEC-11.4**: Единое время (NTP), корреляция логов (trace ID на запрос). Приоритет: Should.
  - Угроза: невозможность расследования.
  - Приёмка: проверка форматов логов.

### SEC-12. Управление зависимостями и цепочка поставок

- **SEC-12.1**: SCA-сканирование зависимостей (мобильных и серверных) на каждом билде; политика: критичные уязвимости блокируют релиз. Приоритет: Must.
  - Угроза: уязвимые open-source библиотеки (log4j-класс инцидентов).
  - Приёмка: интеграция SCA в CI, политики. Соответствие: NIST SSDF PW.4, OWASP Top 10 A06.
- **SEC-12.2**: Формирование SBOM для релизов (перечень компонентов и версий). Приоритет: Should.
  - Угроза: невозможность быстрой реакции на новые CVE.
  - Приёмка: генерация SBOM в CI. Соответствие: EO 14028, NIST SSDF.
- **SEC-12.3**: Политика обновления зависимостей: регулярные обновления, мониторинг CVE (GitHub Dependabot / аналог), фиксация версий (lock-файлы). Приоритет: Should.
  - Угроза: использование устаревших уязвимых библиотек.
  - Приёмка: проверка lock-файлов, алерты Dependabot.

### SEC-13. Резервное копирование и восстановление

- **SEC-13.1**: Автоматические резервные копии БД (YDB) и Object Storage; RPO <= 1 час, RTO <= 4 часа. Приоритет: Must.
  - Угроза: потеря данных, ransomware.
  - Приёмка: тест восстановления (restore drill). Соответствие: NIST SP 800-53 CP-9, CP-10.
- **SEC-13.2**: Бэкапы шифруются и хранятся в отдельной учётной записи/регионе с ограниченным доступом. Приоритет: Must.
  - Угроза: компрометация бэкапов.
  - Приёмка: проверка шифрования бэкапов, прав доступа.
- **SEC-13.3**: Ежегодные/ежеквартальные учения по восстановлению (disaster recovery drill) с отчётом. Приоритет: Should.
  - Угроза: неработающий план БК.
  - Приёмка: наличие отчёта об учении.

### SEC-14. Обработка инцидентов

- **SEC-14.1**: План реагирования на инциденты (IRP): классификация (S1-S4), контактная цепочка, время реакции (S1 <= 1 час), эскалация. Приоритет: Must.
  - Угроза: хаос при инциденте, затягивание реакции.
  - Приёмка: review плана, tabletop-учение. Соответствие: NIST SP 800-61, SSDF SR.3.
- **SEC-14.2**: Уведомление пользователей и регуляторов об утечке ПДн в сроки: РФ (24 часа – при необходимости, по 152-ФЗ), GDPR (72 часа). Приоритет: Must.
  - Угроза: штрафы, репутационный ущерб.
  - Приёмка: шаблоны уведомлений готовы, сроки зафиксированы.
- **SEC-14.3**: Процесс forensic-сбора (сохранение логов, образов) без уничтожения доказательств. Приоритет: Should.
  - Угроза: невозможность расследования.
  - Приёмка: проверка процедур.

### SEC-15. Соответствие регуляторным требованиям

- **SEC-15.1**: Соответствие 152-ФЗ «О персональных данных»: уведомление Роскомнадзора, согласия, локализация данных на территории РФ (Yandex Cloud РФ). Приоритет: Must.
  - Угроза: штрафы, блокировка.
  - Приёмка: юридический аудит, проверка локализации.
- **SEC-15.2**: Соответствие GDPR для пользователей из ЕС (если выход на ЕС): правовые основания, DSAR, DPA. Приоритет: Should.
  - Угроза: штрафы GDPR (до 4% оборота).
  - Приёмка: юридический аудит.
- **SEC-15.3**: Возрастные ограничения: запрет регистрации до 13 лет (COPPA/152-ФЗ), проверка возраста при регистрации. Приоритет: Should.
  - Угроза: обработка данных несовершеннолетних без согласия родителей.
  - Приёмка: проверка сценария регистрации.

### SEC-16. Процесс безопасной разработки (связь с другими этапами SSDLC)

- **SEC-16.1**: Определение Definition of Done (DoD): задача не завершена без проверки на OWASP Top 10, код-ревью, SAST-прогона. Приоритет: Must.
  - Угроза: попадание уязвимостей в прод.
  - Приёмка: проверка чек-листа DoD на PR. Соответствие: NIST SSDF PW.6.
- **SEC-16.2**: Security Gates в CI/CD: SAST, SCA, секрет-скан блокируют merge при критичных находках. Приоритет: Must.
  - Угроза: уязвимости в коде до тестирования.
  - Приёмка: демонстрация блокировки пайплайна. Соответствие: NIST SSDF PW.4.
- **SEC-16.3**: Threat modeling проводится на этапе Analysis (этап 2) для каждой крупной фичи; результаты учитываются в требованиях. Приоритет: Must.
  - Угроза: пропущенные архитектурные риски.
  - Приёмка: наличие threat model артефакта.
- **SEC-16.4**: Обучение команды: Security Champion в каждой команде, ежегодный тренинг по безопасной разработке. Приоритет: Should.
  - Угроза: человеческий фактор.
  - Приёмка: записи о прохождении тренингов.

## 8. Критерии приемки и Definition of Done (для этапа Requirements)

Этап Requirements считается завершённым, когда выполнены ВСЕ пункты:

- [ ] Все функциональные (FR) и нефункциональные (NFR) требования описаны, имеют уникальные ID и согласованы стейкхолдерами.
- [ ] Требования безопасности (SEC) покрывают OWASP Top 10, OWASP ASVS Level 1+ и OWASP MASVS (для мобильных клиентов).
- [ ] Проведена классификация данных (PII / некритичные) и определены требования к их обработке.
- [ ] Определены регуляторные требования (152-ФЗ, GDPR, возрастные ограничения).
- [ ] Каждое требование имеет критерий приемки (как проверить) и приоритет (MoSCoW).
- [ ] Проведена первичная оценка рисков (вход для этапа 2 Analysis).
- [ ] Требования трассируемы: FR/NFR/SEC связаны с источниками и между собой.
- [ ] Документ утверждён: подписи Product Manager и Security Lead.

## 10. Допущения, зависимости и риски

### Допущения

- Команда владеет инструментами: Semgrep (SAST), MobSF, Frida, Burp Suite, SCA-инструмент.
- Yandex Cloud предоставляет необходимые сервисы безопасности (Lockbox, Security Groups, шифрование).
- Бюджет на безопасность согласован (пентесты, инструменты, обучение).

### Зависимости

- Юридическое заключение по 152-ФЗ/GDPR (до этапа Design).
- Выбор SCA-инструмента и его интеграция в CI (этап 3 Planning).
- Доступность AppSec-ресурса для threat modeling (этап 2 Analysis).

### Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Утечка PII из-за IDOR/ошибок доступа | Высокая | Критичное | SEC-3.2, обязательный pen-test перед релизом |
| Компрометация аккаунтов (credential stuffing) | Высокая | Высокое | SEC-1.1, SEC-1.3, SEC-1.6 (MFA) |
| Уязвимые зависимости | Средняя | Высокое | SEC-12.1, SEC-12.3 |
| Нарушение 152-ФЗ | Средняя | Высокое | SEC-15.1, юридический аудит |
| SSRF к метаданным облака | Средняя | Критичное | SEC-5.3 |

## 11. Метрики безопасности (для этапа Requirements)

- % требований, имеющих критерий приемки (цель: 100%).
- % покрытия OWASP ASVS L1 (цель: >= 80% применимых пунктов отражены в требованиях).
- Количество SEC-требований с приоритетом Must без критерия приемки (цель: 0).
- Количество выявленных рисков с оценкой (вход в этап Analysis).
- Время от старта до утверждения требований (цель: не более 3 недель).
