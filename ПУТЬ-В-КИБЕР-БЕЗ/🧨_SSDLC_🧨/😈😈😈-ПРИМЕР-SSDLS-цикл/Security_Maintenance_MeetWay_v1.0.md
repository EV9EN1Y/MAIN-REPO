## 1. Цель и задачи этапа Maintenance

Цель – поддерживать безопасность системы на протяжении всей эксплуатации: мониторинг угроз, обновления, реагирование на инциденты, периодические оценки, и в конце – безопасное завершение жизненного цикла.

Задачи:
- Непрерывный мониторинг уязвимостей и аномалий.
- Управление патчами и обновлениями (включая 0-day).
- Периодические оценки безопасности (квартальные ревью, ежегодный пентест).
- Реагирование на инциденты в эксплуатации.
- Ротация ключей, управление доступом, бэкапы.
- Безопасный вывод из эксплуатации (retirement).

## 2. Непрерывный мониторинг

| Что мониторим | Инструмент | Периодичность | Реакция |
|---|---|---|---|
| CVE в зависимостях | SCA / Dependabot | Непрерывно | Критичные – патч <= 7 дней |
| Уязвимости образов | trivy | Еженедельно | High+ – патч |
| Аномалии API (всплеск ошибок, rate limit) | Метрики/алерты | Непрерывно | По IRP |
| Неудачные логины, подозрительные входы | SIEM/логи | Непрерывно | Расследование |
| Изменения конфигурации (IAM, Security Groups) | Аудит облака | Еженедельно | Ревью изменений |
| Доступ к секретам | Аудит Lockbox | Ежемесячно | Ревью |

## 3. Управление патчами (patch management)

- Политика: Critical – 7 дней, High – 30 дней, Medium – 90 дней.
- Еженедельный цикл: скан -> оценка -> тест на stage -> деплой.
- Обновление зависимостей: SCA-алерты, авто-PR (Dependabot), ревью и merge.
- 0-day: внеочередной процесс (эскалация, временные компенсации, экстренный патч).
- Ченджлог security-фиксов ведётся и публикуется (для пользователей – при необходимости).

## 4. Периодические оценки

| Оценка | Периодичность | Владелец |
|---|---|---|
| Ревью реестра рисков (RSK/THR) | Ежеквартально | Security Lead |
| Повторный threat modeling (при изменении архитектуры) | По изменению | Security Lead |
| Внешний пентест | Ежегодно + перед крупными релизами | Внешний подрядчик |
| Аудит доступа (IAM, роли, сервисные аккаунты) | Ежеквартально | DevOps |
| Аудит соответствия (152-ФЗ, GDPR) | Ежегодно | DPO |
| Tabletop-учения (инциденты) | Ежеквартально | Security Lead |
| Restore drill (восстановление из бэкапов) | Ежеквартально | DevOps |

## 5. Управление инцидентами в эксплуатации

- Классификация S1-S4, цепочка эскалации, дежурная смена 24/7 (или оговорённое окно).
- Время реакции: S1 <= 1 час, S2 <= 4 часа.
- Процесс: обнаружение -> триаж -> сдерживание -> устранение -> восстановление -> разбор (post-mortem).
- Уведомления: пользователи и регуляторы по срокам (152-ФЗ, GDPR 72 часа).
- База знаний инцидентов (уроки, обновление runbook'ов).

## 6. Ротация ключей и секретов

| Секрет | Периодичность | Триггер внеплановой ротации |
|---|---|---|
| JWT signing key | Ежеквартально | Подозрение на компрометацию |
| Ключи БД | Ежеквартально | Смена персонала с доступом |
| Ключи S3 | Ежеквартально | Инцидент |
| Ключи push/SMS | Ежеквартально | Инцидент |
| Сертификаты TLS | До истечения (автообновление) | Компрометация CA/ключа |

## 7. Управление доступом (жизненный цикл)

- Приём/увольнение: доступы выдаются по RACI, отзываются в день ухода.
- Ежеквартальный ревью: список людей с доступом к prod, админке, секретам.
- Принцип наименьших привилегий, MFA обязательна для всего административного доступа.
- Сервисные аккаунты: минимальные права, мониторинг использования.

## 8. Бэкапы и восстановление

- RPO <= 1 час, RTO <= 4 часа (подтверждается drill'ами).
- Ежеквартальный restore drill с отчётом.
- Бэкапы зашифрованы, в отдельном регионе/учётной записи, доступ ограничен.
- Проверка целостности бэкапов (автоматическая).

## 9. Обновление документации

- Runbook'и и IRP обновляются после каждого инцидента (post-mortem).
- Документация актуализируется при изменении архитектуры/API (в течение 5 дней).
- Ежеквартальный аудит актуальности комплекта документации.

## 10. Вывод из эксплуатации (retirement)

Когда продукт/компонент завершает жизненный цикл:
- [ ] Уведомление пользователей за установленный срок, экспорт данных (DSAR) обеспечен.
- [ ] Безопасное удаление PII из всех систем (БД, S3, бэкапы, логи) по политике хранения.
- [ ] Аннулирование сертификатов, ключей, доступов.
- [ ] Удаление/архивирование инфраструктуры, закрытие Security Groups.
- [ ] Фиксация акта вывода из эксплуатации.
- [ ] Уведомление Роскомнадзора при необходимости (152-ФЗ).

## 11. KPI эксплуатации

| Метрика | Цель |
|---|---|
| Время закрытия Critical CVE | <= 7 дней |
| Время реакции на S1-инцидент | <= 1 час |
| Время восстановления (RTO) | <= 4 часа |
| Успешность restore drill | 100% |
| Открытых High-рисков | <= 3 |
| Ротация ключей по графику | 100% |
| Обновление документации после инцидента | 100% в течение 5 дней |

## 12. Передача опыта в новый цикл SSDLC

Результаты эксплуатации (инциденты, находки пентестов, уроки) передаются в начало следующего цикла SSDLC (этап 1 Requirements) как входные данные: новые требования, обновлённые стандарты, улучшенные чек-листы.
