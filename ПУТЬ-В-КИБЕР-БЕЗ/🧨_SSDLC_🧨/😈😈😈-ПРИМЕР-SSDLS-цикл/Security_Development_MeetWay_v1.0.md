## 1. Цель и задачи этапа Development

Цель – писать код в соответствии со стандартами безопасной разработки, выявлять уязвимости на этапе написания кода (shift-left), а не после релиза.

Задачи:
- Применять secure coding стандарты (OWASP, SEI CERT).
- Интегрировать SAST, SCA, секрет-скан в процесс (PR-гейты).
- Проводить обязательный secure code review.
- Соблюдать Definition of Done (SEC-16.1).

## 2. Стандарты безопасной разработки

| Стандарт | Применение |
|---|---|
| OWASP Secure Coding Practices | Валидация ввода, аутентификация, криптография, обработка ошибок |
| OWASP Top 10 | Чек-лист на каждый PR |
| OWASP ASVS L1/L2 | Критерии приёмки фич |
| SEI CERT (C/C++/Java/Kotlin/Swift) | Правила безопасного кодирования |
| OWASP MASVS | Мобильные клиенты (V2-V8) |

## 3. Secure coding практики по компонентам

### 3.1. Валидация ввода (все компоненты)

- Whitelist-валидация на сервере: тип, длина, формат, диапазон.
- Параметризованные запросы к YDB (запрет конкатенации SQL).
- Экранирование вывода (output encoding) против XSS.
- JSON-schema валидация тела запросов.
- Валидация URL (запрет внутренних адресов, SSRF-защита).
- Загрузка файлов: magic bytes, размер, переименование в UUID.

### 3.2. Аутентификация и сессии (Backend)

- Пароли: argon2id/bcrypt, соль уникальная, запрет собственных алгоритмов хэширования.
- JWT: RS256, короткий TTL, проверка aud/iss/exp, секреты в Lockbox.
- Refresh: opaque-токен, хэш в БД, ротация, отзыв.
- Ограничение попыток: rate limit + временная блокировка.
- Никогда не логировать пароли, токены, коды OTP.

### 3.3. Авторизация (Backend)

- Проверка прав на каждом эндпоинте (серверная, не клиентская).
- Ownership-проверки для ресурсов (IDOR-защита).
- Роли из JWT/БД, не из запроса клиента.
- Deny by default для новых эндпоинтов.

### 3.4. Криптография

- Только утверждённые алгоритмы (дизайн 6.3): AES-256-GCM, RS256, SHA-256, argon2id.
- Запрет: MD5, SHA1, DES, RC4, ECB-режим, самописная криптография.
- Ключи генерируются в Keystore/Lockbox, никогда в коде.

### 3.5. Обработка ошибок

- Единый формат ошибок: код, сообщение (без стектрейсов), trace ID.
- Логирование ошибок с деталями – только на серверной стороне, без PII.
- Fail secure: при исключении доступ закрыт.

### 3.6. Логирование

- Без PII и секретов (маскирование телефонов/email/токенов).
- Аудит-события: логин, смена пароля, 2FA, удаление аккаунта, действия админа.
- Append-only для audit_log, права только на INSERT.

### 3.7. Мобильные клиенты (iOS/Android)

- Хранение: Keychain / EncryptedSharedPreferences+Keystore (запрет UserDefaults/SharedPreferences для секретов).
- Запрет cleartext: ATS (iOS), network security config (Android).
- Обфускация: Swift-obfuscator/R8/ProGuard.
- Root/jailbreak-детект с мягким/жёстким режимом.
- Безопасный WebView (запрет javascript для чужих URL, отключение file-доступа).
- Проверка целостности подписи приложения.
- Не логировать чувствительные данные; защита clipboard.

### 3.8. CI/CD и инфраструктура-как-код

- IaC (terraform/аналоги): секреты через переменные, не в файлах.
- Образы: минимальные, не от root, сканирование (trivy).
- Pipeline: секреты только из CI secrets/Lockbox.

## 4. Secure code review (процесс)

Обязателен для каждого PR:
1. Автор прогоняет SAST локально (pre-commit hook).
2. PR проверяется: SAST, gitleaks, SCA (автоматически, блокируют merge).
3. Code review человеком: чек-лист из 10 пунктов (см. 4.1), минимум 1 ревьюер, для security-критичных файлов – Security Champion/Security Lead.
4. Комментарии ревьюера: severity-метки, обязательное закрытие перед merge.
5. Merge только при зелёных статусах и одобрении.

### 4.1. Чек-лист code review (топ-10)

- [ ] Ввод валидируется на сервере (тип/длина/формат), запросы параметризованы.
- [ ] Вывод экранирован (нет XSS-векторов).
- [ ] Нет хардкода секретов/ключей/токенов.
- [ ] Авторизация и ownership-проверки на месте.
- [ ] Криптография из утверждённого списка, ключи не в коде.
- [ ] Ошибки не раскрывают внутренности, нет PII в логах.
- [ ] Rate limit/лимиты для публичных операций.
- [ ] Работа с файлами безопасна (тип, размер, пути).
- [ ] Нет опасных функций (eval, десериализация недоверенных данных).
- [ ] Новые зависимости прошли SCA, версии зафиксированы.

## 5. Автоматизация в процессе разработки

| Инструмент | Запуск | Действие при находке |
|---|---|---|
| Semgrep (SAST) | pre-commit + на PR | Critical/High – блок merge |
| gitleaks | на PR | Любой секрет – блок merge |
| SCA (Dependabot) | на PR + nightly | Critical CVE – блок merge |
| Форматтеры/линтеры | pre-commit | Обязательны |
| Тесты безопасности (unit/integration) | на PR | Падение – блок merge |
| MobSF | на билд приложения | High+ – блок релиза |

## 6. Git-гигиена

- main защищена: branch protection, обязательное ревью, зелёные статусы.
- Подписанные коммиты (GPG/SSH signing).
- Запрет force-push в main, запрет коммитов напрямую.
- Ветки короткоживущие, feature-флаги для незавершённых фич.
- Мониторинг на утечки секретов в истории (git log scan).

## 7. Definition of Done (DoD) для задач

Задача считается завершённой, если:
- [ ] Реализована по спецификации (FR/SEC-требования).
- [ ] SAST/SCA/gitleaks зелёные.
- [ ] Code review пройден (чек-лист 4.1).
- [ ] Юнит/интеграционные тесты написаны и зелёные (включая негативные security-тесты).
- [ ] Нет PII/секретов в коде и логах.
- [ ] Обновлена документация (если затрагивает API/архитектуру).

## 8. Типичные анти-паттерны (запрещено)

- Конкатенация SQL/запросов с пользовательским вводом.
- Хранение секретов в коде, конфигах, UserDefaults.
- Собственные криптоалгоритмы, использование MD5/SHA1.
- Доверие client-side проверкам (роли, лимиты).
- Логирование паролей, токенов, OTP, полных номеров телефонов.
- Использование неактуальных зависимостей без SCA.
- eval/десериализация недоверенных данных.
- Публичные ACL на бакеты, открытые Security Groups.

## 9. Передача в Documentation и Testing (этапы 6-7)

На этапы 6-7 передаются:
1. Код, прошедший DoD и code review.
2. Отчёты SAST/SCA/gitleaks (для аудита).
3. Список security-тестов, которые необходимо выполнить (из SEC-требований).
4. Обновлённый список компонентов (для SBOM).
5. Задокументированные решения (ADR) и изменения API.
