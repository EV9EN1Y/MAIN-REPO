## 1. Цель и задачи этапа Design

Цель – спроектировать систему так, чтобы безопасность была встроена в архитектуру (secure by design), а не добавлена заплатками. На этом этапе проводится полноценный threat modeling на основе утверждённой архитектуры.

Задачи:
- Построить диаграммы потоков данных (DFD) и определить trust boundaries.
- Провести threat modeling (STRIDE) по каждому потоку данных.
- Зафиксировать архитектурные решения безопасности (криптография, сессии, доступы).
- Провести security design review и согласовать архитектуру.

## 2. Архитектурные принципы (secure by design)

| Принцип | Применение в MeetWay |
|---|---|
| Defense in depth | Несколько слоёв защиты: TLS + валидация + авторизация + шифрование at rest |
| Least privilege | Минимальные права для пользователей, сервисных аккаунтов, ролей |
| Fail secure | При ошибке – закрытый доступ (deny by default), а не открытый |
| Trust boundaries | Чёткие границы: клиент -> API -> БД; ничего не доверяем клиенту |
| Minimize attack surface | Минимум публичных эндпоинтов, отключение неиспользуемых функций |
| Secure defaults | Безопасные настройки по умолчанию (приватность, шифрование) |
| Never trust input | Валидация всего ввода на сервере, параметризация запросов |

## 3. Высокоуровневая архитектура

```text
[iOS / Android клиент]
        | TLS 1.3 (certificate pinning)
        v
[API Gateway / Cloud Functions (Yandex Cloud)]
        |                        |
        v                        v
[YDB (шифрование at rest)]  [Object Storage S3 (SSE, presigned URL)]
        |                        |
        +---- [Lockbox: секреты] +---- [Push-провайдеры (APNs/FCM)]
        |
[CI/CD: SAST -> SCA -> gitleaks -> DAST -> deploy]
        |
[Мониторинг: логи, метрики, алерты (append-only аудит-лог)]
```

## 4. Диаграммы потоков данных (DFD)

### 4.1. DFD уровень 0 (контекст)

| Процесс | Внешние сущности | Данные |
|---|---|---|
| MeetWay | Пользователь (iOS/Android), Админ, Push-провайдер, SMS-провайдер | PII, посты, сообщения, медиа |

### 4.2. DFD уровень 1 (основные процессы)

| ID | Процесс | Вход -> Выход | Хранилище |
|---|---|---|---|
| P1 | Регистрация/аутентификация | Креды -> JWT | YDB (users, sessions) |
| P2 | Управление профилем | Профиль -> ответ | YDB (profiles) |
| P3 | Посты и лента | Пост -> лента | YDB (posts), S3 (медиа) |
| P4 | Чаты и сообщения | Сообщение -> чат | YDB (messages), push |
| P5 | Поиск | Запрос -> результаты | YDB (index) |
| P6 | Модерация/админка | Действия админа | YDB, аудит-лог |

### 4.3. Trust boundaries

| Граница | Что разделяет | Контроль |
|---|---|---|
| TB-1 | Клиент <-> API | TLS, JWT, валидация ввода, rate limit |
| TB-2 | API <-> YDB | Только внутренняя сеть, Security Groups, сервисные аккаунты с минимальными правами |
| TB-3 | API <-> S3 | Presigned URL, SSE-шифрование, ACL private |
| TB-4 | API <-> Push/SMS | Отдельные ключи в Lockbox, rate limit |
| TB-5 | Админ <-> Админка | 2FA обязательна, RBAC, аудит |

## 5. Threat modeling (STRIDE) по утверждённой архитектуре

> Полный threat model по каждой trust boundary. Реестр угроз THR-XXX дополняет реестр рисков этапа 2.

| ID | Граница | STRIDE | Угроза | Митигация (дизайн) |
|---|---|---|---|---|
| THR-001 | TB-1 | S | Подделка JWT / replay | Короткий TTL access (15 мин), ротация refresh, jti-чёрный список |
| THR-002 | TB-1 | I | Перехват трафика (MITM) | TLS 1.3, pinning, запрет cleartext (ATS, network security config) |
| THR-003 | TB-1 | D | DDoS / исчерпание квот | Rate limit на gateway, WAF, автоскейлинг |
| THR-004 | TB-2 | I | Прямой доступ к YDB | Только внутренняя сеть, IAM-роли, шифрование at rest |
| THR-005 | TB-3 | I | Доступ к чужим медиа | Проверка владения до выдачи presigned URL, короткий TTL |
| THR-006 | TB-4 | T | Перехват/подмена push | TLS к провайдерам, ключи в Lockbox, валидация токенов устройств |
| THR-007 | TB-5 | E | Эскалация прав админа | RBAC, SoD, 2FA, аудит-лог append-only |
| THR-008 | Вся система | R | Отсутствие следов действий | Аудит-лог всех чувствительных операций, trace ID |
| THR-009 | API | T | Инъекции | Параметризация YDB-запросов, whitelist-валидация |
| THR-010 | Клиент | I | Извлечение данных с устройства | Keychain/Keystore, обфускация, защита от root/jailbreak |

## 6. Архитектурные решения безопасности

### 6.1. Аутентификация и сессии

- Пароли: argon2id (или bcrypt cost 12+) с уникальной солью.
- Access token: JWT, TTL 15 минут, подпись RS256 (асимметричная, ключ подписи в Lockbox).
- Refresh token: случайный opaque-токен в БД (хэш), ротация при каждом использовании, отзыв при logout/смене пароля.
- MFA: TOTP (основной), SMS-OTP (резервный). Обязательна для админов.
- Верификация: OTP на email/SMS, срок 5 минут, 5 попыток.

### 6.2. Авторизация

- RBAC: user / moderator / admin. Матрица прав в коде + проверка на сервере.
- Владельческие проверки (ownership) для всех ресурсов: посты, чаты, профили, медиа.
- Запрет доверия client-side ролям: роли приходят только с сервера (в JWT claims или отдельным запросом).

### 6.3. Криптография

| Область | Решение | Обоснование |
|---|---|---|
| Канал | TLS 1.3 (мин. 1.2), HSTS | Защита от MITM |
| Пароли | argon2id / bcrypt | Устойчивость к брутфорсу |
| Данные at rest | AES-256 (YDB), SSE-S3 | Защита хранилищ |
| Токены | RS256 JWT | Асимметричная подпись |
| Локальные данные клиента | AES-256-GCM, ключ в Keystore | Защита на устройстве |
| Хэши refresh-токенов | SHA-256 | Хранение без plaintext |

### 6.4. Дизайн API

- REST + версионирование `/v1/`, JSON + schema validation.
- Все state-changing запросы: авторизация + idempotency-ключи (сообщения).
- Ошибки: единый формат без внутренних деталей (код, сообщение, trace ID).
- Rate limit: по пользователю и по IP (login, поиск, сообщения, SMS).
- WebSocket (чаты): WSS, аутентификация при handshake, валидация каждого сообщения.

### 6.5. Дизайн данных (YDB)

- Таблицы: users, profiles, sessions (refresh), posts, comments, messages, media, audit_log.
- PII-поля: зашифрованы/маскированы в логировании; разделение чувствительных полей.
- TTL/политика удаления: сообщения и логи по политике хранения.
- Аудит-лог: append-only (отдельная таблица, права только на INSERT).

### 6.6. Дизайн медиа (S3)

- Bucket private, доступ только через presigned URL (TTL 15 минут, однократное использование для upload).
- SSE-S3 шифрование, версионирование bucket (защита от случайного удаления).
- Проверка MIME по magic bytes на upload, лимит 20 МБ, переименование в UUID.

### 6.7. Мобильная архитектура

- iOS: Keychain (kSecAttrAccessibleWhenUnlockedThisDeviceOnly), ATS (запрет http), обфускация, jailbreak-детект.
- Android: EncryptedSharedPreferences + Keystore, network security config (запрет cleartext), root-детект, R8/ProGuard.
- Push: токены устройств в БД зашифрованы, при logout – удаление токена.

### 6.8. Дизайн CI/CD

- Ветки: main защищена (branch protection, ревью, статусы SAST/SCA/gitleaks обязательны).
- Подпись артефактов (codesign iOS, apksigner Android), SBOM на релиз.
- Секреты: только в Lockbox/CI secrets, запрет в коде и логах.

## 7. Security design review (процесс)

Проводится для каждой крупной фичи до начала разработки:
1. Обновлённый DFD и trust boundaries.
2. STRIDE по новым потокам.
3. Чек-лист: OWASP ASVS L1/L2, MASVS, принципы secure by design.
4. Решение: approve / approve with comments / rework.
5. Фиксация в реестре решений (ADR - Architecture Decision Records).

Критерии approve:
- [ ] Нет новых Critical/High угроз без митигации.
- [ ] Все trust boundaries определены и контролируются.
- [ ] Криптография выбрана из утверждённого списка (6.3).
- [ ] PII обрабатывается по классификации (этап 2, раздел 5).

## 8. Передача в Development (этап 5)

На этап 5 Development передаются:
1. Утверждённая архитектура и DFD.
2. Модель угроз THR-001..010 с назначенными митигациями.
3. Спецификация API (схемы, авторизация, rate limit).
4. Криптографические стандарты (6.3) – обязательные для реализации.
5. Secure coding стандарты и чек-листы (разрабатываются на этапе 5).
