## 1. Цель и задачи этапа Documentation

Цель – зафиксировать архитектуру, процессы и контрольные меры в документации, чтобы обеспечить:
- Проведение аудитов и проверок соответствия (152-ФЗ, GDPR, внутренние политики).
- Быстрое реагирование на инциденты (runbook'и, контакты).
- Поддержку и развитие системы без потери контекста безопасности.

Задачи:
- Составить перечень обязательных документов.
- Определить владельцев и периодичность обновления.
- Обеспечить контроль версий и доступ.

## 3. Требования к документам

- Каждый документ: владелец, версия, дата, статус (draft/reviewed/approved).
- Контроль версий в репозитории (git) или вики с историей.
- Обязательная актуализация при изменении архитектуры, API, процессов.
- Доступ по ролям (RACI), чувствительные документы (IRP, секретные процедуры) – ограниченный доступ.
- Язык: русский (команда), технические термины – на английском.

## 4. Процесс обновления документации

1. Триггер обновления: изменение архитектуры (ADR), API, инфраструктуры, регуляторики, инцидент.
2. Владелец документа вносит изменения в течение 5 рабочих дней.
3. Ревью документа: Security Lead (для security-документов), Architect (для архитектуры).
4. Фиксация версии, отметка в ченджлоге.
5. Ежеквартальный аудит актуальности всего комплекта.

## 5. Документация для аудитов

Подготовка к аудиту (152-ФЗ, GDPR, клиентские):
- Карта данных и журнал согласий.
- Политики обработки ПДн.
- Отчёты сканирований и пентестов.
- Журнал инцидентов и реагирования.
- Доказательства контроля доступа (IAM-аудит).
- Доказательства обучения команды.

## 6. Передача в Testing (этап 7)

На этап 7 Testing передаются:
1. API-спецификация (для тестов).
2. Отчёты SAST/SCA (базовая линия для DAST/пентеста).
3. Модель угроз THR (для тест-кейсов).
4. SEC-требования с критериями приёмки (для верификации).
5. Runbook'и (для проверки эксплуатационных процедур).
