## 1. Цель и область анализа

Цель этапа Analysis – количественно и качественно оценить уязвимости системы, построить карту угроз (threat landscape) и спланировать худшие сценарии (worst-case), а не рассчитывать на лучшее стечение обстоятельств.

Задачи:
- Инвентаризация активов и классификация данных.
- Построение модели угроз по методологии STRIDE.
- Оценка рисков (вероятность x влияние) и приоритизация.
- Формирование worst-case сценариев с планами реагирования.
- Подготовка входных данных для этапа 3 Planning (бюджет, инструменты, обучение).

Область: мобильные клиенты (iOS, Android), API (Yandex Cloud Functions), БД (YDB), Object Storage (S3), push-уведомления, админ-панель, CI/CD.

## 2. Входные данные

- SRS_MeetWay_v1.0.md – функциональные, нефункциональные и требования безопасности (SEC-1..SEC-16).
- Схема архитектуры (черновик, уточняется на этапе 4 Design).
- Перечень регуляторных требований (152-ФЗ, GDPR, возрастные ограничения).
- Результаты первичной оценки рисков из этапа 1 (раздел 10 SRS).

## 3. Методология

### 3.1. Модель угроз STRIDE

| Категория | Угроза | Пример для MeetWay |
|---|---|---|
| S – Spoofing | Подмена личности | Подделка JWT, захват чужого аккаунта |
| T – Tampering | Изменение данных | Подмена сообщений, постов, медиафайлов |
| R – Repudiation | Отказ от действий | Отрицание отправки сообщения, действий админа |
| I – Information Disclosure | Раскрытие информации | IDOR, утечка PII, SSRF к метаданным |
| D – Denial of Service | Отказ в обслуживании | DDoS API, спам, исчерпание квот облака |
| E – Elevation of Privilege | Повышение привилегий | Эскалация user -> admin, обход RBAC |

### 3.2. Оценка риска

- Вероятность (P): 1 – маловероятно, 2 – низкая, 3 – средняя, 4 – высокая, 5 – почти гарантированно.
- Влияние (I): 1 – незначительное, 2 – низкое, 3 – среднее, 4 – высокое, 5 – критическое.
- Уровень риска = P x I (матрица 5x5, см. Приложение 13.2).
- Градации: Critical (15-25), High (8-12), Medium (4-6), Low (1-3).

### 3.3. DREAD (для топ-рисков)

Оценка по 5 факторам: Damage, Reproducibility, Exploitability, Affected users, Discoverability (шкала 1-10). Применяется к рискам уровня High/Critical для детального ранжирования.

## 8. Worst-case сценарии (планирование худшего)

> По IBM SSDLC: анализ готовит команду к худшим сценариям, а не к оптимистичным допущениям.

### WC-1. Полная утечка БД (PII всех пользователей)

- Триггер: компрометация доступа к YDB (украденный ключ, SSRF, инсайдер).
- Цепочка: доступ к БД -> выгрузка PII -> публикация/продажа данных.
- Последствия: штрафы (152-ФЗ, GDPR), репутационный ущерб, отток пользователей, судебные иски.
- Реагирование: IRP (SEC-14.1), отзыв ключей, уведомление пользователей и регуляторов (SEC-14.2), forensic-сбор (SEC-14.3).
- Метрика восстановления: уведомление регулятора <= 72 часа (GDPR), изоляция доступа <= 1 час.

### WC-2. Массовый захват аккаунтов (credential stuffing)

- Триггер: утечка паролей на сторонних сервисах + отсутствие MFA у пользователей.
- Цепочка: автоматизированный перебор -> захват аккаунтов -> рассылка спама, фишинг друзьям, кража данных.
- Последствия: массовые жалобы, блокировка в магазинах приложений, потеря доверия.
- Реагирование: принудительный сброс паролей (SEC-7.3), временное усиление rate limiting (SEC-1.3), обязательная 2FA при подозрительном входе (SEC-1.5).

### WC-3. SSRF к метаданным облака (компрометация сервисных ключей)

- Триггер: уязвимость в обработке URL (загрузка по ссылке, парсинг) -> запрос к 169.254.169.254.
- Цепочка: кража IAM-токена -> доступ ко всем сервисам Yandex Cloud -> утечка данных.
- Последствия: полная компрометация облачного окружения.
- Реагирование: ротация всех ключей, аудит IAM (SEC-10.3), проверка логов на аномальные вызовы.

### WC-4. Ransomware / уничтожение данных

- Триггер: компрометация CI/CD или админки -> шифрование/удаление БД и S3.
- Последствия: остановка сервиса, потеря данных.
- Реагирование: восстановление из бэкапов (SEC-13.1, RTO <= 4 часа), изоляция заражённых сегментов.

### WC-5. Инсайдер (админ/разработчик со злым умыслом)

- Триггер: легитимный доступ использован для кражи данных.
- Последствия: утечка PII, саботаж.
- Реагирование: аудит-логи (SEC-11.1), разделение обязанностей (SEC-3.4), ограничение экспорта данных, мониторинг аномалий (SEC-11.3).

### WC-6. DDoS / исчерпание квот облака

- Триггер: атака на API или спам-кампания (SMS-бомбинг, массовая регистрация).
- Последствия: недоступность сервиса, финансовые потери (квоты).
- Реагирование: rate limiting (SEC-6.1), анти-автоматизация (CAPTCHA, SEC-5.6), алерты и автоскейлинг (NFR-2, NFR-3).
