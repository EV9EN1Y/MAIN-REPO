# Как устроена работа в компании: SSDLC на практике

Версия: 1.0 | Дата: 04.08.2026 | Назначение: понять, как процессы безопасности живут в реальной компании – от kick-off проекта до эксплуатации, глазами всех ролей.

---

## 1. Главная мысль

SSDLC – это **не «неделя в начале проекта» и не набор документов**. Это постоянный процесс, встроенный в повседневную работу: каждая фича проходит через него (в облегчённом виде), каждый релиз – через полный цикл, а безопасность обновляется всю жизнь продукта. Документы – это только «скелет», который наполняется действиями каждый день.

Уровень безопасности в системе **падает сам по себе**, если его не поддерживать: зависимости стареют, выходят новые CVE, меняются законы, появляются новые техники атак. Поэтому процесс никогда не останавливается.

---

## 2. Роли и их зона ответственности

Каждая роль видит процесс по-своему и отвечает за свой кусок. Вся система держится на том, что эти куски стыкуются.

### 🏢 Руководство (CTO / CEO / владелец продукта)

- Задаёт **тон сверху**: безопасность – приоритет или «потом».
- Утверждает **бюджет**: инструменты, пентесты, обучение, зарплата AppSec.
- Принимает **стратегические решения** при конфликте «скорость vs безопасность» (risk acceptance на уровне компании).
- Ничего не пишет и не кодит, но от его позиции зависит, будет ли SSDLC жить или останется бумажкой.

### 📋 Product Manager (PM)

- Владелец **приоритетов**: что делаем, в каком порядке, к каким дедлайнам.
- Переводит бизнес-требования в задачи, согласует компромиссы (фича vs срок vs безопасность).
- Отвечает за то, чтобы **требования безопасности попали в бэклог** наравне с фичами.
- Подписывает релиз (go/no-go вместе с Security Lead).

### 👨‍💻 Tech Lead

- Разбирает крупные задачи на **подзадачи** и распределяет между разработчиками.
- Отвечает за архитектуру и **code review**.
- Следит за соблюдением DoD (Definition of Done) в команде.
- Первая линия эскалации технических проблем.

### 🛡️ Security Lead / AppSec-инженер

- Составляет **требования безопасности** (SEC), стандарты, чек-листы.
- Проводит **threat modeling** на архитектуре и крупных фичах.
- Настраивает и следит за **CI/CD security gates** (SAST, SCA, gitleaks, DAST).
- Организует **пентесты**, анализирует находки, ведёт реестр рисков.
- Управляет **инцидентами** безопасности и post-mortem.
- Единственная роль, которая может **заблокировать релиз** (veto).

### ⭐ Security Champion

- Разработчик в команде, прошедший доп. обучение по безопасности.
- **Мост** между командой и AppSec: переводит требования на язык разработчиков.
- Проводит security-ревью PR, помогает с безопасным кодированием.
- Нужен, чтобы AppSec не был бутылочным горлышком на каждую мелочь.

### 👨‍🔧 Разработчик (Backend / Mobile)

- Пишет код по **secure coding стандартам** (валидация, параметризация, Keychain/Keystore).
- Прогоняет SAST локально до PR, закрывает свои находки.
- Проходит code review, участвует в threat modeling своей фичи.
- Самая массовая роль – от их привычек зависит 80% результата.

### ⚙️ DevOps / SRE

- Строит **CI/CD** с security gates, настраивает инфраструктуру (Security Groups, секреты, TLS).
- Управляет **секретами** (Lockbox), бэкапами, обновлениями (patch management).
- Дежурный по мониторингу и алертам.

### 🧪 QA Lead

- Верифицирует **критерии приёмки** требований, включая security-тесты.
- Гоняет негативные сценарии, помогает с DAST.
- Фиксирует дефекты с severity и следит за SLA исправления.

### ⚖️ DPO / Юрист

- Отвечает за **регуляторику**: 152-ФЗ, GDPR, согласия, DSAR (запросы пользователей на данные).
- Пишет политику конфиденциальности, проверяет соответствие.
- Включается в инциденты (уведомление регуляторов в сроки).

## 3. Как всё начинается: kick-off проекта

Перед стартом крупного проекта выделяется **1-2 недели** (иногда больше для банков/гос). Это не «написание документов ради документов», а проектирование скелета, по которому дальше пойдёт вся работа.

**Что происходит по шагам:**

1. **SRS (требования)** – PM собирает функциональные требования, AppSec добавляет требования безопасности (SEC) по стандартам (ASVS/MASVS) под тип проекта.
2. **Анализ рисков** – AppSec + архитектор считают активы, строят модель угроз (STRIDE), составляют реестр рисков, worst-case сценарии.
3. **План** – роли (RACI), бюджет, инструменты, дорожная карта, CI/CD gates, обучение.
4. **Дизайн** – архитектор проектирует систему, AppSec проводит threat modeling по DFD, фиксируются крипторешения.
5. **Настройка CI/CD** – DevOps поднимает пайплайн с SAST/SCA/gitleaks, пороги блокировки.
6. **Согласование** – руководство утверждает бюджет и политику рисков.

**Выход kick-off:** рабочий процесс, в котором каждая фича автоматически проходит security-проверки. Дальше документы живут своей жизнью и обновляются.

> Важно: kick-off делается один раз на проект/крупную веху. Не на каждую фичу.

## 4. Постоянный цикл: как живёт каждая фича

После kick-off начинается рутина. **Каждая фича** проходит облегчённый цикл – это и есть SSDLC в действии.

### 4.1. Лёгкий цикл фичи (обычная задача)

```text
Идея/бэклог
   │
   ▼
1. Требование        PM формулирует фичу; если несёт риски (данные,
   │                 доступы, интеграции) – AppSec добавляет SEC-требования
   ▼
2. Оценка риска      Threat modeling «на коленке»: какие данные трогает,
   │                 кто может атаковать, что будет при взломе
   ▼
3. Реализация        Разработчик пишет код по secure coding + гоняет SAST локально
   │
   ▼
4. Проверка          PR: SAST + SCA + gitleaks автоматически (блокируют merge),
   │                 code review (Security Champion для security-критичных файлов)
   ▼
5. Тест              QA: функциональные + негативные security-тесты
   │
   ▼
6. Merge/деплой      Фича уходит в релизный цикл
```

**Роли в этом цикле:** PM (1) → AppSec (2) → разработчик (3) → CI/CD + Champion (4) → QA (5) → DevOps (6).

### 4.2. Тяжёлый цикл релиза (полные 9 фаз)

Релиз (крупная версия, например v1.0) прогоняется **полностью**:

1. **Requirements** – все требования собраны, включая новые SEC.
2. **Analysis** – риски пересчитаны, модель угроз обновлена.
3. **Planning** – ресурсы, бюджет, график.
4. **Design** – архитектура + threat modeling.
5. **Development** – код по стандартам, SAST/SCA на каждом PR.
6. **Documentation** – обновлены документы, runbook'и, SBOM.
7. **Testing** – полный прогон: DAST, MobSF, ручные тесты, **внешний пентест**.
8. **Deployment** – hardening, post-deploy checks, watch window.
9. **Maintenance** – передача в эксплуатацию.

**Ключевая точка релиза – go/no-go:** Security Lead (AppSec) + QA + PM подписывают решение. Если есть открытые Critical/High риски – релиз не выходит, пока не исправят.

### 4.3. Как масштабируется тяжесть

| Тип изменения | Что прогоняется |
|---|---|
| Мелочь (цвет кнопки, текст) | SAST на PR + code review |
| Обычная фича (новый экран) | Лёгкий цикл: риск → код → SAST → тест |
| Крупная фича (платежи, геолокация) | Лёгкий цикл + отдельный threat modeling + усиленные тесты |
| Релиз | Полный 9-фазный цикл + пентест + go/no-go |
| Банк/гос (любое изменение) | Всегда тяжёлый процесс, любые изменения через контроль |

## 5. CI/CD – автоматический страж

Настраивается один раз, дальше работает сам. Это «робот-охранник», который не устаёт и не пропускает мимо глаз.

| Гейт | Когда | Что делает | Порог блокировки |
|---|---|---|---|
| SAST (Semgrep) | Каждый PR | Ищет уязвимости в коде | Critical/High – блок merge |
| Секрет-скан (gitleaks) | Каждый PR | Ищет пароли/ключи в репо | Любая находка – блок |
| SCA (Dependabot) | PR + nightly | Ищет CVE в зависимостях | Critical CVE – блок |
| DAST (ZAP) | nightly + перед релизом | Тестирует API извне | High+ – блок релиза |
| MobSF | на каждый билд | Анализ мобильного клиента | High+ – блок релиза |
| SBOM | на релиз | Перечень компонентов | – |

**Почему это важно:** разработчик не может «забыть» прогнать SAST – пайплайн не даст замерджить. Безопасность становится частью процесса, а не вопросом дисциплины.

## 6. Обнаружение дыр: что происходит

Дыры приходят из разных источников. У каждого свой маршрут, но финал один: **фикс → ре-тест → урок → обновление требований**.

### 6.1. Источники находок

| Источник | Кто находит | Пример |
|---|---|---|
| SAST/SCA в CI | Автоматически | SQL-инъекция в новом коде |
| DAST | Автоматически | XSS в API |
| Code review | Разработчик/Champion | Пропущенная проверка прав |
| Ручные security-тесты | QA/AppSec | IDOR на новом эндпоинте |
| Пентест | Внешний подрядчик | Критичная уязвимость перед релизом |
| Мониторинг | DevOps/AppSec | Аномальная активность в проде |
| Bug bounty / репорты | Внешние исследователи | Уязвимость, найденная «снаружи» |
| Инцидент | Дежурный | Взлом, утечка |

### 6.2. Процесс обработки находки (триаж)

```text
Находка
  │
  ▼
1. Триаж (AppSec):     реальная или ложная? Какая severity (Critical/High/Medium/Low)?
  │                    Какой актив затронут? Можно ли воспроизвести?
  ▼
2. Оценка влияния:     кто пострадал (пользователи, данные, деньги), насколько легко
  │                    эксплуатировать (DREAD)
  ▼
3. Решение:            фиксить / принять риск / компенсировать (мониторинг, WAF-правило)
  │
  ▼
4. Задача на фикс:     в бэклог с приоритетом и SLA (Critical – немедленно, High – 5 дней)
  │
  ▼
5. Фикс + ре-тест:     разработчик чинит → AppSec/QA перепроверяет (ре-тест обязателен)
  │
  ▼
6. Урок:               post-mortem / запись: как дыра появилась, как не допустить снова
  │
  ▼
7. Новое требование:   если дыра типовая → добавляется SEC-требование / SAST-правило /
                       пункт в чек-лист code review (чтобы не повторилось)
```

### 6.3. SLA по severity

| Severity | Пример | SLA на фикс |
|---|---|---|
| Critical | RCE, утечка всей БД, обход аутентификации | Немедленно, релиз блокируется |
| High | IDOR, XSS, утечка PII | 5 рабочих дней |
| Medium | Слабые настройки, инфо-утечки | 15 рабочих дней |
| Low | Косметика, рекомендации | По плану |

## 7. Инцидент: полный цикл

Инцидент (взлом, утечка, компрометация) – это экстренный сценарий, отработанный заранее (план IRP).

```text
1. Обнаружение        Мониторинг/алерт/репорт. Дежурный подтверждает, классифицирует (S1-S4)
   │
   ▼
2. Сдерживание        Остановить кровь: отключить доступ, отозвать ключи, изолировать
   │                  (время реакции: S1 <= 1 час)
   ▼
3. Устранение         Убрать первопричину: патч, откат, пересоздание
   │
   ▼
4. Восстановление     Вернуть сервис, восстановить из бэкапов, проверить целостность
   │
   ▼
5. Уведомления        Пользователи + регуляторы в сроки (152-ФЗ, GDPR: 72 часа)
   │
   ▼
6. Post-mortem        Разбор: хронология, первопричина, что сработало/нет
   │
   ▼
7. Действия           Задачи с владельцами: фиксы, новые требования, обновление
                      runbook'ов, обучение
   │
   ▼
8. В память процесса  Находки инцидента -> новые SEC-требования, SAST-правила,
                      улучшение мониторинга
```

**Кто что делает:** дежурный (1-2), DevOps (2-4), Security Lead (всё координирует, 6-8), DPO (5), PM (коммуникация, 5).

## 8. Откуда берутся новые требования безопасности

Требования **не застывают** после kick-off. Они обновляются из 5 источников:

1. **Новые фичи** – добавили платежи → PCI DSS; геолокацию → новые правила приватности; чаты → шифрование сообщений.
2. **Инциденты** – взломали через XSS → добавили требование «CSP на всех страницах» + SAST-правило.
3. **Пентесты** – нашли дыру → новое требование с критерием приёмки, чтобы дыра не вернулась.
4. **Регуляторика** – вышел новый ГОСТ/закон → компания обязана соответствовать → новые требования.
5. **Технологии** – перешли на новую библиотеку/облако → пересмотр требований под новую платформу.

Каждое новое требование проходит: формулировка → обоснование (угроза) → критерий приёмки → приоритет → владелец → дата. И попадает в SRS/бэклог.

## 9. Maintenance: когда фич нет

Когда разработка затихает, безопасность **не останавливается** – она переходит в режим поддержки. Пассивность здесь опасна: бездействие = деградация.

| Действие | Периодичность | Зачем |
|---|---|---|
| Патчи зависимостей | Critical за 7 дней, High за 30 | CVE копятся, если не чинить |
| Мониторинг CVE/0-day | Непрерывно | Быстрая реакция на новые уязвимости |
| Ротация ключей и секретов | Ежеквартально | Ограничить ущерб от утечки ключей |
| Ревью реестра рисков | Ежеквартально | Риски меняются, старые закрываются |
| Tabletop-учения | Ежеквартально | Проверка готовности к инцидентам |
| Restore drill (бэкапы) | Ежеквартально | Бэкап, который не восстановили = его нет |
| Внешний пентест | Ежегодно | Свежий взгляд со стороны |
| Аудит доступов (IAM) | Ежеквартально | Уволившиеся/ушедшие не должны сохранять доступ |
| Обновление документации | При изменениях | Runbook'и должны быть актуальными |

## 10. Модернизация самого процесса

SSDLC тоже развивается. Компания периодически смотрит на свой процесс и улучшает его:

- **Ретроспективы** – после релизов и инцидентов: что в процессе не сработало.
- **Метрики** – % закрытых High-рисков, MTTR, покрытие SAST, время на фикс. По метрикам видно, где процесс буксует.
- **Модели зрелости** (OWASP SAMM, BSIMM) – оценка уровня: «мы на уровне 1, хотим на 3» → план улучшений.
- **Новые инструменты** – попробовали новый SAST, он ловит больше → обновили пайплайн.
- **Новые угрозы** – вышла новая техника атак → новые правила/требования.
- **Обратная связь команды** – если гейты слишком жёсткие и тормозят всех, процесс калибруется (например, порог блокировки поднимается с «любой находки» до «только Critical»).

Процесс – это живой организм, а не музейный экспонат.

## 11. Сценарий «жизнь фичи» от идеи до прода (пример)

**Фича:** «Добавить геолокацию в посты» (соцсеть).

1. **PM** завёл фичу в бэклог: «пользователи могут добавлять геоточку к посту».
2. **AppSec** на планировании фичи: геолокация = PII → нужны SEC-требования: явное согласие, настройка приватности, шифрование при передаче, запрет публикации по умолчанию.
3. **Архитектор + AppSec** – короткий threat modeling: кто может украсть гео? (IDOR на эндпоинте гео, перехват). Добавили: проверка владения, TLS, rate limit.
4. **Разработчик** реализует с учётом требований: валидация координат на сервере, ownership-проверка, согласие в UI.
5. **CI/CD** прогнал SAST/SCA/gitleaks – всё зелёное, merge.
6. **QA** проверил: гео чужого юзера не отдаётся (403), без согласия не публикуется, в логах координаты маскируются.
7. **DAST** на nightly ничего не нашёл.
8. Фича ушла в релизный цикл → в релизе пройдёт полный прогон.

**Итог:** фича с PII прошла полный контур SSDLC за пару спринтов, не создав долгов.

## 12. Сценарий «нашли критичную дыру» (пример)

**Событие:** пентестер нашёл IDOR: можно читать чужие личные сообщения, подменяя chat_id в запросе.

1. **Триаж (AppSec):** реальная, воспроизводится, High (утечка приватных данных) → ставим Critical, т.к. массовый доступ к PII.
2. **Решение:** блокируем релиз, фиксим в рамках SLA (немедленно).
3. **Разработчик:** добавляет ownership-проверку (владелец чата = текущий пользователь) на сервере.
4. **AppSec/QA ре-тест:** повторяют атаку – 403. Закрыто.
5. **Урок:** IDOR появился потому, что новый эндпоинт писали без проверки прав.
6. **Новое требование:** в SRS добавлено SEC-требование «ownership-проверки для всех ресурсов» + пункт в чек-лист code review + SAST-правило, ловящее подобные паттерны.
7. **Проверка всей кодовой базы:** прогнали поиск похожих мест – нашли и закрыли ещё 2 эндпоинта с той же проблемой.
8. **Отчёт руководству:** что было, что сделано, что добавлено в процесс.

**Ключевое:** дыра не просто закрывается – из неё извлекается урок, который укрепляет весь процесс (правило + требование + проверка аналогов).

## 13. Как тяжесть процесса зависит от компании

| Компания | Процесс | Почему |
|---|---|---|
| Стартап (MVP) | Облегчённый: SAST+SCA на PR, базовые требования | Скорость важнее, риски принимаются осознанно |
| Средняя (соцсеть, SaaS) | Полный SSDLC: threat modeling, гейты, пентест перед релизом | Есть PII пользователей, репутация |
| Банк / финтех | Максимальный: ASVS L2/L3, MASVS L2+R, PCI DSS, аудиты, все изменения через контроль | Деньги, регуляторика, штрафы |
| Гос / оборонка | Жёсткий: ГОСТы, ФСТЭК, аттестация, любые изменения по регламенту | Законодательные требования |

Одна и та же методология SSDLC, разная глубина применения. **Уровень строгости = f(риск, регуляторика, цена ошибки).**

## 14. Частые ошибки и мифы

| Миф | Реальность |
|---|---|
| «Безопасность делается в конце, перед релизом» | Это самый дорогой вариант: фикс на этапе тестирования стоит в десятки раз дороже, чем на этапе требований |
| «Мы написали документы SSDLC – мы защищены» | Документы без процесса – бумага. Защищает только выполнение |
| «AppSec должен проверять каждую строчку» | Для этого есть CI/CD и Security Champions; AppSec управляет процессом, а не тонет в PR |
| «У нас нет бюджета на безопасность» | SAST/SCA/gitleaks бесплатны, base-level обходится дёшево; дорого – игнорировать и платить за инциденты |
| «Если фич нет – ничего не делаем» | Maintenance активный: патчи, ротация, учения. Без этого уровень безопасности падает |
| «Пентест один раз = безопасно навсегда» | Пентест – снимок на момент времени. Код меняется, уязвимости появляются снова |

## 15. Итоговая картина (одна схема)

```text
KICK-OFF (1-2 недели): SRS + риски + план + дизайн + CI/CD
        │
        ▼
   ПОСТОЯННЫЙ ЦИКЛ:
   ┌─────────────────────────────────────────────┐
   │  Фича: риск → код → SAST/SCA → ревью → тест │  ← лёгкий прогон, каждый день
   └─────────────────────────────────────────────┘
        │
        ▼
   РЕЛИЗ (полный 9-фазный цикл): тесты + пентест + go/no-go
        │
        ▼
   ЭКСПЛУАТАЦИЯ: патчи, мониторинг, инциденты, ротация, учения
        │
        ├──► дыра найдена → триаж → фикс → ре-тест → урок → новое требование
        ├──► инцидент → сдерживание → устранение → post-mortem → новые правила
        └──► новая фича → снова лёгкий цикл + обновление требований
```

**Три уровня, которые нужно запомнить:**

1. **Стартовый (kick-off)** – один раз на проект: скелет процесса и требований.
2. **Операционный (каждая фича)** – постоянный лёгкий цикл + автоматические гейты в CI/CD.
3. **Поддерживающий (эксплуатация)** – патчи, мониторинг, учения, обновление требований из уроков.

Вся система держится на связке ролей: **руководство даёт бюджет и тон, PM приоритизирует, Tech Lead распределяет, AppSec ставит правила и гейты, разработчики пишут безопасно, DevOps строит пайплайн, QA проверяет, DPO следит за законом.** Если одно звено выпадает – процесс дырявеет.
