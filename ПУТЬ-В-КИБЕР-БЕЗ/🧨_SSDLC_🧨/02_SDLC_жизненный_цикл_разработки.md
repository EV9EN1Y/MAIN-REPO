# SDLC – жизненный ци кл разработки ПО

> Полное руководство: см. остальные файлы в папке SDLC


**SDLC (Software Development Life Cycle)** – процесс разработки программного обеспечения, состоящий из последовательных этапов.

> **SDLC** – Software Development Life Cycle (жизненный цикл разработки программного обеспечения)


**Классические этапы SDLC:**

| Этап                             | Что происходит                       | Вопросы безопасности                                      |
| -------------------------------- | ------------------------------------ | --------------------------------------------------------- |
| **1. Требования (Requirements)** | Сбор и анализ требований заказчика   | Какие данные обрабатываем? Какие регуляторные требования? |
| **2. Анализ и планирование**     | Оценка ресурсов, сроков, рисков      | Оценка рисков безопасности, бюджет на безопасность        |
| **3. Дизайн/Проектирование**     | Архитектура, выбор технологий        | Threat modeling, security-требования к архитектуре        |
| **4. Разработка (Coding)**       | Написание кода                       | Secure coding, code review, SAST                          |
| **5. Тестирование**              | Проверка функциональности и качества | DAST, пентест, тестирование уязвимостей                   |
| **6. Деплой/Внедрение**          | Выкатка в продакшн                   | Проверка конфигурации, сканирование окружения             |
| **7. Эксплуатация и поддержка**  | Мониторинг, обновления               | Мониторинг инцидентов, патчинг, реагирование на CVE       |

>>"Регуляторные требования" в контексте информационной безопасности - это не просто скучный список правил. Это, по сути, свод законов и стандартов, которые государство или отраслевые надзорные органы устанавливают для бизнеса. Их основная цель – обеспечить защиту информации, персональных данных и критической инфраструктуры, а также установить ответственность за нарушения


**🟢    Модели SDLC:

- **Waterfall (водопад)** – линейная модель, каждый этап строго после предыдущего. Безопасность обычно в конце. Устаревшая, но встречается.
- 
- **Agile/Scrum** – итеративная разработка короткими спринтами. Безопасность должна встраиваться в каждый спринт.
- 
- **DevOps** – разработка и эксплуатация вместе, непрерывная поставка (CI/CD). Безопасность автоматизируется в пайплайнах.
- 
- **DevSecOps** – DevOps + безопасность: безопасность автоматизирована в CI/CD, "security as code".


> **CI/CD** – Continuous Integration / Continuous Delivery 
- (непрерывная интеграция    /   непрерывная поставка)


**На каком этапе SDLC участвует AppSec-инженер?** На всех. Роль называется "security champion" или "AppSec-инженер": на этапе требований он проверяет требования на полноту безопасности, на дизайне проводит threat modeling, на разработке настраивает SAST, на тестировании проводит DAST/пентест, на деплое проверяет конфигурации, в эксплуатации мониторит и реагирует на уязвимости.

> **DAST** – Dynamic Application Security Testing (динамическое тестирование безопасности приложений)

> **SAST** – Static Application Security Testing (статическое тестирование безопасности приложений)

> **AppSec** – Application Security (безопасность приложений)

**1. Требования (Requirements)**
### 📄 Пример 1. Документ требований (этап Requirements)

> Документ: `SRS_MeetWay_v1.0.md` – Software Requirements Specification

```markdown
# Требования к социальной сети "MeetWay"

Версия: 1.0 | Статус: согласовано | Владелец: Product Manager

## 1. Цель проекта
Мобильная социальная сеть для общения: профили, посты, чаты, поиск людей.

## 2. Функциональные требования

### FR-1. Регистрация и авторизация
- FR-1.1: Регистрация по email + пароль и по номеру телефона (SMS-код).
- FR-1.2: Вход по email/телефону + паролю.
- FR-1.3: Восстановление пароля через email/SMS.
- FR-1.4: Выход из аккаунта на всех устройствах.

### FR-2. Профиль пользователя
- FR-2.1: Просмотр и редактирование профиля (имя, фото, bio, город).
- FR-2.2: Просмотр профилей других пользователей.
- FR-2.3: Настройки приватности (кто видит профиль/посты).

### FR-3. Посты и лента
- FR-3.1: Создание, редактирование, удаление постов (текст + фото).
- FR-3.2: Лента постов (свои + друзей), пагинация.
- FR-3.3: Лайки и комментарии.

### FR-4. Чаты
- FR-4.1: Личные чаты (1-на-1) и групповые чаты.
- FR-4.2: Отправка текста, фото, геолокации.
- FR-4.3: Уведомления о новых сообщениях (push).

### FR-5. Поиск людей
- FR-5.1: Поиск по имени/фамилии/городу.
- FR-5.2: Фильтры (возраст, город, интересы).

## 3. Нефункциональные требования

### NFR-1. Производительность
- NFR-1.1: Время загрузки ленты < 500 мс.
- NFR-1.2: Поддержка 100 000 одновременных пользователей.

### NFR-2. Безопасность (кратко, детально – в документе требований безопасности)
- NFR-2.1: Пароли хранить только в виде хэшей (bcrypt/argon2).
- NFR-2.2: Весь трафик – TLS 1.2+.
- NFR-2.3: Доступ к API только по JWT (access + refresh).

## 4. Ограничения
- Платформы: iOS 15+, Android 10+.
- Бэкенд: Yandex Cloud (YDB, Cloud Functions).
```

**2. Анализ и планирование**
### 📄 Пример 2. Документ анализа и планирования (этап Analysis/Planning)

> Документ: `Project_Plan_MeetWay_v1.0.md`

```markdown
# План проекта "MeetWay" – анализ и планирование

## 1. Оценка ресурсов
| Роль                | Кол-во | Занятость | Срок        |
|---------------------|--------|-----------|-------------|
| iOS разработчик     | 2      | 100%      | 4 месяца    |
| Android разработчик | 2      | 100%      | 4 месяца    |
| Backend разработчик | 2      | 100%      | 4 месяца    |
| QA инженер          | 1      | 50%       | 3 месяца    |
| AppSec инженер      | 1      | 25%       | весь проект |
| DevOps              | 1      | 25%       | 2 месяца    |

## 2. Оценка сроков (вехи)
- M1 (месяц 1): архитектура + регистрация/авторизация
- M2 (месяц 2): профили + посты
- M3 (месяц 3): чаты + поиск
- M4 (месяц 4): тестирование, пентест, релиз

## 3. Оценка рисков проекта (бизнес-риски)
| Риск                                    | Вероятность | Влияние | Митигация                        |
|-----------------------------------------|-------------|---------|----------------------------------|
| Задержка сроков из-за авторизации       | Высокая     | Высокое | Начать с MVP авторизации         |
| Нехватка QA                             | Средняя     | Среднее | Автотесты + code review          |
| Отток пользователей из-за багов чата    | Средняя     | Высокое | Нагрузочное тестирование чата    |

## 4. Оценка рисков безопасности (security risks)
| Риск                                   | Вероятность | Влияние | Митигация                          |
|----------------------------------------|-------------|---------|------------------------------------|
| Утечка персональных данных (ПДн)       | Средняя     | Критич. | Шифрование, контроль доступа, логи |
| Перехват трафика чата                  | Средняя     | Высокое | TLS + certificate pinning          |
| Массовый парсинг профилей (скаперы)    | Высокая     | Среднее | Rate limiting, капча, блокировка   |
| IDOR (доступ к чужим данным по id)     | Средняя     | Высокое | Проверка прав на каждый запрос     |
| Атака на цепочку поставок (зависимости)| Низкая      | Высокое | SCA, сканирование зависимостей    |

## 5. Бюджет на безопасность
- SAST/SCA инструменты: 50 000 руб/мес
- Пентест перед релизом: 300 000 руб (разово)
- SIEM/мониторинг: 30 000 руб/мес
```

### 📄 Пример 3. План разработки (этап Design/Development)

> Документ: `Dev_Plan_MeetWay_v1.0.md` – базовый план старта разработки

```markdown
# План разработки "MeetWay" – спринт 1 (первые 2 недели)

## Цель спринта: работающий каркас с авторизацией
- Настроить репозиторий (git, ветки, правила, .gitignore)
- Настроить CI (сборка + линтеры + SAST Semgrep)
- Каркас бэкенда (FastAPI + YDB), схема БД
- Каркас мобильного приложения (iOS SwiftUI / Android Kotlin)
- Экран регистрации/входа (UI)
- API: /auth/register, /auth/login, /auth/refresh

## Задачи (бэклог спринта)
1. [DEV-1] Инициализация репозиториев и CI – 1 день
2. [DEV-2] Схема БД: users, posts, chats, messages – 2 дня
3. [DEV-3] API регистрации (email+пароль, хэш bcrypt) – 2 дня
4. [DEV-4] API логина + JWT (access/refresh) – 2 дня
5. [DEV-5] Экран логина iOS – 2 дня
6. [DEV-6] Экран логина Android – 2 дня
7. [DEV-7] Интеграция мобилка <-> API – 2 дня

## Определение готовности (Definition of Done)
- Код в main + MR прошёл review
- SAST (Semgrep) без критических замечаний
- SCA (Trivy/Dependency-Check) без CVE Critical
- Юнит-тесты на авторизацию
- Документация API (OpenAPI) обновлена

## Критерии безопасности (security acceptance)
- Пароли не хранятся в открытом виде
- JWT подписан секретом из переменной окружения (не в коде!)
- Rate limiting на /auth/login (защита от брутфорса)
```

### 📄 Пример 4. Тестирование (этап Testing)

**Что это такое:** этап проверки, что система работает как задумано и не содержит уязвимостей.

**Виды тестирования:**
| Вид | Что проверяет | Кто делает | Когда |

| Юнит-тесты | Отдельные функции/классы | Разработчик | В каждом спринте |

| Интеграционные | Взаимодействие модулей | Разработчик/QA | В каждом спринте |

| E2E (UI) | Сценарии пользователя целиком | QA | Перед релизом |

| Нагрузочное | Поведение под нагрузкой | QA/DevOps | Перед релизом |

| SAST | Статический анализ кода | AppSec (авто) | В CI на каждый MR |

| SCA | Анализ зависимостей | AppSec (авто) | В CI на каждый MR |

| DAST | Динамический анализ запущенного приложения | AppSec | На staging |

| Пентест | Ручной поиск уязвимостей | Внешние/AppSec | Перед релизом |



**Пример плана тестирования (Test Plan):**
```markdown
# Тест-план релиза MeetWay 1.0
1. Функциональное тестирование (QA): 5 дней
   - Регистрация/логин/выход
   - Посты: CRUD, лайки, комментарии
   - Чаты: отправка, получение, push
   - Поиск: фильтры, пагинация
   
  
2. Безопасность (AppSec):
   - SAST: Semgrep (каждый MR) - 0 Critical/High
   - SCA: Trivy (каждая сборка) - 0 Critical CVE
   - DAST: OWASP ZAP на staging - Critical/High = 0
   - Ручной пентест: авторизация, IDOR, XSS, инъекции - 3 дня
3. Нагрузочное: 100k пользователей, чат - 2 дня
4. Критерий выхода: все Critical/High закрыты, Medium задокументированы
```

### 📄 Пример 5. Деплой/Внедрение (этап Deployment)

**Что это такое:** выкатка приложения в рабочее (продакшн) окружение. Для AppSec это не просто "запустили", а контролируемый процесс с проверками.

**Пример чек-листа деплоя (Deployment Checklist):**
```markdown
# Чек-лист деплоя MeetWay 1.0 в прод

## Перед деплоем (pre-deploy)
- [x] Все Critical/High уязвимости закрыты (SAST/SCA/DAST)
- [x] Пентест пройден, найденное устранено
- [x] Секреты не в коде (проверено gitleaks)
- [x] SBOM сгенерирован и сохранён
- [x] Бэкап БД настроен и протестирован

## Проверка конфигурации (configuration review)
- [x] Отключены debug-режимы (DEBUG=False)
- [x] Смена дефолтных паролей/ключей
- [x] TLS 1.2+ включён, старые протоколы запрещены
- [x] CORS настроен (только свои домены)
- [x] Заголовки безопасности: CSP, HSTS, X-Frame-Options
- [x] Rate limiting включён на /login, /register, /search

## Сканирование окружения (environment scan)
- [x] Сканирование Docker-образов (Trivy) - 0 Critical
- [x] Сканирование портов/сервисов (nmap) - открыты только нужные
- [x] Проверка конфигурации облака (Yandex Cloud): доступы, security groups
- [x] Обновления ОС/пакетов установлены

## После деплоя (post-deploy)
- [x] Мониторинг (логи, метрики, алерты) работает
- [x] SIEM/логирование инцидентов включено
- [x] Откат (rollback) проверен
- [x] Ответственный за инциденты назначен
```

**Пример команды сканирования образа перед деплоем:**
```bash
# сканируем Docker-образ на уязвимости
trivy image --severity CRITICAL,HIGH --exit-code 1 registry.example.com/meetway-api:1.0.0

# сканируем открытые порты
nmap -sV -p- api.meetway.example

# проверяем заголовки безопасности
curl -sI https://api.meetway.example | grep -iE "strict-transport-security|content-security-policy"
```
