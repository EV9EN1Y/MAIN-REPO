`Host header` - обязательный заголовок HTTP/1.1, который указывает доменное имя, которое хочет посетить клиент. Он необходим для маршрутизации запросов на правильный сервер, когда на одном IP-адресе размещено несколько сайтов (виртуальный хостинг) или когда трафик проходит через промежуточные системы (балансировщики нагрузки, CDN, reverse proxy)

## суть 

многие серверы неявно доверяют значению Host header, считая его безопасным, хотя на самом деле он полностью контролируется пользователем. Если значение не валидируется и не экранируется должным образом, это может привести к различным атакам

##  типы атак

---------

### Password reset poisoning

Когда приложение генерирует ссылку для сброса пароля, используя значение Host header для формирования абсолютного URL, атакующий может подменить этот заголовок

Пример:  
Запрос от атакующего:  
```http
GET /reset HTTP/1.1  
Host: attacker.com
```

Сервер генерирует ссылку:  
`https://attacker.com/reset?token=xyz`

Ссылка отправляется жертве
Жертва переходит на сайт атакующего, передавая свой валидный токен сброса

--------------
### Web cache poisoning

Если Host header отражается в ответе без экранирования и используется веб-кеш, можно отравить кеш

Пример c xss  
Запрос:  
```http
GET / HTTP/1.1  
Host: vulnerable.com"><script>alert(1)</script>
```

Ответ кешируется. Все последующие пользователи получают XSS-пейлоад

------------
### Routing-based SSRF

Промежуточные компоненты (балансировщики, reverse proxy) могут использовать Host header для определения, на какой бэкенд направить запрос. Если они неправильно настроены, можно заставить их перенаправить запрос на произвольный внутренний сервер

Пример:  
```http
GET / HTTP/1.1  
Host: 192.168.0.1
```
Запрос уходит во внутреннюю сеть ?????

-----------
### доступ к внутренним сайтам

па одном сервере могут быть размещены как публичные, так и внутренние сайты. Если подобрать или угадать имя внутреннего хоста ( intranet.example.com ), можно получить к нему доступ, просто подставив его в Host header

### классические серверные уязвимости

Значение Host header может передаваться в SQL-запросы, команды системы и другие чувствительные функции, что открывает возможность даже для SQL-инъекций, командных инъекций и других атак........

-----------

## Как тестить это дело все.....?

### подстановка произвольного Host header

Отправить запрос с измененным Host header на произвольное значение и посмотреть, достигает ли запрос целевого приложения

### обход валидации

Способы обойти проверки:

- Использовать порт для инъекции: vulnerable.com: payload
    
- Использовать поддомен, который проходит валидацию: payload.vulnerable.com
    
- Зарегистрировать домен, оканчивающийся на разрешенную последовательность
   

### создание неоднозначных запросов

Дублирование Host header:  
```http
GET / HTTP/1.1  
Host: vulnerable.com
Host: payload.com
```

Использование абсолютного URL:  
```http
GET https://vulnerable.com/ HTTP/1.1  
Host: payload.com
```
Добавление пробела в начало строки заголовка для создания обернутой строки

### использование заголовков для переопределения Host

```http
X-Forwarded-Host

X-Forwarded-Server  
X-HTTP-Host-Override  
Forwarded
```

Если приложение поддерживает такие заголовки, они могут иметь приоритет над Host header

## Методы защиты

Использовать относительные URL вместо абсолютных, когда это возможно.

Если требуются абсолютные URL, хранить домен в конфигурационном файле и использовать его вместо Host header.

Валидировать Host header по белому списку разрешенных доменов.

Отключить поддержку заголовков, которые могут переопределять Host (X-Forwarded-Host и другие).

Настроить балансировщики и reverse proxy так, чтобы они перенаправляли запросы только на разрешенные домены из белого списка.

Не размещать внутренние и публичные сайты на одном сервере.

## Ключевые выводы

Host header - удобная цель для атакующих, потому что разработчики часто забывают, что этот заголовок контролируется пользователем.

Многие уязвимости возникают не из-за небезопасного кода, а из-за неправильной конфигурации инфраструктурных компонентов.

Даже если приложение защищено от прямых атак через Host header, могут существовать другие заголовки, которые переопределяют его значение.

Для успешной эксплуатации часто требуется комбинация техник: обход валидации, создание неоднозначных запросов и использование особенностей разных компонентов системы
