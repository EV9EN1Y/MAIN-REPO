###### быстрая детекция - IDOR, вертикальное/горизонтальное повышение, обходы, path traversal

🟠 горизонтальное повышение (IDOR):
- найти параметры: id, user, account, invoice, file, doc, email
- подставить другой ID того же уровня (id=wiener → id=carlos, user=123 → user=124)
- если в ответе данные другого юзера - горизонтальный IDOR
- проверить массивы: ?id[]=123, ?id=123&id=124 - может вернуть несколько записей

🟠 вертикальное повышение:
- найти параметры: role, group, admin, isAdmin, privilege, access_level
- подставить admin=true, role=admin, group=administrator, privilege=10
- проверить скрытые админ-функции: /admin, /mod, /manage, /system
- попробовать выполнить админ-действие (удалить пользователя, создать аккаунт) из обычного аккаунта

🟠 обход через X-Original-URL / X-Rewrite-URL:
- отправить GET / HTTP/1.1 с заголовком X-Original-URL: /admin - если админка открылась - bypass
- то же с X-Rewrite-URL: /admin
- проверить, что URL-нормализация работает (X-Original-URL: /admin/../admin)

🟠 обход через IP-заголовки:
- добавить X-Forwarded-For: 127.0.0.1, X-Remote-IP: 127.0.0.1, X-Client-IP: 127.0.0.1
- если сайт доверяет этим заголовкам - можно обойти блокировки по IP
- проверить localhost, 127.0.0.1, 10.0.0.1, 192.168.0.1, 169.254.169.254

🟠 обход через редиректы и реферер:
- если доступ к админке по Referer: /admin - добавить Referer: https://site.com/admin
- проверить, можно ли перейти на /admin через открытый редирект: /redirect?url=/admin

🟠 path traversal / file include:
- найти параметры: file, path, page, template, include, doc, image, attachment
- передать ../../../etc/passwd - если вернулся файл - уязвимость
- передать file:///etc/passwd, http://localhost/admin - если работает - SSRF
- Windows: ../../../../boot.ini, ..\..\..\windows\win.ini
- пробовать URL-кодирование: %2e%2e%2f, %252e%252e%252f
- пробовать null byte: ../../../etc/passwd%00.jpg (если проверяется расширение)

🟠 обход фильтров path traversal:
- если фильтр удаляет ../, попробовать ....// (после удаления останется ../)
- если фильтр удаляет только один слэш: ..././..././..././etc/passwd
- использовать абсолютный путь: /etc/passwd (если базовая директория не проверяется)
- использовать Unicode: ..%c0%af (для старых систем)

🟠 проверка прямого доступа к ресурсам:
- после логаута попробовать открыть /my-account, /profile, /dashboard - если открылись - нет проверки сессии
- попробовать прямой переход к /admin/backup.sql, /config.php, /.env, /logs/error.log
- проверить S3-бакеты: bucket.s3.amazonaws.com/secret.txt - если открыто - IDOR

🟠 проверка доступа к функционалу:
- попробовать выполнить чувствительное действие (DELETE, POST) без CSRF-токена
- попробовать изменить метод: POST → GET, PUT → POST (если проверка прав привязана к методу)

🟢 альтернативные каналы:
- искать мобильные версии (m.example.com, /mobile), UAT/тестовые сайты, партнерские приложения
- проверить, используют ли они ту же учетную запись, но слабее защищены (HTTP вместо HTTPS, слабый сброс пароля)

🟢 транспорт credentials:
- перехватить логин, смену пароля, регистрацию - проверить, что все идут по HTTPS
- проверить куки сессии: есть ли флаг Secure; если нет - могут утечь по HTTP
- попробовать переключить протокол на HTTP (http://example.com/login) - если страница загрузилась и передала данные - уязвимо

🟢 дефолтные credentials:
- попробовать admin/admin, root/root, administrator/password, guest/guest
- проверить документацию к CMS/устройству (WordPress, Tomcat, Cisco) на предмет дефолтных паролей
- проверить комментарии в HTML/JS, бэкапы конфигов - могут быть hardcoded credentials

🟢 слабый lockout:
- отправить 3-5 неверных паролей, затем верный - если пустил - лимит не работает
- отправить 10+ неверных паролей, затем верный - если пустил - lockout отсутствует
- проверить, блокируется ли только IP или аккаунт (если IP - обход через X-Forwarded-For)
- проверить CAPTCHA: можно ли отправить запрос без решения, повторно использовать старый токен, или она только на фронте

🟢 обход аутентификации:
- попробовать прямой переход на /admin, /user/123, /dashboard минуя логин
- в параметрах искать authenticated=false → true, admin=0 → 1, role=user → admin
- SQL injection в форме логина: admin' --, ' OR 1=1--
- если сессии предсказуемы (id=1,2,3 или инкрементные куки) - попробовать угадать

🟢 remember password / cache:
- проверить, хранится ли пароль в localStorage, sessionStorage, cookie в открытом виде
- после логаута нажать "Назад" - если видна страница с данными - история кешируется
- проверить заголовки Cache-Control: no-cache, no-store, Pragma: no-cache на страницах с sensitive данными

🟢 слабая password policy:
- проверить минимальную длину (можно ли поставить 1 символ)
- проверить разрешенные символы (только цифры или только буквы)
- проверить, можно ли поставить пароль, совпадающий с логином, или "password", "123456"
- проверить историю паролей: можно ли сменить на тот же или на старый

🟢 слабые security questions:
- если вопросы типа "любимый цвет", "город рождения", "девичья фамилия матери" - ответы часто угадываются или находятся в соцсетях
- если пользователь сам придумывает вопрос - часто это "1+1", "мой пароль", "username"
- проверить lockout на security questions: можно ли перебирать ответы без блокировки

🟢 сброс/смена пароля:
- можно ли сбросить пароль другого юзера, зная только его логин
- приходит ли новый пароль в открытом виде на почту (значит хранится в открытом виде)
- запрашивается ли старый пароль при смене (если нет - session fixation)
- ссылка для сброса: одноразовая? угадывается? (reset_token=123)
- можно ли подменить параметр username=admin в запросе сброса

🟢 куки - проверить атрибуты:
- Secure: должен быть на всех куках с чувствительными данными (Set-Cookie: ...; Secure)
- HttpOnly: должен быть, чтобы защитить от XSS (Set-Cookie: ...; HttpOnly)
- Domain: проверить, не слишком ли широкий (.example.com вместо app.example.com)
- Path: проверить, не слишком ли широкий (/ вместо /app)
- Expires / Max-Age: persistent куки не должны жить вечно (max-age > 0)
- 
- SameSite: Strict или Lax - защита от CSRF; если None - обязательно Secure
- 
🟢 куки - проверить префиксы:
- ``__Host-: требует Secure, Path=/, без Domain`` - самый безопасный вариант
   ` __Secure-: требует Secure, может быть с Domain`
- если префиксы используются, но условия нарушены - кука будет отклонена браузером
- 
🟢 фиксация сессии:
- получить куку до логина (JSESSIONID=...), затем залогиниться
- если кука НЕ изменилась - уязвимо к session fixation
- попробовать восстановить старую куку после логаута - если пускает - проблема

🟢 логаут:
- после логаута нажать "Назад" - если страница с данными открылась - кеширование
- после логаута попробовать переиспользовать старую куку (через Repeater) - если пускает - сессия не убита на сервере
- проверить, есть ли кнопка логаута на всех страницах
- 
🟢 таймаут:
- залогиниться, ждать 15-30 мин, обновить страницу - если все еще залогинен - таймаут слишком большой или отсутствует
- проверить, зависит ли таймаут от клиентских данных (expires в куке) - если да, можно изменить
- 
🟢 хайджекинг (перехват сессии):
- проверить, передается ли кука по HTTP (без Secure) - можно перехватить в открытой сети
- проверить, используется ли HSTS (Strict-Transport-Security) — если нет, можно даунгрейдить до HTTP
- проверить, можно ли украсть куку через XSS (если нет HttpOnly)
- 
🟢 предсказуемость сессии:
- собрать 20+ сессионных кук для одного и того же пользователя

- если значения предсказуемы - можно подобрать чужую сессию

🟢 экспозиция сессии:
- проверить, не передается ли Session ID в GET-параметрах (url?sessionid=123)
- проверить, не виден ли Session ID в реферере, логах прокси, истории браузера
- 
🟢 session puzzling (перегрузка переменных):
- одна и та же переменная сессии используется для разных целей
- попробовать установить ее в одном контексте (например, восстановление пароля), затем использовать в другом (доступ к аккаунту)

<h2 id="^HTTPSplitting">🏆 ⭕️ HTTP Request/Response Splitting (CRLF Injection)</h2>

^HTTPSplitting

быстрая детекция - разделение ответа через CRLF, отравление кеша, XSS, дефакинг

HTTP Splitting (CRLF Injection) возникает, когда пользовательский ввод без валидации попадает в заголовки HTTP-ответа. Вставка `%0d%0a` (CRLF) позволяет злоумышленнику контролировать структуру ответа, разделяя его на два и более ответа

---

 🔴 БЫСТРАЯ ДЕТЕКЦИЯ =—= 3 ТЕСТА

1🟥 найти места, где пользовательский ввод попадает в заголовки ответа

- параметры редиректа: `?url=`, `?redirect=`, `?next=`, `?return_to=`

- `Referer` заголовок, который сервер куда-то пихает
   
- `User-Agent`, если он отражается в `Set-Cookie` или `Location`
   
- куки, которые сервер читает и вставляет в ответ
   

2🟥 ввставить простой тест на CRLF->

- передать `%0d%0aTest: test` в параметр
   
- смотреть в ответе (через Repeater или прокси с raw view) - появился ли новый заголовок `Test: test`
   
- если да - есть CRLF injection
   

3🟥 подтвердить сплиттинг

- передать 
 ```html
 %0d%0aContent-Length:%200%0d%0a%0d%0aHTTP/1.1%20200%20OK%0d%0aContent-Type:%20text/html%0d%0aContent-Length:%2020%0d%0a%0d%0a<script>alert(1)</script>
 ```
   
- если в ответе появилось два HTTP-ответа (смотри raw) - уязвимость подтверждена
   

---

 КЛЮЧЕВЫЕ ТЕСТЫ

🟥 1  Внедрение нового заголовка

`GET /redirect?url=/home%0d%0aSet-Cookie:%20hacked=1 HTTP/1.1`

Если в ответе появилась кука `hacked=1` - CRLF есть

🟥 2 Разделение ответа (Splitting)

```http
GET /redirect?url=/home%0d%0aContent-Length:%200%0d%0a%0d%0aHTTP/1.1%20200%20OK%0d%0aContent-Type:%20text/html%0d%0aContent-Length:%2020%0d%0a%0d%0a<script>alert(1)</script> HTTP/1.1
```

В raw-ответе должно быть два блока:

- первый - оригинальный редирект
- второй - полностью подконтрольный ответ с XSS


🟥 3 Отравление кеша (если есть кеширование)

```http
GET /redirect?url=/home%0d%0aContent-Length:%200%0d%0a%0d%0aHTTP/1.1%20200%20OK%0d%0aContent-Type:%20text/html%0d%0aContent-Length:%2050%0d%0a%0d%0a<h1>Hacked%20by%20AppSec</h1> HTTP/1.1
```
После этого запросить `/redirect?url=/home` обычным пользователем - если вернулся взломанный контент - кеш отравлен

🟥 **Тест 4: Обход через разные кодировки**  
Если `%0d%0a` блокируется:

- `%0a` (только LF) - иногда работает
   
- `%0d` (только CR)
   
- `%250d%250a` (двойное URL-кодирование)
   
- `\r\n` в теле запроса (если параметр передается в POST)
   
- `\n` (unix-style)
   
- `%00%0a` (null byte + LF)
   

🟥 5  Внедрение в Referer
eсли сервер логирует Referer и отражает его в заголовках:

```http
GET / HTTP/1.1
Host: example.com
Referer: http://evil.com/%0d%0aSet-Cookie:%20hacked=1
```

###### быстрая детекция --> CRLF Injection в заголовках

🟥  все места, где ввод попадает в заголовки
- параметры редиректа (Location)
- куки Set-Cookie)
- referer (если отражается)
- user-agent (если отражается)
- любые параметры, которые подставляются в Location, Refresh, Content-Disposition


🟥 **Простейший тест:**  
Передать `%0d%0aTest: injected` в каждый потенциальный параметр. Если в ответе появился заголовок `Test: injected` - уязвимость!!

🟥 проверить, есть ли защита:
- экранируется ли `%0d%0a`
- экранируется ли `\r\n`
- обрезаются ли символы
- есть ли WAF, который режет CRLF

🟥 обход защиты (если есть):
- `%250d%250a` (двойное URL-кодирование)
- `%0a` (только LF, если сервер нормализует)
- `\n` в теле POST-запроса
- `%00%0a` (null byte)
- если WAF режет `%0d%0a` целиком, попробовать `%0dxxx%0a`

🟥 проверить влияние:
- можно ли добавить новый заголовок
- можно ли завершить текущий ответ и начать новый
- можно ли отравить кеш (повторить запрос дважды и сравнить ответы)
- можно ли установить свою куку
- можно ли изменить политику безопасности (CSP, CORS)

<h2 id="^lfi-rfi">🏆 LFI / RFI (Local & Remote File Inclusion (CRLF Injection)</h2>

^lfi-rfi
> Local File Inclusion (LFI) - когда через параметр можно подключить локальный файл сервера (часто с обходом директорий).  
   Remote File Inclusion (RFI) - когда можно подключить файл с внешнего сервера (часто приводит к RCE).

### 🔴 LFI - БАЗОВАЯ ДЕТЕКЦИЯ

1🟣 - нашел параметры `file`, `page`, `path`, `template`, `include`, `doc`, `document` - передал `../../../etc/passwd` — если вернулся файл с пользователями - есть LFI

2🟣 - если на `../../../etc/passwd` ответа нет, но ошибка изменилась - пробовать Windows пути: `..\..\..\windows\win.ini`

3🟣 - если дописывается расширение `.php` (например, `include($_GET['file'] . ".php")`) - пробовать null byte: `../../../etc/passwd%00` (работает на старых PHP < 5.3.4)

4🟣 - если null byte не работает - пробовать path truncation: накидать 4096+ символов, чтобы расширение уехало за лимит  
`../../../etc/passwd/./././... (1000+ раз)`

5🟣 - пробовать обходы через URL-кодирование: `..%252f..%252fetc%252fpasswd`, `..%c0%af..%c0%af` (двойное кодирование, Unicode)

АПГРЕЙД ДО RCE

6🟣 - чтение исходного кода (php://filter - > передал  
`php://filter/convert.base64-encode/resource=index.php`  
вернулась base64-строка, декодировал - получил исходник. так можно читать любые php-файлы

3. загрузил как аватар (сервер сохранил в `/uploads/avatar.jpg`)
4. передал в уязвимый параметр: `zip://./uploads/avatar.jpg%23shell`  
    - выполнилась команда `id`


8🟣 - RCE через data:// (если `allow_url_include=On`) - передал  
`data://text/plain;base64,PD9waHAgc3lzdGVtKCdpZCcpOyA/Pg==`  
- выполнилась команда `id` без загрузки файлов

9🟣 - RCE через expect:// (если модуль установлен) - передал  
`expect://id`  
- вернулся результат команды
