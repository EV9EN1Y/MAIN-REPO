
###  Тестирование Hop-by-Hop инъекции

Это продвинутая атака, которая использует заголовок `Connection` для удаления других заголовков

**Как это работает:**

1. Я отправляю запрос, добавляя в `Connection` название внутреннего заголовка (например, `X-Forwarded-For`):
   
```q
   GET /admin HTTP/1.1
   Host: example.com
   X-Forwarded-For: 203.0.113.10
   Connection: close, X-Forwarded-For
```
   
2. Прокси-сервер (если он есть и неправильно настроен) должен удалить заголовок `X-Forwarded-For` из запроса перед отправкой на бэкенд
 
3. Бэкенд не получает IP-адрес и может обработать запрос без проверки


**Что я проверяю:**

- Пытаюсь подменить `X-Forwarded-For` на свой IP и удалить его через `Connection`
   
- Пытаюсь удалить `X-Authenticated-User` или другие заголовки аутентификации
   
- Пытаюсь удалить `X-Forwarded-Proto` (схема протокола)


--------

### Боевой пример: Уязвимость в Fastify (CVE-2026-33805)

В библиотеках `@fastify/reply-from` и `@fastify/http-proxy` была реальная дыра 
Сначала прокси добавляет свой внутренний заголовок, например, `X-Forwarded-By`, а потом обрабатывает `Connection` от клиента и удаляет ВСЁ, что там перечислено, включая только что добавленный прокси-заголовок 

**PoC (упрощенно):**
# Базовый запрос через прокси — x-forwarded-by есть
```c
curl http://proxy.local/proxy/api/echo

# Ответ: { "x-forwarded-by": "proxy-server" }

# Атакующий запрос — добавляем Connection и заставляем прокси удалить свой же заголовок

curl -H "Connection: close, x-forwarded-by" http://proxy.local/proxy/api/echo

# Ответ: { }  — x-forwarded-by удален! [citation:9]
```

### Что это дает атакующему

Если бэкенд доверяет заголовкам, которые должен добавлять только прокси (например, `X-Authenticated-User`, `X-Forwarded-For`, `X-Admin-Role`), то атакующий может убрать их, чтобы обойти контроль доступа 

**Сценарий обхода IP-фильтрации:**

1. Админ-панель доступна только с IP 10.0.0.1
   
2. Прокси добавляет реальный IP клиента в заголовок `X-Forwarded-For`
   
3. Бэкенд проверяет этот заголовок
   
4. Атакующий добавляет `Connection: close, X-Forwarded-For`, и прокси удаляет этот заголовок
   
5. Бэкенд не видит `X-Forwarded-For` и может пропустить запрос 

### Пример 1: Обход IP-фильтрации

**Ситуация:** Админ-панель доступна только с IP `10.0.0.1`. Прокси доверяет заголовку `X-Forwarded-For`.

```c
Обычный запрос (админ, если IP правильный):


GET /admin HTTP/1.1
Host: example.com
X-Forwarded-For: 10.0.0.1

--------**Атакующий запрос:**-------------


GET /admin HTTP/1.1
Host: example.com
X-Forwarded-For: 203.0.113.10
Connection: close, X-Forwarded-For
```

**Что происходит:**

1. Прокси читает `Connection: close, X-Forwarded-For`
    
2. Прокси удаляет заголовок `X-Forwarded-For` из запроса
    
3. Бэкенд не видит `X-Forwarded-For` и не может проверить IP
    
4. Если бэкенд по умолчанию разрешает доступ без IP-проверки - атака успешна

-----------

   

###  Как защищаться

- Прокси должен обрабатывать `Connection` **до** добавления своих заголовков, а не после
   
- Не доверять слепо заголовкам от прокси - проверять их подлинность 
   
- Отключить эту оптимизацию или использовать более строгую логику
   
- Бэкенд должен корректно обрабатывать случаи, когда важные заголовки отсутствуют
