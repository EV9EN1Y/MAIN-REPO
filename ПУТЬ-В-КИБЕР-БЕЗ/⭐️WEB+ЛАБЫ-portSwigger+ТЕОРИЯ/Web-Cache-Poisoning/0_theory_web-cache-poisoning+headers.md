## что такое web-cache-poisoning

`это когда я заставляю кеш сохранить в себя вредоносный ответ, который потом получают другие пользователи`

------
###### web cache poisoning via ambiguous requests

> это атака, при которой злоумышленник заставляет кеш сохранить вредоносный ответ, используя неоднозначные запросы, где разные компоненты системы (кеш и бэкенд) по-разному интерпретируют один и тот же запрос

суть:
>- Кеш фронта-> использует один метод определения ключа кеша (например, смотрит на Host header)
>- Бэкенд -> использует другой метод (например, смотрит на X-Forwarded-Host)
>- Атакующий отправляет запрос, который для кеша выглядит как запрос к валидному домену, а бэкенд обрабатывает его с вредоносным значением

короче, это очень похоже на HTTP_Request _Smuggling, когда клиент и бек по разному считывают заголовки  длинны запроса и чанки, только в случае с `web cache poisoning `  речь идет про заголовки хоста!!!
 
Пример:  
```http
GET / HTTP/1.1  
Host: vulnerable.com  -> фронт использует это
X-Forwarded-Host: attacker.com -> а бек использует это и, возможно, хранит в кеше общем, и отдает остальным всез запросам, пока живет кеш, то есть например 30 сек, и все подключениия за эти 30 сек - получают attacker.com
```

Кеш сохраняет ответ для `vulnerable.com`, но бэкенд генерирует ответ на основе `attacker.com`, включая в него вредоносный код

В результате все пользователи, которые получают страницу из кеша, получают скомпрометированный ответ


---------

кеш сидит между пользователем и сервером и сохраняет копии ответов, чтобы не нагружать сервер повторными запросами

кеш определяет, сохранять ответ или нет, по так называемому кеш-ключу

кеш-ключ обычно состоит из метода, пути и host заголовка

все остальные части запроса, такие как дополнительные заголовки или куки, называются `неключевыми`

если я могу повлиять на ответ через неключевой ввод, и этот ответ закешируется, то я отравил кеш

`заголовок Cache-Control отвечает за кеш`

---------
**Ключ кэша** — это набор элементов запроса, по которым кэш-сервер (или CDN) определяет, **нужно ли отдавать сохраненную копию или генерировать новый ответ**.

#### перед тем, как перейти к примерам, доп инфа по заголовкам
одни используются для атаки, другие помогают исследовать кеш, третьи выдаются самим кешем в ответе

с пояснением, для чего каждый нужен

##### заголовки, которые атакующий использует для отравления

#### x-forwarded-host  
предназначен для того, чтобы прокси или балансировщик передавал бэкенду оригинальное имя хоста, который запросил пользователь  
используется в атаках, когда кеш не включает его в ключ, а бэкенд использует его для генерации ссылок  
значение может быть любым доменом, 
ip-адресом, или xss-пейлоадом типа` a"><script>alert(1)</script>`

#### x-forwarded-scheme  
передает протокол, который использовал клиент (http или https)  
в атаках используется для превращения редиректа в перенаправление на другой домен в паре с x-forwarded-host  
значения - http, https, или невалидное значение типа nothttps, которое заставляет сервер генерировать редирект

#### x-forwarded-server  
аналогичен x-forwarded-host, но иногда имеет приоритет при маршрутизации  
используется в route poisoning, когда приложение хостится на платформе вроде hubspot, которая определяет клиента по этому заголовку  
значение - домен клиента на платформе

#### x-host  
нестандартный заголовок, который некоторые приложения используют для переопределения host  
найден в атаках на [unity3d.com] и других сайтах  
значение - домен атакующего с xss-пейлоадом

#### x-original-url  
заголовок, который переопределяет путь запроса  
изначально появился в zend framework, потом перекочевал в symfony и drupal  
используется для обхода waf, подмены пути в кеше, и вложенного отравления кеша  
значение - любой путь на сервере, включая /admin

#### x-rewrite-url  
аналог x-original-url с тем же назначением  
используется в некоторых конфигурациях nginx и apache  
значение - путь для перезаписи

#### x-http-method-override  
позволяет переопределить http-метод, отправляя get с телом, который воспринимается как post  
используется в fat get-атаках, когда кеш использует метод из строки запроса, а бэкенд - из этого заголовка  
значение - `post`, `put`, `delete`

#### forwarded  
стандартизированная замена для x-forwarded-* заголовков  
содержит параметры for, by, host, proto  
используется в атаках, если приложение поддерживает этот заголовок  
пример - forwarded: host=[attacker.com]; proto=http

#### origin  
заголовок, который браузер добавляет при кросс-доменных запросах  
в некоторых cdn включается в кеш-ключ по умолчанию  
используется как кеш-бастер, если добавить в него уникальное значение  
значение - любой домен

#### accept-encoding  
сообщает серверу, какие методы сжатия поддерживает браузер  
включается в кеш-ключ на некоторых cdn  
используется как кеш-бастер, если добавить в него уникальную строку  
значение - gzip, deflate, br, плюс произвольная строка через запятую

#### cookie  
заголовок с данными сессии  
обычно не входит в кеш-ключ, но иногда включается через vary  
используется в атаках, когда через cookie передается язык или регион, и это влияет на ответ  
также используется как кеш-бастер

---

##### заголовки, которые помогают исследовать кеш

#### pragma: akamai-x-get-cache-key  
отладочный заголовок для akamai cdn  
заставляет сервер вернуть в ответе заголовки x-cache-key и x-true-cache-key, показывающие, как формируется кеш-ключ  
значение - `akamai-x-get-cache-key`, `akamai-x-get-true-cache-key` и другие аналогичные

#### x-cache-key  
возвращается akamai cdn при отправке отладочных pragma  
показывает, какой кеш-ключ используется  
значение - строка с путем, параметрами и другими компонентами ключа

#### x-true-cache-key  
аналогичен x-cache-key, но показывает более чистую версию без некоторых временных параметров  
значение - строка кеш-ключа

---

##### заголовки, которые кеш добавляет в ответ

#### cache-status  
показывает, был ли ответ взят из кеша или пришел с сервера  
встречается в современных cdn  
значения - `hit, miss, bypass, dynamic`

#### cf-cache-status  
заголовок cloudflare cdn  
значения - `hit, miss, expired, updating, bypass, dynamic`

#### x-cache  
используется в fastly и varnish  
значения - `hit, miss, hit from cloudfront и др`

#### x-cache-hits  
показывает, сколько раз этот ответ был выдан из кеша  
значение - число

#### via  
показывает, через какие прокси и кеши прошел ответ  
в varnish указывает версию и идентификатор кеша  
значение - 1.1 varnish-v4

#### age  
показывает, сколько секунд ответ уже находится в кеше  
используется для расчета момента, когда кеш истечет, если известно max-age  
значение - число секунд

#### cache-control  
управляет поведением кеша  
важные директивы - `public` (можно кешировать), `private` (нельзя кешировать в общем кеше), `max-age=n` (сколько секунд живет), `no-cache` (формально запрещает кеш, но cdn часто игнорируют)

#### vary  
указывает, какие дополнительные заголовки должны входить в кеш-ключ  
значение - список заголовков, например `user-agent, accept-encoding, origin`

---

##### заголовки, используемые в атаках на connection state

#### connection  
управляет поведением tcp-соединения  
значение keep-alive говорит серверу не закрывать соединение после ответа  
в атаках на connection state это ключевой заголовок - через одно соединение отправляется сначала легитимный запрос, а потом вредоносный с подмененным host

#####  🔴 пример 1 `базовое отравление через отражеине x-forwarded-host`

представим сайт, который вставляет значение заголовка 
`x-forwarded-host` в open graph мета-тег

обычный запрос выглядит так
```http
get /en http/1.1  
host: www.redhat.com  
x-forwarded-host: innocent.com
```
в ответе будет  
```html
<meta property="og:image" content="https://innocent.com/cms/social.png" />
```

я меняю `x-forwarded-host `на свой вредоносный пейлоад
```http
get /en?dontpoisoneveryone=1 http/1.1  
host: www.redhat.com
x-forwarded-host: a."><script>alert(1)</script>
```
сервер генерирует ответ (с html) с незаэкранированным скриптом
```html
<meta property="og:image" content="https://a."><script>alert(1)</script>"/cms/social.png" />
```

если этот ответ закешируется, то любой пользователь, который зайдет на /en, получит этот скрипт в своем браузере

в этом примере кеш оказался включен на `cdn`, и ответ действительно закешировался, хотя в заголовках было `cache-control: no-cache`

👉 это важно - никогда не верь заголовкам кеша, всегда проверяй на практике

>>	CDN - это сеть доставки контента, или content delivery network
	это распределенная сеть серверов, которые хранят копии статического и динамического контента сайта и отдают его пользователям с ближайшего к ним сервера
		когда ты заходишь на сайт, ты обычно подключаешься не к его оригинальному серверу, а к одному из cdn-серверов, который находится ближе всего к тебе
	это ускоряет загрузку страниц и снижает нагрузку на основной сервер

в контексте веб-кеш-поэзинга cdn - это огромный распределенный кеш, который можно отравить


==============================================

на `catalog.data.gov` нашли, что` x-forwarded-host` отражается в атрибуте` data-site-root`
 
```html
<body data-site-root="https://canary/">
```

и отравил кеш, чтобы сайт загружал этот файл у меня

#####  🔴 пример 7:` local route poisoning через x-original-url`

в drupal и многих php-фреймворках оказалась поддержка заголовков x-original-url и x-rewrite-url, которые переопределяют путь запроса

это позволяет обойти waf  
```http
get /admin http/1.1  
host: unity.com
```
ответ 403 forbidden
но
запрос:
```http
get /anything http/1.1  
host: unity.com
x-original-url: /admin
```
ответ 200 ok

для кеша это еще интереснее - кеш-ключ строится на основе пути, который видит кеш, а бэкенд отдает контент из другого пути

если отправить запрос с `x-original-url`, можно закешировать страницу с одним путем, а отдавать её пользователям, которые запрашивают другой путь

#####  🔴 пример 8: `вложенное отравление кеша (nested cache poisoning)`

в `drupal` есть внутренний кеш, который учитывает `x-original-url`, но при этом включает в кеш-ключ строку запроса из этого заголовка

плюс в `drupal` есть открытый редирект через параметр destination

цепочка атаки выглядит так

сначала я отравляю внутренний кеш, заменяя `/redir` на свой редирект

```http
get /?destination=https://evil.net\@store.unity.com/ http/1.1  
host: store.unity.com
x-original-url: /redir
```

потом я отравляю внешний кеш, заменяя /download?v=1 на /redir
```http
get /download?v=1 http/1.1  
host: store.unity.com
x-original-url: /redir
```

в итоге пользователь, который нажимает "скачать", получает редирект на мой сайт

эта техника позволяет превратить любую страницу в редирект, подменить json, вставить xss в скрипты, подменить rss-ленты

#####  🔴 пример 9: `unkeyed query string`


если кеш исключает строку запроса из кеш-ключа, то все параметры игнорируются при решении, отдавать ли кешированный ответ

но это не значит, что они игнорируются бэкендом

> обнаружить такую ситуацию сложно, потому что даже при добавлении любых параметров ответ не меняется - всегда приходит кеш

нужно добавлять кеш-бастеры в заголовки, которые входят в кеш-ключ, например в accept, cookie, origin

или использовать разницу в нормализации пути между кешем и бэкендом

например, для apache запросы к // и / могут кешироваться отдельно, но на бэкенде вести на одну страницу

когда такая уязвимость найдена, она становится очень опасной

обычно xss в параметрах требует, чтобы жертва перешла по специальной ссылке

но если строка запроса неключевая, я могу отравить кеш один раз, и все пользователи, которые заходят на обычный url, будут получать xss

#####  🔴 пример 10: `cache parameter cloaking`

иногда кеш исключает только отдельные параметры, например utm_content

но можно использовать разницу в парсинге url между кешем и бэкендом

кеш считает, что параметры разделяются только амперсандом, и видит два параметра

а бэкенд считает, что параметры могут разделяться и точкой с запятой, как в ruby on rails

я отправляю запрос

```http
get /?keyed_param=abc&excluded_param=123;keyed_param=bad-stuff-here
```

кеш видит `keyed_param=abc и excluded_param=123;keyed_param=bad-stuff-here`, убирает `excluded_param`, и в кеш-ключ попадает только `keyed_param=abc`

а бэкенд на rails видит три параметра, и из-за того, что последний keyed_param имеет приоритет, подставляет мой вредоносный параметр

таким образом я могу переопределить любой параметр, который входит в кеш-ключ, не меняя сам кеш-ключ

#####  🔴 пример 11:` fat get`

некоторые кеши не включают метод запроса в кеш-ключ, а некоторые фреймворки принимают тело у get-запросов

если я отправлю get с телом, кеш может сохранить ответ, а бэкенд возьмет параметры из тела

на github нашли такую уязвимость-
```http
get /contact/report-abuse?report=albinowax http/1.1  
host: github.com  
content-type: application/x-www-form-urlencoded  
content-length: 22

report=innocent-victim
```


в кеш-ключ попал параметр `report=albinowax`, а бэкенд обработал `report=innocent-victim`

в результате кеш отдавал ответ, который отправлял жалобу не на меня, а на другого пользователя

github заплатил 10000 долларов за эту уязвимость

#####  🔴 пример 12: `нормализация кеш-ключа`

иногда кеш нормализует ввод, например, декодирует url

на [download.mozilla.org], где обновляется firefox, кеш-ключ строится так, что url-декодируется

я отправляю запрос на обновление с закодированным вопросительным знаком

```http
get /%3fproduct=firefox-73.0.1-complete&os=osx&lang=en-gb&force=1 http/1.1  
host: download.mozilla.org
```

бэкенд не понимает такой запрос и отдает редирект на главную страницу [mozilla.org]

но кеш-ключ для этого запроса совпадает с кеш-ключом обычного запроса на обновление

в результате все пользователи firefox перестали получать обновления и перенаправлялись на главную страницу

#####  🔴 пример 13: `cache key injection`

иногда кеш склеивает компоненты кеш-ключа через разделители, не экранируя их

если я могу вставить свой разделитель, то могу заставить кеш сохранить ответ для одного ключа, а отдавать по другому

например, кеш-ключ формируется как `/path?param=123__origin='значение'`

я отправляю запрос с origin: `'-alert(1)-'__`

кеш сохраняет ответ с `x-cache-key: /path?param=123__origin='-alert(1)-'__`

потом я отправляю запрос с url, где параметр выглядит как `123__origin='-alert(1)-'`

кеш находит этот ключ и отдает ответ со скриптом, хотя в исходном запросе не было xss

это превращает уязвимость в `keyed`-заголовке в полноценный xss

---
==============================================



#####  🔴 пример 14: `internal cache poisoning без кеш-ключа`

в некоторых фреймворках кеш работает на уровне фрагментов страницы

каждый фрагмент кешируется отдельно, и у него нет ключа, он просто используется везде, где встречается

если я отравлю такой фрагмент, он будет отображаться на всех страницах, для всех пользователей

это особенно опасно, потому что невозможно добавить кеш-бастер или как-то изолировать себя при тестировании

при тестировании таких кешей нужно быть предельно осторожным и использовать только свой домен в пейлоаде, чтобы случайно не навредить

--------
==============================================

###  🟢 как защититься

самое надежное - отключить кеш там, где он не нужен

если кеш нужен, ограничить его только статическими ответами

не брать ввод из заголовков и кук для генерации динамического контента

отключить все неиспользуемые заголовки, особенно те, которые могут переопределять host, путь или схему

использовать `param miner`, чтобы найти все неключевые вводы на своем сайте

если заголовок нельзя отключить, добавить его в кеш-ключ с помощью vary или конфигурации cdn

не принимать fat get-запросы

не игнорировать клиентские уязвимости, даже если кажется, что их нельзя эксплуатировать - кеш может сделать их эксплуатируемыми
