
**JWT (JSON Web Token)** — это, по сути, цифровая JSON записка, которую сервер выдаёт клиенту. В ней лежат данные о пользователе (claims): имя, роль, айдишник, срок годности + секрет токен
Главная фишка: всё это хранится у клиента, а сервер просто проверяет подпись, и когда нужно выдает новый токен, рефреш токена...

#### работа JWT на примере моего приложения MeetWay
Короч, отправляем серверу запрос на получение jwt токена и сессионного токена, отправляя ему наш id (и необходимые даные) - далее сервер обрабатывает это все согласно свеой логике и выдает JWT /или не выдает новый JWT . и в этот jwt токен нужен потом для работы прилоэжения, например, в моем приложении MEETWAY (соц сеть) - там каждое сетевое действие требует в своем сопровождении не просроченный JWT (для доступа к системе аунтетификации, для просмотра чужих профилей, для отправки смс, для выполнения поиска юзеров по бд внутри приложения, добавление поста в ленту или коммента, или при изменении своих данных в аккаунте, также для отправки реакций итд, в общем - почти для всех дейсквий - сервер требует этот самый JWT : и каждые n минут - токен устаревает - и приложение запрашивает новый токен, сервер проверяет запрос - и далее от условий - выдает или не выдает новый JWT)

Это удобно для распределённых систем, где много бэкенд-серверов
Им не надо лазить в общую базу сессий — вся инфа уже в токене.

#### Header (Заголовок) — base64url от JSON. Там обычно:

**`alg` (Algorithm)** — это обязательный параметр в заголовке (header) JWT, который указывает, **каким алгоритмом подписана эта хрень**

- **HS256, HS384, HS512** — симметричные (H) (один секрет для подписи и проверки)
    
- **RS256, RS384, RS512** — асимметричные (R) (приватный ключ для подписи, публичный для проверки)
    
- **ES256, ES384, ES512** — на эллиптических (E) кривых (тоже асимметричные)
    
- **PS256, PS384, PS512** — RSA с PSS-набивкой  (PS) (более безопасная версия RSA)

## JKU (JWK Set URL)

**JKU** — это URL, откуда сервер должен скачать набор ключей (JWKS).



Сервер идет по этому URL, получает JSON с ключами и использует их для проверки

**Как ломают**:

```js

2. Меняешь в токене `jku` на URL своего сервера
    
3. Сервер скачивает твой ключ и валидирует подпись
```

**Важно**: Иногда серверы проверяют, что URL ведет на доверенный домен

####  KID (Key ID)

**KID** (Key ID) — это строка-идентификатор, которая говорит серверу: "Эй, для проверки этого токена используй вот такой ключ из хранилища"

```json
{
  "alg": "HS256",
  "kid": "my-hmac-key-2026"
}
```

Сервер ищет в своей базе ключ с таким ID (в файловой системе, в БД, в переменных окружения)

**Твоя задача** — сделать так, чтобы сервер достал **контролируемый тобой ключ**, которым ты заранее подписал свой левый токен


##  🔴 как ломают JWT 

Ты можешь изменять payload как хочешь, но без валидной подписи сервер тебя пошлёт на другие три буквы
Поэтому все атаки сводятся к одному из трёх:

1. Заставить ==сервер не проверять подпись== вообще
   
2. ==Узнать/подобрать секретный ключ== и подписать свой токен
   
3. Подменить ключ проверки своим

⭐️🔥🟢-------кратко по атаки--------⭐️🔥🟢 


## способ 1: Отсутствие проверки подписи

Разработчик перепутал `decode()` и `verify()`. 
Подпись не проверяется — меняй payload как хочешь, сервер не поверит

## способ 2: Алгоритм `none`

Меняешь `alg` на `none`, удаляешь подпись. Сервер думает "нет подписи — и ладно". Обход через `None`, `NONE`, `none`  (с пробелом)

## способ 3: Брутфорс слабого ключа (HS256)

Если ключ типа `secret` или `password`, его можно подобрать локально через hashcat (mode 16500) . Потом подписываешь любой токен, сомнительно конечно.. но теория такая есть..

## способ 4: Algorithm confusion (RS256 → HS256)

Меняешь `alg` с RS256 на HS256. Сервер думает, что публичный ключ — это HMAC-секрет
Подписываешь токен публичным ключом — сервер его принимает

## способ 5: Инъекция через `jwk`

Вставляешь в заголовок `jwk` со своим публичным ключом, подписываешь токен своим приватным 
Сервер доверяет ключу из токена — подпись проходит

## способ 6: Инъекция через `jku`

Указываешь в `jku` URL своего сервера с JWK-набором. Сервер скачивает твой ключ и использует для проверки Обход через открытые редиректы

## способ 7: Инъекция через `kid`

Подделываешь `kid`, чтобы сервер использовал не тот ключ:

- Path traversal: `"kid": "../../../../dev/null"`
    
- SQLi: `"kid": "key' UNION SELECT 'mykey'"`
    
- Угадывание переменных окружения

# 🟢 ПОДРОБНЕЕ -  АТАКИ JWT 

#### СПОСОБ  Принимаем произвольные подписи (Accepting arbitrary signatures)

самая тупая ошибка разработчика: использовать метод `decode()` вместо `verify()`

например в Node.js библиотеке `jsonwebtoken` есть два метода:

- `verify()` — проверяет подпись
   
- `decode()` — просто декодирует base64
   

если разработчик поставил `decode()`, то подпись вообще не проверяется. Ты можешь вставить любой говнокод в payload, и сервер поверит
(но это все всплывет (скорее всего) сразу же на этапе первичного тестирование самим же програмистом при настройске работы этой системы как раз...)

пример атаки:
был токен:

```json
{"username": "carlos", "isAdmin": false}
```

ты меняешь на:

```json
{"username": "administrator", "isAdmin": true}
```

вуаля — ты админ


В спецификации есть алгоритм `none` — это значит "без подписи". Если разработчик не отключил эту возможность, можно просто:

1. Изменить `"alg": "HS256"` на `"alg": "none"`
    
2. Удалить подпись (или оставить пустой)
    
3. Изменить payload как душе угодно (например, `"role": "user"` на `"role": "admin"`)
    

Некоторые библиотеки пропускают такие токены. А если фильтрация есть, её можно обойти написав `"alg": "None"`, `"alg": "NONE"` или `"alg": "none "` (с пробелом





---------


Атакующий делает следующий трюк:

1. Меняет заголовок с `"alg": "RS256"` на `"alg": "HS256"` (симметричный)
    
2. Теперь сервер думает, что должен проверить подпись **тем же ключом, который используется для подписи**
    
3. Атакующий подписывает токен, используя **публичный ключ сервера** как HMAC-секрет
    
4. Сервер проверяет подпись своим же публичным ключом (который у него есть) и думает, что всё ОК

#### СПОСОБ   Алгоритм none (Accepting tokens with no signature)

В заголовке `alg` может стоять значение `none`. Это значит "без подписи"
По спецификации, если `alg: none`, то часть с подписью должна быть пустой (просто точка . в конце)

alg - это **ахиллесова пята** всей JWT-безопасности

**`alg` (Algorithm)** — это обязательный параметр в заголовке (header) JWT, который указывает, **каким алгоритмом подписана эта хрень**

разработчики обычно блокируют такие токены. Но фильтрацию можно обойти:

обфускация

- `Alg: NoNe` (смешанный регистр)
   
- `alg: None` с пробелами
   
- нестандартные кодировки
   

если обошёл — подпись не проверяется, payload меняешь как хочешь

#### СПОСОБ  Инъекции в заголовки JWT (JWT header parameter injections)

самый интересный раздел  - в  заголовке JWT могут быть параметры, которые влияют на выбор ключа для проверки подписи

основные параметры:

- `jwk` (JSON Web Key) — встраивает публичный ключ прямо в токен
    
- `jku` (JSON Web Key Set URL) — URL, откуда сервер должен скачать набор ключей
    
- `kid` (Key ID) — идентификатор ключа, если их несколько
    

атакующий может использовать эти параметры, чтобы подсунуть свой собственный ключ

#####  атака через jwk (Injecting self-signed JWTs via the jwk parameter)

если сервер доверяет ключу, который приходит в `jwk`, то можно:

1. сгенерировать свою пару RSA-ключей
    
2. подписать токен своим приватным ключом
    
3. вставить публичный ключ в параметр `jwk` заголовка
    

сервер увидит ключ в токене и использует его для проверки подписи -
а подпись-то сделана твоим ключом — значит, всё сойдётся

в Burp Suite для этого есть расширение ==JWT Editor:==

- Заходим в JWT Editor Keys
    
- Создаём новую RSA-пару
    
- В Repeater на вкладке JSON Web Token правим payload
    
- Жмём "Sign" и выбираешь "Don't modify header" (чтобы оставить свой `jwk`)
    

#####  Атака через jku (Injecting self-signed JWTs via the jku parameter)

то же самое, но публичный ключ не встраивается прямо в токен, а загружается по URL из `jku`. 
Ты можешь:

1. хостить на своём сервере JSON с JWK-набором, содержащим твой публичный ключ
    
2. вставить URL своего сервера в `jku`
   
3. сервер скачает твой ключ и использует для провер
   

важно: URL должен быть валидным и доступным 
иногда серверы проверяют, что URL ведёт на доверенный домен, но это часто обходится через открытые редиректы

#####  атака через kid (Injecting self-signed JWTs via the kid parameter)

`kid` — это идентификатор ключа. Сервер ищет ключ с таким ID в своей базе. Ты можешь:

- Если сервер хранит ключи в файловой системе, попробуй path traversal: `"kid": "../../../../dev/null"`
    
- Если сервер использует SQL, попробуй SQLi: `"kid": "key' UNION SELECT 'mykey'"`
    
- Если ключи берутся из окружения, можно попробовать угадать имя переменной
    

иногда `kid` вообще игнорируется, и сервер берёт любой ключ, лишь бы подпись сошлась




#### СПОСОБ  Algorithm confusion attacks

самая сложная, но и самая жирная атака!
Суть: перепутать симметричный и асимметричный алгоритмы

контекст:

- ==Симметричные алгоритмы (HS256)==: один секретный ключ и для подписи, и для проверки.
    
- ==Асимметричные (RS256, ES256)==: пара ключей. Приватный подписывает, публичный проверяет.
    

сервер знает свой публичный ключ. Если ты изменишь `alg` с `RS256` на `HS256`, сервер может попытаться использовать свой **публичный ключ** как **секретный** для HMAC
гениально и просто!


как это работает:

1. сервер ожидает RS256 и имеет публичный ключ (например, в виде PEM-файла)
   
2. ты меняешь заголовок на `"alg": "HS256"`
   
3. сервер думает: "Ага, теперь я должен использовать симметричный алгоритм. Где же мой секретный ключ? А дай-ка я возьму содержимое публичного ключа и использую его как секрет!" скуяли нет ?
   
4. подписываешь свой поддельный токен, используя публичный ключ как HMAC-секрет
   
5. сервер проверяет — подпись сходится
   

как добыть публичный ключ:

- иногда сервер отдаёт его на `/jwks.json` или в метаданных OIDC
   
- можно вытащить из старого, легитимного токена, если там был `jwk` (но тогда это другая атака)
   
- в некоторых реализациях ключ лежит в открытом доступе

###### "метаданные OIDC это:
>	Простыми словами, это **цифровая визитная карточка провайдера** (например, Google, Microsoft, VK ID). Это JSON-файлик, который висит по специальному адресу и рассказывает всем желающим, как с этим провайдером общаться

>	У каждого провайдера есть **стандартный адрес**, где лежат эти метаданные. Он почти всегда выглядит так:  
>		
		`https://[domain_providera]/.well-known/openid-configuration`


👉 Если ты, как атакующий, нашел метаданные OIDC, ты получаешь **подарок** — ссылку на `jwks_uri`. 
Перейдя по ней, ты скачаешь **публичный ключ**, которым подписываются все JWT-токены этого провайдера







##  Защита от JWT-атак (по версии OWASP и здравого смысла)

OWASP даёт такие рекомендации:

#### 1. Проверяй подпись всегда, везде, неукоснительно

Никаких `decode()` вместо `verify()`. Никаких `alg: none`. Даже если токен прилетел из "доверенного" источника

#### 2. Строго валидируй заголовки

- Отключи поддержку `jwk` и `jku`, если они не нужны нафиг
    
- Если нужны — проверяй, что URL из `jku` ведёт на белый список доверенных хостов, и что соединение идёт по HTTPS
    
- Валидируй `kid` — он не должен содержать path traversal или SQLi
    

#### 3. Используй сильные ключи и храни их безопасно

- Для HS256 ключ должен быть длинным и случайным (не `secret123`)
    
- Регулярно меняй ключи
    
- Не храни ключи в коде или в публичных репозиториях
    

#### 4. Защищайся от algorithm confusion

- Явно указывай, какие алгоритмы разрешены. Лучше всего — только один
    
- Никогда не используй публичный ключ для HMAC-проверки
    

#### 5. Устанавливай короткие сроки жизни токенов

- Используй `exp` (expiration) и проверяй его строго
    
- Для долгих сессий используй refresh tokens, а не долгоживущие JWT
    

#### 6. Используй проверенные библиотеки и обновляй их

- Не пиши свою криптографию
    
- Следи за обновлениями библиотек — в них часто правят именно такие дыры
    

##  Инструменты для тестирования JWT

- **Burp Suite + JWT Editor** — мастхэв для пентеста. Позволяет править и переподписывать токены прямо в Repeater
    
- **[jwt.io](https://jwt.io/)** — онлайн-дебаггер, удобно смотреть структуру
    
- **jwt_tool** — скрипт для автоматизации атак (алгоритм конфьюжн, брутфорс, кража ключей)
    
- **hashcat** — для брутфорса секретов (mode 16500)

##  Итог

JWT — это мощный, но опасный инструмент. Ошибки в его реализации могут стоить  всего приложения. главное:

- **Подпись — это всё**. Если её можно обойти или подделать — ты лох
    
- **Не доверяй тому, что приходит в заголовках**. Особенно `alg`, `jwk`, `jku`, `kid`
    
- **Ключи должны быть секретными и сильными**. Слабый ключ = смерть
    
- **Тестируй всё**. Даже если библиотека "проверенная", разработчик мог настроить её неправильно

### суть атаки  путаницы  симметричные и  асимметричные алг..

Мы говорили, что бывают **симметричные алгоритмы (HS256)**, где один секрет и для подписи, и для проверки, и **асимметричные (RS256)**, где есть пара ключей: приватный (подписывает) и публичный (проверяет)

**Уязвимость** возникает из-за того, что разработчики и библиотеки иногда делают одну и ту же тупую ошибку:

1. Сервер ожидает, что токен подписан **асимметрично (RS256)** и для проверки у него есть **публичный ключ**
    
2. Но библиотека для проверки (`verify()`) смотрит на параметр `alg` в заголовке токена и говорит: "Ага, тут написано HS256! Значит, буду использовать симметричную проверку и тот ключ, что мне дали, как **общий секрет**"
    
3. **Ты, как атакующий**, меняешь `alg` на `HS256` и подписываешь свой левый токен тем же **публичным ключом**, который забрал с сервера (например, с `/jwks.json`)
    
4. Сервер, получив твой токен, честно пытается проверить подпись, используя **публичный ключ как HMAC-секрет**. И, о чудо, подпись сходится! Ведь ты её сделал этим же ключом.
    

**Итог:** ты заставил сервер проверить асимметричную подпись симметричным методом, используя публичный ключ, который и так был у всех на виду. Всё, ты в системе.

###  Как это делается 

В статье как раз описывается эта механика. Давай сверим с тем, что мы учили:

|Шаг из статьи|Как это ложится на нашу теорию|
|---|---|
|**1. Раздобыть публичный ключ сервера.**|Мы говорили, что публичный ключ — не секрет. Его можно найти на стандартных эндпоинтах типа `/jwks.json` или даже вытащить из пары старых JWT-токенов .|
|**2. Сконвертировать ключ в нужный формат.**|Ключ может быть в JSON (JWK), а серверу нужен PEM. Нужно привести к тому же виду, что и у сервера, иначе подпись не совпадет .|
|**3. Изменить JWT.**|Создаёшь свой токен, ставишь в заголовке `"alg": "HS256"`, а в полезной нагрузке (payload) меняешь данные на то, что хочешь, например `"sub": "administrator"`.|
|**4. Подписать токен.**|Берёшь добытый на шаге 1 и сконвертированный на шаге 2 публичный ключ и используешь его как **секрет** для подписи своего токена алгоритмом **HS256** .|

## легенда о шифровании

### Пролог: Рим, 50 год до н.э., кругом одни мудаки

Представь: Гай Юлий Цезарь сидит в своём римском особняке, жрет виноград, чешет репу и думает:

— Бля, ну сколько можно?! Каждый раз одно и то же! Пишу я своему генералу: "Завтра в 5 утра атакуем галлов с левого фланга". Приходит гонец, отдает письмо. Генерал читает, кивает. А на следующий день хуяк — и всё идет по пизде! Потому что это письмо **перехватили галлы**, прочитали нихуя не поняли (они ж тупые), но сам факт, что какие-то варвары читают мою личную переписку — это унижение!

И тут приходит его жена Кальпурния и говорит:  
— Дорогой, ты опять бухтишь? Иди лучше галлов завоёвывай.

Цезарь:  
— Отстань, женщина, я тут государственной важности хуйнёй страдаю. Мне надо придумать, как письма шифровать, чтобы если враг перехватит — нихуя не понял, а свои чтобы сразу врубались 

Кальпурния закатывает глаза и уходит. А Цезаря осеняет!

### Часть 1. Бамбук, вино и гениальная мысль

Цезарь зовёт своего кореша **Марка Антония** (того самого, который потом с Клеопатрой мутил). Сидят они, пьют вино, курят бамбук (ну или что там в Риме курили — может, лавровый лист, хуй знает).

Цезарь:  
— Слышь, Марк, есть идея. Давай договоримся: я пишу письмо, но каждую букву **сдвигаю на три позиции вперёд** в алфавите. Типа А превращается в Г, Б в Д, В в Е и так далее 

Антоний (с похмелья):  
— Чего? Нахуя?

Цезарь:  
— Ну смотри: допустим, я хочу тебе сказать "ВЫЕБИ ГАЛЛОВ". В зашифрованном виде это будет "ЕЮЁК ЕГООС". Если галлы перехватят — подумают, что это какой-то неизвестный язык, и выкинут нахуй 

Антоний:  
— А если они догадаются про сдвиг?

Цезарь (затягиваясь бамбуком):  
— Не догадаются. Они ж галлы, у них мозг размером с оливку. К тому же мы им будем подкидывать ложные письма с надписью "СДВИГ ПЯТЬ", чтобы сбить с толку.

Так родился **шифр Цезаря** — самая гениальная хуйня, которую придумал ленивый римлянин, чтобы не учить своих солдат грамоте 

---

### Часть 2. Как это работало на деле

Цезарь садится за стол, достаёт папирус, пишет:

**V E N I V I D I V I C I**  
(Пришёл, увидел, победил)

Потом сдвигает каждую букву на 3 позиции и получает:

**Y H Q L Y L G L Y L F L** 
Отдаёт гонцу:  
— На, вези. Только если по дороге галлы нападут — сожги письмо или съешь.

Гонец:  
— А если я его съем, то как я доставлю?

Цезарь:  
— Ты умный такой? Съешь **после того** как прочитаешь! Или запомни!

Гонец уходит, думая: "Нахуй я в армию пошёл? Лучше бы в Греции оливки собирал".

### Часть 3. Проблемы перевода (или "Ой, бля, мы забыли про алфавит")

Через пару недель Цезарь получает письмо от Антония. Открывает, а там:

**ZKDW WKH IXCN LV WKLV?**

Цезарь:  
— Антоний, ты ебанулся? Это латинский алфавит? Где буквы U, J, W? У нас их вообще нет в классической латыни! 

Оказалось, что в латинском алфавите времён Цезаря было всего 23 буквы. Не было W, J и U. А Антоний использовал современный английский алфавит, потому что в детстве читал слишком много греческих свитков.

Цезарь пишет ответ:  
— Слышь, Марк, давай договоримся: используем **латинский алфавит**, бля! 23 буквы! W и J отменяются!

Антоний:  
— А как тогда писать "Юлий"? Там же нужна J!

Цезарь:  
— Пиши IVLIVS, как нормальные люди!

Так они разрулили этот кринж.

### Часть 4. Галлы пытаются взломать

Галльский вождь **Верцингеторикс** перехватывает письмо Цезаря. Созывает совет старейшин.

Верцингеторикс:  
— Мужики, у меня тут послание от врага. Надо расшифровать.

Старейшина №1:  
— Дай гляну. "YHQL YLGL YLFL". Хм... Может, это на древнеэтрусском?

Старейшина №2:  
— Не, я думаю, это заклинание. Надо сжечь, чтобы проклятие не навести.

Старейшина №3:  
— А давайте спросим у друидов? Они вон траву курят, может, видели такие символы?

Верцингеторикс (бьёт кулаком по столу):  
— Вы дебилы? Это ж шифр! Надо подобрать сдвиг!

Пробуют сдвиг 1 — фигня. Сдвиг 2 — фигня. Сдвиг 3 — **VENI VIDI VICI**.

Старейшина №1:  
— О, тут написано "Пришёл, увидел, победил". Это что, угроза?

Старейшина №2:  
— Не, это рецепт салата по-римски.

Верцингеторикс:  
— Вы безнадёжны. Готовьтесь к войне.

Итог: галлы проиграли, потому что не шарили в криптографии и вместо этого спорили про салаты

### Часть 5. Наследие (или "Эта хуйня работает до сих пор!")

Прошло 2000 лет. Интернет, 4chan, 2012 год. Появляется картинка с текстом:

**"lxxt>33m2mqkyv2gsq3q=j02ntk"**

Кто-то на форуме пишет:  
— Пацаны, это шифр Цезаря! Там написано "Тиберий Клавдий Цезарь говорит"! Сдвиг на 4!

Начинается движуха. Люди шифруют, расшифровывают, находят ссылки, картинки с утками, телефонные номера, постеры по всему миру. Это была **Cicada 3301** — тайное общество, которое вербовало гениев через шифры 

А всё началось с того, что римский император 2000 лет назад сказал:  
— Нахуй учить генералов читать, лучше буквы сдвину.
