##  эксплуатация парсеров URL в популярных языках программирования

**Автор:** Orange Tsai (Тайвань)  

---

### **1. Введение в SSRF (Server-Side Request Forgery)**

- **Что это:** Уязвимость, позволяющая злоумышленнику заставить сервер выполнить произвольный HTTP-запрос к выбранной цели.
   
- **Цели атаки:**
   
   - Обход межсетевых экранов.
   
   - Доступ к внутренним (интранет) сервисам (Struts2, Redis, Elasticsearch).
   
- **Усиление атаки (Protocol Smuggling):** Превращение SSRF в более мощный вектор путем "провоза" других протоколов внутри HTTP(S).
   
   - **На основе HTTP:** Elastic, CouchDB, MongoDB, Docker API.      
   - **Текстовые протоколы:** FTP, SMTP, Redis, Memcached.
     

---

### **2. Проблема: Несоответствия в парсинге URL**

- **Корень проблемы:** Различия в реализации парсеров URL (валидация) и библиотек, выполняющих запросы.
   
- **Почему это сложно:** Спецификации (RFC 2396, 3986, WHATWG) — это лишь рекомендации. Каждый язык/библиотека реализует парсер по-своему.
   

**Основные компоненты URL (RFC 3986):**  

```http
-
scheme://[userinfo@]host[:port]/path?query#fragment  
```

Атаки фокусируются на обмане парсера относительно `host`, `port` и внедрении данных в `authority`.

---

### **3. Ключевые техники атак и примеры**

#### **A. CR-LF инъекция и смугглинг протоколов**

- **Идея:** Внедрение символов перевода строки (`%0D%0A`) для завершения HTTP-запроса и начала команды другого протокола.
   
- **Пример 1 (SMTP через HTTP):**
   

   ```http
   -
   http://127.0.0.1:25/%0D%0AHELO orange.tw%0D%0AMAIL FROM...
   
   Сервер SMTP отвергает открытый прокси
   ```
 
   
- **Пример 2 (SMTP через HTTPS/SNI - Обход невозможного):** Инъекция в поле `Server Name Indication` (SNI) при TLS-рукопожатии (до шифрования).
    
  ```http
  -
     http://127.0.0.1:25/%0D%0AHELO orange.tw%0D%0AMAIL FROM...
   
      Сервер SMTP отвергает открытый прокси.
  ```

    
    https://127.0.0.1%0D%0AHELO%20orange.tw%0D%0AMAIL%20FROM...:25/
    
    В сниффере трафика видно, что инжектированные данные попадают в plaintext часть ClientHello.
    

#### **B. Злоупотребление парсингом Authority (`userinfo@host:port`)**

- **Идея:** Использование разницы в интерпретации `@`, `:`, `#` и пробелов.
    
- **Пример 1 (PHP `parse_url` vs `readfile`):**
    
    
   ```php
   // Код проверяет, что host=google.com и port=80
    $url = 'http://' . $_GET[url];
    $parsed = parse_url($url);
    if ( $parsed[port] == 80 && $parsed[host] == 'google.com') {
        readfile($url); // Выполнит запрос
    }
    
    
    --
    Обход: http://127.0.0.1:11211:80/
    
    - parse_url видит host=google.com, port=80.
        
    - readfile/cURL идут на 127.0.0.1:11211.
    
   ```
   

        
- **Пример 2 (Обман с `@` и `#`):**  
    `http://google.com#@evil.com/`
    
    - Парсер (PHP) видит `host=google.com` (фрагмент после `#` игнорируется).
        
    - Запрос выполняется к `evil.com` (для некоторых библиотек).
        
- **Пример 3 (cURL/libcurl и многие другие):**  
    `http://foo@evil.com:80@google.com/`
    
    - **cURL < 7.54:** видит `host=google.com`, идет на `evil.com:80`.
        
    - **Обход патча (cURL 7.54+):** Добавление пробела. `http://foo@127.0.0.1 @google.com/`. cURL считает это "некорректным вводом" и не чинит.
        

#### **C. Unicode-обманы (NodeJS)**

- **Идея:** Использование Unicode-символов, которые нормализуются в опасные ASCII.
    
- **Пример 1 (Обход фильтра `..`):**  
    Код: `if (path.indexOf("..") == -1) { http.get(base + path, callback); }`  
    **Обход:** `http://orange.tw/sandbox/ＮＮ/passwd`  
    Символ `Ｎ` (U+FF2E, Fullwidth Latin N) после нормализации становится обычной `N`. `ＮＮ` -> `..`.
    
- **Пример 2 (Обход защиты от CR-LF в HTTP-модуле):**  
    NodeJS кодирует `\r\n` в `%0D%0A`, что безопасно.  
    **Обход:** Использование Fullwidth дефиса и астериска: `U+FF0D` (`－`) и `U+FF0A` (`＊`). После нормализации они становятся `-` и `*`, которые Redis/Memcached интерпретируют как `\r\n`.
    

#### **D. Особенности Glibc NSS (Name Service Switch)**

- **Идея:** Использование особенностей резолвинга имен в стандартной библиотеке C.
    
- **Особенность 1 (RFC1035 - восьмеричные/десятичные escape-последовательности в именах хостов):**  
    `\o\r\a\n\g\e.t\w` -> `orange.tw`. Можно обфусцировать домен.
    
- **Особенность 2 (Отбрасывание "мусора" после пробельных символов):**  
    `socket.gethostbyname("127.0.0.1\r\nfoo")` -> `127.0.0.1`.
    
- **Эксплуатация в SSRF:**
    
    - **Обход валидации хоста:** `http://127.0.0.1\tfoo.google.com`. Парсер видит `host=127.0.0.1\tfoo.google.com`, `gethostbyname()` резолвит в `127.0.0.1`, запрос идет на `127.0.0.1`.
        
    - **Смугглинг через инъекцию в Host-заголовок:** `http://127.0.0.1\r\nSLAVEOF...:6379/`. `gethostbyname()` видит `127.0.0.1`, библиотека отправляет запрос, где после `Host:` идут инжектированные команды.
        
    - **Обход патча Python CVE-2016-5699 (CR-LF в заголовках):** Патч запрещал `\r` и `\n`, за которыми НЕ следует пробел/таб. **Обход:** Начать строку с пробела. `http://0\r\n SLAVEOF...`.
        

#### **E. Несоответствия стандартов IDNA (Internationalized Domain Names)**

- **Проблема:** Парсер и "запрашиватель" используют разные версии стандарта (IDNA2003 vs IDNA2008).
    
- **Пример:** Домены с символами, которые по-разному преобразуются (например, `ß` (IDNA2003 -> `ss`, IDNA2008 -> `xn--...`)).
    
    - Парсер может не распознать `wordpreß.com` как валидный (false), а браузер/cURL преобразуют и запросят `wordpress.com`.

### **4. Кейс-стади**

#### **A. Обход SSRF-защит в WordPress/MyBB/vBulletin**

- **Концепт:** Найти различия в поведении трех компонентов: **Парсер URL**, **DNS-чекер**, **Библиотека запросов**.
    
- **Техника 1 (TOCTOU - "Разное время проверки и использования"):**
    
    1. Код спрашивает у DNS `evil.orange.tw` и получает "белый" IP `1.2.3.4`.
        
    2. Проходит проверку.
        
    3. cURL выполняет запрос и **снова** делает DNS-запрос. В этот момент DNS возвращает "черный" IP `127.0.0.1`. SSRF успешен.
        
- **Техника 2 (Разница в IDNA-конверсии):**
    
    - PHP-функция `gethostbynamel()` не преобразует IDNA-домены (`ß.orange.tw` -> false, проверка не пройдена).
        
    - cURL преобразует `ß` -> `ss` и идет на `ss.orange.tw` (`127.0.0.1`).
        
- **Техника 3 (Разница парсера и cURL):**  
    Использование трюков с `@`, `#` и пробелами, описанных выше.
    

#### **B. Удаленное выполнение кода (RCE) на GitHub Enterprise**

**Цепочка из 4 уязвимостей:**

1. **SSRF-байпас в Webhooks:** Обход черного списка IP через `http://0/`.
    
2. **SSRF во внутреннем сервисе Graphite:** Графитный ? сервис (`127.0.0.1:8000`) уязвим к SSRF через параметр `url`.
    
3. **CR-LF инъекция в Graphite (Python `httplib`):** Позволяет смугглить протокол Memcached в запросе к Graphite.

>**HTTP Request Smuggling** — это уязвимость в информационной безопасности, при которой злоумышленник вмешивается в обработку последовательности HTTP-запросов, которую веб-приложение получает от одного или нескольких пользователей


4. **Небезопасная десериализация в клиенте Memcached (Ruby Marshal):** Данные в кеше десериализуются.    Можно инжектить (внедрять код) вредоносный сериализованный Ruby-объект (например, `ERB`), приводящий к RCE.
    

**Итоговый эксплойт:** Webhook -> Graphite SSRF -> Инъекция команды `set` в Memcached с сериализованным объектом -> При извлечении из кеша объект десериализуется и исполняет код.

### **5 меры защиты 

- на уровне приложения-
    
    - Не использовать входящий URL "как есть" для запроса.
      
    - Разбирать URL, извлекать hostname, **самостоятельно** резолвить его в IP (не доверять `gethostbyname`), применять белые/черные списки, и только затем конструировать новый, контролируемый URL для запроса.
      
- на сетевом уровне
    
    - Использовать сетевые политики и фаерволы для блокировки исходящих запросов с сервера к внутренним сервисам (loopback, private сети).
      
- Проекты:
- Использовать библиотеки типа ==SafeCurl==, которые обеспечивают безопасный резолвинг и проверку

### выводы 

- **Новая поверхность атаки для SSRF:** Уязвимости парсеров URL.
   
- **Новый вектор для смугглинга:** Особенности Glibc NSS и Unicode.
   
- **Проблема актуальна** для OAuth, браузеров, прокси-серверов.
   
- **Защита:** Не доверяйте входящим URL. Проверяйте и конструируйте запросы сами.
