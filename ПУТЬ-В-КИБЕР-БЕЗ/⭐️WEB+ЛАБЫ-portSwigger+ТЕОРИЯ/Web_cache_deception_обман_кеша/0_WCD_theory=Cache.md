>Отравление веб-кэша манипулирует ключами кэша, чтобы внедрить вредоносный контент в кэшируемый ответ, который затем подается другим пользователям.
    Обман веб-кэша использует правила кэширования, чтобы обмануть кэш, чтобы он хранил конфиденциальный или частный контент, к которому злоумышленник затем может получить доступ.

повтор теории
>Веб-кэш - это система, которая находится между исходным сервером и пользователем. Когда клиент запрашивает статический ресурс, запрос сначала направляется в кэш. Если кэш не содержит копии ресурса (известный как промах кэша), запрос пересылается на исходный сервер, который обрабатывает и отвечает на запрос. Затем ответ отправляется в кэш перед отправкой пользователю. Кэш использует предварительно настроенный набор правил для определения того, следует ли хранить ответ.
    Когда в будущем будет сделан запрос на тот же статический ресурс, кэш служит сохраненной копией ответа  непосредственно пользователю (известный как хит кэша).

Динам контент - обычно не кешируется, так как часто содержит секреты

Правила статического расширения файлов -
-----
Эти правила соответствуют расширению файла запрашиваемого ресурса, 
например .==css== для таблиц стилей или ==.js== для файлов JavaScript.

Правила статических каталогов
----
Эти правила соответствуют всем путям URL, которые начинаются с определенного префикса. Они часто используются для нацеливания на конкретные каталоги, которые содержат только статические ресурсы, 
например ==/static== или ==/assets==.

Правила имен файлов
-----
 Эти правила соответствуют конкретным именам файлов с целевыми файлами, которые универсально необходимы для веб-операций и редко меняются, такие как ==robots.txt== и ==favicon.ico==.

# базовая атака на обман кеша

1) Определить целевую конечную точку, которая возвращает динамический ответ, содержащий конфиденциальную информацию. Просмотрите ответы в Burp, так как некоторая конфиденциальная информация может быть не видна на отображаемой странице. Сосредоточьтесь на конечных точках, которые поддерживают методы *GET*, HEAD или OPTIONS, так как запросы, которые изменяют состояние исходного сервера, как правило, не кэшируются.
2) Определите несоответствие в том, как кэш и исходный сервер видят путь URL. Это может быть несоответствие в том, как они:
    - Сопоставляют URL-адреса с ресурсами.
    - Символы разделителя процесса.?
    - Нормализовывают пути.
3) Создайть вредоносный URL-адрес, который использует несоответствие для обмана кэша и заставил его хранить динамический ответ. Когда жертва получает доступ к URL-адресу, его ответ сохраняется в кэше. Используя Burp, вы можете отправить запрос на тот же URL-адрес для получения кэшированного ответа, содержащего данные жертвы. Избегайте этого непосредственно в браузере, так как некоторые приложения перенаправляют пользователей без сеанса или аннулируют локальные данные, что может скрыть уязвимость.

### Использовать разрушитель кэша

во время поиска и создания уязвимости следует использовать разные ключи кеша, чтобы приходила страница всегда с сервера, а не с кеша. То есть при каждом запросе нужно менять данные в заголовках так, чтобы было каждый раз как от нового юзера, это можно автоматизировать -нпример- с помощью Param Miner в burp
>**«Настройки»** верхнего уровня «Параметры», затем выберите «**Добавить динамический кэшбустер**». Теперь Burp добавляет уникальную строку запроса к каждому вашему запросу.

### Обнаружение кэшированных ответов
# ключевые заголовки + тайминги

==X-Cache== заголовок предоставляет информацию о том, был ли подан ответ из кэша. Типичные значения включают в себя:

==X-Cache: hit==- Ответ был подан из кэша.
==X-Cache: miss== Кэш не содержал ответа на ключ запроса, поэтому он был получен с исходного сервера
==X-Cache: dynamic== Исход сервер динамич генер контент. Как правило, это означает, что ответ не подходит для кэширования
==X-Cache: refresh== Кэшированный контент был устаревшим и нуждался в обновлении или повторной валидации.
==Cache-Control== Заголовок может включать директиву, которая указывает на кэширование, например, публичный с максимальным возрастом выше 0.  Это только предполагает, что ресурс кэшируется. 
Это не всегда указывает на кэширование, так как кэш иногда может переопределить этот заголовок.

## Использование правил кэша статического расширения

Правила кэша часто нацелены на статические ресурсы, сопоставляя общие расширения файлов, такие как ==.css== или ==.js==. Это поведение по умолчанию в большинстве CDN.

*Если есть расхождения в том, как кэш и исходный сервер сопоставляют путь URL-адреса с ресурсами или используют разделители, злоумышленник может создать запрос на динамический ресурс со статическим расширением, который игнорируется исходным сервером, но просматривается кэшем.*

---
### Несоответствия отображения путей


Сопоставление путей URL - это процесс связывания путей URL с ресурсами на сервере, такими как файлы, скрипты или выполнение команд
Есть два распространенных стиля:
- ==традиционное сопоставление URL-адресов 
- ==сопоставление URL-адресов RESTful

==Традиционное сопоставление URL-адресов== представляет собой прямой путь к ресурсу, расположенному в файловой системе. Вот типичный пример:

```http
http://example.com/path/in/filesystem/resource.html

----

- http://example.com указывает на сервер.
- /path/in/filesystem/ представляет путь к каталогу в файловой системе сервера.
- resource.html это конкретный файл, к которому обращаются.
```



Напротив, ==URL-адреса в стиле REST== напрямую не соответствуют физической файловой структуре. 
Они абстрагируют пути к файлам в логические части API:
```http
`http://example.com/path/resource/param1/param2`

---------

- http://example.com указывает на сервер.
- /path/resource/ это конечная точка, представляющая ресурс.
- param1 and param2 это параметры пути, используемые сервером для обработки запроса.

```

### пример:

Расхождения в том, как кэш и исходный сервер сопоставляют путь URL-адреса с ресурсами, могут привести к уязвимостям обмана веб-кэша. Рассмотрим следующий пример:
```http
http://example.com/user/123/profile/wcd.css
```
Исходный сервер, использующий сопоставление ==URL-адресов в стиле REST==, может интерпретировать это как запрос для конечной точки ==/user/123/profile== и возвращает информацию о профиле для пользователя 123, 
игнорируя ==wcd.css== как несущественный параметр.

Кэш, использующий ==традиционное сопоставление URL-адресов==, может просматривать это как запрос на файл с именем ==wcd.css==, расположенный ==в каталоге /profile в /user/123==. Он интерпретирует путь URL как ==/user/123/profile/wcd.css==. Если кэш настроен на хранение ответов на запросы, где путь заканчивается на ==.css==, он будет кэшировать и обслуживать информацию о профиле, как если бы это был файл ==CSS==.


-----
### Использование расхождений в сопоставлении путей

Чтобы проверить, как исходный сервер отображает путь URL-адреса к ресурсам, 
==добавьте произвольный сегмент пути к URL-адресу целевой конечной точки==. 
Если ответ по-прежнему содержит те же конфиденциальные данные, что и базовый ответ, он указывает на то, что исходный сервер абстрагирует путь URL и игнорирует добавленный сегмент. 
Например, это тот случай, когда ==изменение /api/orders/123 на /api/orders/123/foo== все равно возвращает информацию о заказе.

Чтобы проверить, как кэш отображает путь URL-адреса с ресурсами, вам нужно будет ==изменить путь==, чтобы попытаться соответствовать правилу кэша, ==добавив статическое расширение==. Например, ==обновите /api/orders/123/foo до /api/orders/123/foo.js.==
Если ответ кэширован, это указывает на:

- Что кэш интерпретирует полный путь URL со статическим расширением.
- Что существует правило кэша для хранения ответов на запросы, заканчивающиеся на `.js`.

 Try a range of extensions, including ==.css==, ==.ico==, and ==.exe==.

Затем вы можете создать URL-адрес, который возвращает динамический ответ, хранящийся в кэше. 
Обратите внимание, что эта атака ограничена конкретной конечной точкой, которую вы протестировали, так как исходный сервер часто имеет разные правила абстракции для разных конечных точек.

# пример:---------------------------------------------

###  Этап 1: Разведка и Поиск Целей

**Цель:** Найти конечные точки (URL), которые возвращают чувствительные, персонализированные данные. Это кандидаты для атаки.

1. **Карта приложения**: Пройдись по всему приложению с включенным прокси (Burp/ZAP). Особое внимание:
   
   - Личный кабинет (==/my-account==, ==/profile==, ==/settings==).
   
   - API-эндпоинты, возвращающие JSON с данными пользователя (==/api/me==, ==/api/orders==).
   
   - Страницы с персональной информацией (==/invoice.pdf==, ==/statement==).        
   
1. **Метод запроса**: Фокусируйся на **==GET==-запросах**. POST/PUT/DELETE обычно не кэшируются.
    
2. **Анализ ответов**: Проверяй не только отображаемую ==страницу==, но и ответы в истории прокси. Чувствительные данные ==(токены, email, баланс)== часто приходят в JSON или скрытых полях ==HTML. hidden поля==
   

### Этап 2: Тестирование Расхождения в Обработке Путей

**Цель:** Проверить, игнорирует ли бэкенд "лишние" сегменты пути.

1. **Базовый запрос**: Выбери целевой эндпоинт, например, ==GET /account/profile.
   
2. **Добавь произвольный сегмент**: Измени URL, добавив любой сегмент пути, например:
   
   - GET /account/profile/==arbitrary==
   
   - GET /account/profile/==foo==/==bar==
   
1. **Сравни ответы**: Если ответ **идентичен** исходному (те же чувствительные данные), бэкенд проигнорировал добавленные сегменты. Это **хороший знак**.? **Видимо данные были - но сайт взял только то что нужно?
2. **Уничтожь кэш-ключ (Cache Buster)**: Во время тестов **всегда** добавляй уникальный параметр к каждому запросу (например, `?cb=12345`), чтобы избежать попадания в кэш и видеть свежий ответ от сервера. 
3. Плагины вроде Param Miner делают это автоматически.
   

###  Этап 3: Проверка Правил Кэширования (Обман Кэша)

**Цель:** Заставить кэш ошибочно сохранить ответ от бэкенда.

1. **==Добавь статическое расширение==**: Возьми URL, который прошел этап 2, и добавь к нему популярные расширения статических файлов:
    
    - `/account/profile/arbitrary` → `/account/profile/arbitrary`.**`css`**
        
    - `/account/profile/arbitrary` → `/account/profile/arbitrary`.**`js`**
        
    - `/account/profile/arbitrary` → `/account/profile/arbitrary`.**`png`**
        
    - Также попробовать: `.jpg`, `.woff2`, `.ico`, `.svg`, `.txt`
        
2. **Отправь два запроса**:
    
    - **Запрос 1 (с Cache Buster)**: ==GET /account/profile/arbitrary.css?cb=12345==. Получи ответ от сервера. Убедись, что бэкенд всё ещё отдаёт те же чувствительные данные (игнорирует `.css`).
        
    - **Запрос 2 (без Cache Buster)**: ==GET /account/profile/arbitrary.css==. Отправь его **немедленно** после первого.
        
3. **Анализируй заголовки ответа** на втором запросе. Ищи признаки попадания в кэш:
    
    - `X-Cache: HIT`, `X-Cache: hit` (прямое указание).
        
    - `Age: [число > 0]` (время в секундах, сколько объект уже в кэше).
        
    - `CF-Cache-Status: HIT` (для Cloudflare).
        
    - Заметно ==меньшее **время отклика**== (тайминг-атака) у второго запроса.
        
4. **Проверь содержимое**: Убедись, что во втором ответе всё ещё есть чувствительные данные жертвы (которые пришли в первом запросе).
    

###  Этап 4: Альтернативные Векторы и Углубленное Тестирование

Расширение файла — не единственный способ. Протестируй другие методы создания расхождения:

1. ==**Специальные символы== и кодирование**:
    
    - `/account/profile/;test.css`
        
    - `/account/profile/..%2ftest.css` (URL-encoded `/`)
        
    - `/account/profile/..\test.css` (обратный слэш)
        
2. **Правила статических каталогов**: Попробуй вставить известные префиксы статических путей:
    
    - /static/..==/account/profile==
        
    - /assets/..==/api/users
        
3. **Правила имен файлов**: Используй имена вроде ==robots.txt==, ==sitemap.xml== как часть пути к динамическому эндпоинту.
    
4. **Методы запроса**: Попробуй ==HEAD== или ==OPTIONS== ==вместо GEТ==. Иногда они обрабатываются так же, но правила кэширования для них могут отличаться.
   

### Этап 5: Автоматизация и Инструменты

1. **Burp Suite + Param Miner**:
    
    - **Автоматический Cache Buster**:  в настройках "Add a dynamic cache buster".
        
    - **Сканирование заголовков**: Плагин может автоматически проверять влияние различных заголовков (например, `X-Forwarded-Host`) на ключ кэша.
        
2. **Turbo Intruder / Python-скрипты**: Для массовой проверки множества эндпоинтов и различных суффиксов.
    
3. **Burp Scanner** (Professional): Может авто находить ==некоторые виды уязвимостей кэширования==.

# КРАТКО _ ВЫВОД как искать

#### **Фаза 1: Подготовка и настройка**

1. ** Burp Suite (прокси)** вкл ))
    
2. **Активировать "разрушитель кэша" (Cache Buster)** - В Burp Suite (например, через Param Miner) включить опцию "Add a dynamic cache buster" (например, `?cb=random`). **Результат:** Все  запросы будут иметь уникальный параметр, что заставляет сервер каждый раз возвращать свежий ответ, минуя кэш. Это необходимо для чистоты тестирования.
    

#### **Фаза 2: Разведка и поиск цели**

3. **Составить карту приложения** - Просмотреть всё приложение через прокси. Внимание на методы **GET, HEAD, OPTIONS**. **Результат:** Список URL-адресов (эндпоинтов) для тестирования.
    
4. **Выявить эндпоинты с конфиденциальными данными** - Проанализируйть ответы сервера в истории прокси. Ищем динамические ответы, содержащие личные данные (токены, email, баланс, данные профиля), даже если они не отображаются на странице (например, в JSON или скрытых полях HTML). 
    **Результат:** Целевой список URL-адресов, возвращающих секретные данные.
   

#### **Фаза 3: Поиск расхождения в обработке путей (Path Mapping)**

5. **тест игнорирование сегментов пути бэкендом** - 
6. Для каждого целевого URL (напр., `GET /account/profile`) добавить произвольный сегмент 
7. (напр., `GET /account/profile/arbitrary` или `.../foo/bar`). 
8. Отправьте запрос **с кэш-бастером**. **Результат:** Если ответ идентичен исходному (те же конфиденциальные данные) -> бэкенд игнорирует добавленные сегменты. Это положительный сигнал.
    
9. **Проверь реакцию кэша на статическое расширение** - Возьми URL  (где бэкенд проигнорировал сегмент) и добавьте к нему статическое расширение файла (`.css`, `.js`, `.png`, `.ico`, `.txt`). 
10. Пример: `/account/profile/arbitrary.css`. 
11. **Результат:** Определение, воспринимает ли кэш новый путь как статический ресурс.
