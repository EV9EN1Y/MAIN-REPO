#### CORS - когда я заставляю браузер жертвы сделать какой либо запрос у сервера и полученные данные отразить / переслать еще и на мой сервер (путем поссещения жертвой моего сайта)

#### CSRF - когда я (путем перехода жертвы на мой сайт/сервер) - перенаправлением заставляю ее браузер выполнить то или иное действие на целевом сайте (например выполнить перевод денег, сменить пароль)
#### XSS - когда я (путем перехода жертвы по ссылке которая содержит js код) (либо хранимые xss - когда сервер сам выдает уже уязвимый код, ранее сохраненный в него)- заставляю браузер жертвы выполнить практический любой код, стырить данные или выполнить действие на сайте (то есть просто как доп функционал появляется у сайта - на который перешли по ссылке) 

#### SSRF - когда я (путем изменения запросов к серверу) через запросы от офиц сайта делаю такой запрос на сервер - чтобы сервер выполнил то или иное дейтвие либо отправил команду дальше в внутренний сервер! ТО есть сам сайт отправил серверу команду, например, чтобы показать файлы операционной системы или схему сети! сервер как прокси получается

Cross-site request forgery это уязвимость которая позволяет хакеру-атакеру заставить жертву выполнить нежелательные действия на сайте где она залогинена

атакер обходит same-origin policy и использует сессионные куки жертвы для отправки поддельных запросов


csrf это про то что браузер жертвы сам отправляет запрос используя её куки 

xss это про то что атакер выполняет свой javascript прямо в контексте сайта жертвы

## коротко - виды

|Вид защиты|Суть|Как обойти|
|---|---|---|
|CSRF токен|скрытое поле в форме|переключить метод GET, удалить токен, подставить свой токен, выставить свою куку|
|SameSite Lax|кука только в GET по ссылкам|использовать GET вместо POST, method override, гаджеты на том же сайте, sibling-домены|
|SameSite Strict|кука только в same-site запросах|гаджеты на том же сайте (редиректы), sibling-домены|
|Referer|проверка откуда пришел запрос|убить Referer, подделать через unsafe-url, зарегистрировать похожий домен|

> CSRF это про то что браузер сам таскает куки жертвы куда попало. защита должна быть на сервере и в куках одновременно

### 3 условия для атаки

1. **релевантное действие** — есть что-то что атакер хочет сделать (смена email, перевод денег)
   
2. **сессия в куках** — Обработка сеансов на основе файлов cookie
   
3. **предсказуемые параметры** — атакер может угадать все параметры запроса (есть все данные для запроса)

-------

### Пример классической атаки

обычный запрос смены email:
```http
POST /email/change HTTP/1.1
Host: vulnerable-website.com
Cookie: session=yvthwsztyeQkAPzeQ5gHgTvlyxHfsAfE
Content-Type: application/x-www-form-urlencoded

email=wiener@normal-user.com
```

атакер создает страницу:

```html
<html>
    <body>
        <form action="https://vulnerable-website.com/email/change" method="POST">
            <input type="hidden" name="email" value="HACK@evil-user.net">
        </form>
        <script>document.forms[0].submit()</script>
    </body>
</html>
```

когда жертва заходит на страницу атакера — браузер сам отправляет форму с её куками


произойдет следующее:

- страница злоумышленника запустит HTTP-запрос на уязвимый веб-сайт
- если пользователь вошел на уязвимый веб-сайт, его браузер автоматически включит сеансовый файл cookie в запрос (при усмотре, если файлы cookie SameSite не используются
- уязвимый веб-сайт обработает запрос обычным способом, обработает его как сделанный пользователем-жертвой и изменит свой адрес электронной почты

## ВИДЫ ЗАЩИТЫ И ИХ ОБХОД

## 1. 🔷🔷🔷  CSRF ТОКЕНЫ 🔷🔷🔷 

CSRF ТОКЕНЫ - уникальное секретное значение которое сервер генерирует и вставляет в формы клиент должен отправить его обратно при выполнении действия
```html
<input type="hidden" name="csrf" value="50FaWgdOhi9M9wyna8taR1k3ODOR8d6u">
```
### способы обхода

#### зависимость от метода
если токен проверяется только в POST можно переключиться на GET
(может есть методы - где нет проверки)

уязвимый код проверяет только POST:
```http
POST /email/change HTTP/1.1
...
csrf=token&email=test@test.com
```

атака через GET:
```http
GET /email/change?email=pwned@evil-user.net HTTP/1.1
Cookie: session=...
```

-----------

#### Токен необязателен (если его вообще удалить)

если проверка пропускается когда токен отсутствует — просто удаляем параметр

было
```http
csrf=token&email=test@test.com
```
стало
```http
email=pwned@evil-user.net
```

-----

#### когда токен не привязан к сессии (то есть подходит любой другой токен)

сервер хранит глобальный пул токенов и принимает любой из пула

атакер логинится на свой аккаунт забирает свой токен и подсовывает его жертве

-------
#### токен привязан к отдельной куке

используются две куки: `session` и `csrfKey` но они не связаны

атакер может подменить `csrfKey` через другую уязвимость (например на поддомене) и тогда его токен подойдет

--------
#### Double submit (нелогичная сверка токенов)

токен дублируется в куке и в параметре сервер просто сверяет их
```http
Cookie: csrf=R8ov2YBfTYmzFyjit8o2hKBuoIjXXVpa
...
csrf=R8ov2YBfTYmzFyjit8o2hKBuoIjXXVpa
```

атакер-хакер может сам выставить куку с любым токеном через любой поддомен того же сайта и использовать этот же токен в параметре

--------


## 2.  🔷🔷🔷 SAMESITE COOKIES 🔷🔷🔷  (Strict - Lax - None)

### что это и с чем это едят..

это атрибут куки который говорит браузеру когда отправлять куку на другие сайты

**Strict** — не отправлять ни при каких кросс-сайт запросах  

**Lax** — отправлять только при GET и только при top-level навигации (переход по ссылке)  

**None** — отправлять всегда (требует Secure + HTTPS)

с 2021 хром по умолчанию ставит Lax если атрибут не указан

### способы обхода::->

#### lax + GET

если сервер принимает GET вместо POST можно дернуть ссылкой

```html

<script>document.location='https://site.com/email/change?email=bad@mail.com'</script>
```
#### method override

некоторые фреймворки позволяют переопределить метод через параметр
```html
<form action="https://site.com/email/change" method="POST">
    <input type="hidden" name="_method" value="GET">
    <input type="hidden" name="email" value="bad@mail.com">
</form>
<script>document.forms[0].submit()</script>
```
#### On-site gadgets

даже со Strict можно найти на том же сайте уязвимость которая делает редирект на нужный экшен

когда клиентский редирект считается same-site запросом и куки летят

#### сайблинг-домены

запрос с `app.example.com` на `intranet.example.com` — это **same-site** хотя cross-origin

если на одном из поддоменов есть XSS можно атаковать любой другой поддомен

-----

#### Новые куки (2 минуты)

хром дает лаг в 120 секунд для новых кук с Lax по умолчанию чтобы не ломать SSO

можно заставить жертву обновить куку (например через OAuth логин) и сразу атаковать

--------



## 3.  🔷🔷🔷 REFERER-BASED (рефер) ЗАЩИТА 🔷🔷🔷 

### Че это

сервер проверяет заголовок Referer и убеждается что запрос пришел с его же домена

### как это обойти-

#### Referer не обязателен

если проверка пропускается когда Referer отсутствует - убиваем заголовок

```html
<meta name="referrer" content="never">
```
#### наивная валидация

проверка что домен начинается с expected или содержит его

можно зарегистрировать `vulnerable-site.com.attacker.com` или добавить в параметры `?vulnerable-site.com`

но современные браузеры режут Referer поэтому нужно форсировать через:
```html
<meta name="referrer" content="unsafe-url">

```

##  🔷🔷🔷 КАК ЗАЩИЩАТЬСЯ (ПРАВИЛЬНО) 🔷🔷🔷 

### CSRF токены правильно

**генерация**: CSPRNG + timestamp + секрет  
**передача**: в hidden поле формы (не в куках, не в URL)  
**валидация**: строго для всех методов, обязательное наличие, привязка к сессии

### SameSite куки правильно

**Strict** для всего что модифицирует данные  
**Lax** только если реально нужно (и понимаешь риски)  
никогда не ставь `None` без необходимости

### Доп

изолируй небезопасный контент (загрузки пользователей) на отдельном сайте  
не забывай про sibling-домены — они same-site  
проверяй WebSockets (там тоже бывает CSWSH)

### Проверка на основе реферера 

Некоторые приложения используют заголовок HTTP Referer для защиты от атак CSRF, как правило, проверяя, что запрос исходит из собственного домена приложения. Это, как правило, менее эффективно, чем проверка токена CSRF.
