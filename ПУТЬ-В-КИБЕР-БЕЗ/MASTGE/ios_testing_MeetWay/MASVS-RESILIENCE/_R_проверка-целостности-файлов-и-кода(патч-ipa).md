# **MASTG-TEST-0090** - Testing File Integrity Checks

это проверка того, насколько хорошо приложение защищает свою целостность (т.е. обнаруживает, если кто-то пытается его изменить или взломать)

**Цель теста** - проверить, насколько устойчиво мобильное приложение к **модификациям**(изменению кода, ресурсов, сохраненных данных) и может ли оно **обнаружить вмешательство**

> **Ключевая идея:** Приложение не должно слепо доверять собственным файлам и исполняемому коду. Оно должно активно проверять свою целостность

-------

Без проверок целостности злоумышленник может:

- Изменить бизнес-логику (обойти покупки, проверку лицензии)
    
- Внедрить вредоносный код (шпионить за пользователем)
    
- Подменить ресурсы (фишинговые экраны входа)
    
- Модифицировать сохраненные данные (бесконечные ресурсы в игре)

---------


### два подхода (   Code и  File   )

что должно делать приложение с ур защиты R:

⭐️1️⃣⭐️**ПРОВЕРЯТЬ Целостность кода** (Source Code Integrity)
приложение должно проверять перед запуском - сам глайный исполняемый файл (`Mach-O`), динамические библиотеки, фреймворки, например Внедрение Frida Gadget, патч инструкций, подмены методов!

как защищается приложение при проверке кода:
- **Проверка подписи** (криптографическая верификация `LC_CODE_SIGNATURE`)
- **Вычисление контрольной суммы** (хеш сегмента `__TEXT`)
- **Обнаружение отладчиков** (`ptrace`, `sysctl`)
- **Поиск внедренных библиотек** (Frida, Substrate)



================================================



⭐️2️⃣⭐️**ПРОВЕРЯТЬ  Целостность данных** (File Storage Integrity)
приложение должно проверять перед запуском -  пользовательские файлы приложения: `.plist`, SQLite, `NSUserDefaults`, кэш, документы|
, к примеру : - Изменение сохраненной игры, правка настроек, подмена ресурса

как защищается приложение при проверке файлов:
- **Контрольная сумма** (хеш файла)
- **HMAC** (хеш с секретным ключом, хранящимся в коде или связке ключей)
- **Цифровая подпись** (асимметричное шифрование)
- **Шифрование** (при расшифровке проверяется padding/магическое число)






---------



### реакция на внедрение

при обнаружении модификации приложение **должно** отреагировать, например:

- 🔴 **Аварийное завершение** - тихий краш без объяснения причин
    
- ⚠️ **Предупреждение пользователю** с запросом подтверждения риска

## - 1 - Защита кода приложения (Source Code Integrity)

### 1.1 🟢 Проверка подписи (криптографическая верификация `LC_CODE_SIGNATURE`)

**Что это:** Приложение проверяет, что его кодовая подпись не была изменена после установки

**Как тестировать:**

|1|  Распаковать `.ipa` файл приложения (подойдет и шифрованный ипа)

|2|   Внедрить в исполняемый файл `Mach-O` любое изменение (например, добавить пустую строку в бинарник или изменить одну инструкцию)

|3|   Переподписать приложение своим сертификатом разработчика (например, с помощью `zsign` или `codesign`)

|4|   Установить измененное приложение на джейлбрейкнутое устройство и запустить

**Ожидаемая реакция при наличии защиты:**

- Приложение **аварийно завершается** сразу после запуска
- Появляется сообщение: «Приложение повреждено» или аналогичное
- Приложение **стирает свои данные** и закрывается
- Отправка отчета на сервер разработчика

**Как обойти (для оценки сложности):**

- Найти функцию проверки подписи (например, `SecCodeCheckValidity` или `SecStaticCodeCheckValidityWithErrors`) и захучить её через Frida, заставив возвращать `success`
- Если проверка выполняется при каждом запуске - написать твик для `Cydia Substrate`, который патчит функцию в памяти
   
**критерии оценки:**

- легкая защита: один хук одной функции решает проблему
    
- сложная: проверка размазана по коду или использует обфускацию
    


---------

### 1.2  🟢 вычисление контрольной суммы (хеш сегмента `__TEXT`)

 приложение вычисляет хеш своего сегмента `__TEXT` (кодовый сегмент) и сравнивает с эталонным значением.

**как тестировать:**

|1|   Запустить приложение в неизменном виде - убедиться, что оно работает

|2|   Изменить **один байт** в сегменте `__TEXT` бинарника (использовать любой hex-редактор, через филза может даже)

|3|   Переподписать приложение (обязательно, иначе iOS не запустит, потому что сертификат аппл не сработает, если поменять код, так как сертификат разработчика сверяет хеш SHA-256)

|4|    Запустить измененную версию и смотреть, че по реакции будет

**Ожидаемая реакция при наличии защиты:**

- приложение вычисляет хеш (например, `SHA-256`) сегмента `__TEXT` и сверяет с «зашитым» значением
- при несовпадении - **немедленный краш** или бесконечный цикл


**как обойти:**

- найти функцию, которая вычисляет хеш, и подменить результат на ожидаемый
- если хеш зашит в коде - найти его и заменить на хеш измененного сегмента
- захучить функцию `mach_header` (ну или ту, которая там вызывается, сложность - найти ее!) или системные вызовы чтения памяти

**особенность:** этот механизм может быть эффективен даже против статического патчинга, так как хеш пересчитывается при каждом запуске

### 1.3 🟢  Обнаружение отладчиков (`ptrace`, `sysctl`)

приложение проверяет, не пытается ли к нему подключиться отладчик (LLDB, GDB)

вот здесь я уже выполнял такой тест
🍺 👉[[_R__LLDB-СОПРОТИВЛЯЕМОСТЬ]]

**как тестировать:**

**ptrace**
Запустить приложение через LLDB (подключ как отладчик) и посмотреть, не вылетает ли оно сразу

**sysctl**
Запустить приложение под отладчиком и проверить, не завершается ли оно при попытке приаттачиться

**getppid**
Запустить приложение через отладчик и проверить, не определяет ли оно, что его родительский процесс - не `launchd`

**как выглядит защита в коде:**

```c
// ptrace анти-отладка
ptrace(PT_DENY_ATTACH, 0, 0, 0);  // запрещает подключение отладчика
// sysctl проверка
static bool AmIBeingDebugged(void) {
    struct kinfo_proc info;
    // ... sysctl запрос с P_TRACED флагом
    return ((info.kp_proc.p_flag & P_TRACED) != 0);
}
```
**Ожидаемая реакция:**

- При попытке подключить отладчик приложение **немедленно завершается** (краш)
- Приложение работает в обычном режиме, но отказывается выполнять чувствительные операции

**как обойти:**

- хукнуть `ptrace` и `sysctl` через Frida/lldb до их вызова
   
- использовать анти-анти-отладку: например, установить брейкпоинт на `ptrace` и изменить аргументы вызова
   
- На неджейлбрейкнутом устройстве обойти сложнее, на джейлбрейкнутом - тривиально (патч библиотек или замена системных вызовов)

### 1.4 🟢  поиск внедренных библиотек (Frida, Substrate)

**Че эт:** приложение сканирует список загруженных динамических библиотек на предмет подозрительных (FridaGadget, CydiaSubstrate и т.д.)

**Как тестить:**

|1|  Внедрить Frida Gadget в IPA (или запустить Frida Server на устройстве)

|2|   Запусти приложение

|3|   подключиться к приложению через Frida (`frida-ps -U`, затем`frida -U -n AppName`, т.е минимально поэксплуатировать фриду или скрипт свой запустить)

**что в идеале проверяет приложение:**

- Обход всех загруженных образов через `_dyld_image_count()` и `_dyld_get_image_name()`
   
- поиск строк: `"FridaGadget"`, `"frida"`, `"cynject"`, `"libcycript"`, `"Substrate"`, `"DynamicLibraries"`
   
- проверку открытых портов Frida (по умолчанию 27042) через `bind()` или `connect()`
   
- проверку переменных окружения типа `DYLD_INSERT_LIBRARIES`  
   

**ожидаемая реакция приложения на наличие этих сигнатур:**

Приложение завершается или отказывается выполнять критическую логику
Frida не может аттачиться или процесс зависает
   

**обойти как это дело:**

- Переименовать библиотеку Frida перед внедрением
- Использовать **Frida в режиме «спартанца»** - внедрение без стандартных имен файлов (обфускация фрида)
- Хукчить функцию `_dyld_image_count` или `_dyld_get_image_name`, чтобы скрыть подозрительные библиотеки
- Использовать `frida-server` в обход проверки портов
   

**оценка:**
- Легко: достаточно переименовать библиотеку
- Сложно: если приложение проверяет по хешу, а не по имени

## - 2 -  защита данных на диске (File Storage Integrity)



### 2.1  🟠 контрольная сумма (хеш файла)

**чего это такое..:** Приложение вычисляет хеш важных файлов (конфигурация, база данных, кэш) и сверяет с эталоном

**как тестить:**

|1|   определить директорию приложения: `/var/mobile/Containers/Data/Application/<APP_ID>/` 

|2|     Найти там файлы, которые приложение создает и использует (`.plist`, `.db`, `.json`, `.dat`) (файлы с важными данными)

|3|    изменить **-достаточно одного байта-** в любом из этих файлов (например, с помощью Filza или hex-редактора)

|4|    запустить приложение и наблюдать, че дальше

**ожидаемая реакция:**

- приложение обнаруживает изменение и **сбрасывает данные** к значениям по умолчанию
- приложение отказывается запускаться с «поврежденными» данными
- приложение удаляет модифицированный файл и создает новый
   
**как обойти:**

- найти функцию, вычисляющую хеш, и захучить её, подставляя оригинальное значение
- если хеш хранится отдельно - найти и обновить его
- отключить проверку через патч условных переходов


---------


### 2.2  🟠 HMAC (хеш с секретным ключом)

**что это:** более безопасная версия контрольной суммы - приложение вычисляет HMAC файла с использованием секретного ключа, что не позволяет просто пересчитать хеш без знания ключа

**как тестировать:**

|1|   измени файл данных приложения (как в предыдущем пункте п.2.1)
|2|   запусти приложение и проверь, обнаружило ли оно изменение

**как выглядит защита в коде:**
```swift
// пример с CryptoKit
let secretKey = SymmetricKey(data: "secret".data(using: .utf8)!)
let hmac = HMAC<SHA256>.authenticationCode(for: fileData, using: secretKey)

https://ssojet.com/hashing/hmac-sha3-224-in-swift/#main
```

**ожидаемая реакция:**

- приложение не просто проверяет хеш, а требует HMAC, вычисленный с секретным ключом
- без знания ключа нельзя сгенерировать валидный HMAC для измененного файла

**как обойти:**

- **здесь уже придется - извлечь ключ** из памяти приложения (во время выполнения - через Frida, может по алгоритмы поиска рандомных строк или в кейчен через  `Keychain-Dumper`)
- найти ключ в коде (если он зашит статически - плохая практика)
- захуить функцию верификации HMAC, заставив её всегда возвращать `true`

**критерии оценки (из MASTG):**

- «насколько сложно получить HMAC-ключ?»
- «можно ли обойти, изменив содержимое файла или пары ключ-значение?»

---------


### 2.3  🟠 цифровая подпись (асимметричное шифрование)

**это когда:** приложение подписывает важные файлы с использованием закрытого ключа (на стороне сервера или во время сборки), а проверяет - с использованием публичного ключа, встроенного в приложение

**как тестировать:**

|1|    изменить подписанный файл (обычно это критичные конфиги или ресурсы)

|2|    Запустить приложение и проверить реакцию

**отличие от HMAC:**

- при подписи используется **пара ключей** (приватный + публичный)
- Без приватного ключа нельзя создать новую подпись
- Взломщик не может подделать подпись, даже если знает публичный ключ

**ожидаемая реакция:**

- приложение проверяет подпись файла с помощью публичного ключа
   
- при несовпадении - отказ от загрузки данных
   

**как обойти:**

  **Извлечь публичный ключ** из приложения - это возможно, но не поможет для создания подписи
   
- заменить **публичный ключ** на свой (требует патча приложения)
   
  Захукать функцию верификации подписи
   
- **самый сложный случай:** найти и извлечь приватный ключ (если он по ошибке попал в бинарник - такое бывает, но очень редко)
   

**Оценка:** Обычно **высокая сложность обхода**, если реализовано правильно


---------

### 2.4 🟠  Шифрование файлов

**Че это:** Приложение хранит данные в зашифрованном виде. При расшифровке проверяет padding/константа-число, что позволяет обнаружить подмену

>**Padding (PKCS#7)** - это автоматический механизм проверки целостности, встроенный в большинство алгоритмов блочного шифрования (AES). При изменении зашифрованного файла даже на 1 байт, проверка padding'а с высокой вероятностью обнаружит подмену и вызовет ошибку. Это простой, но эффективный способ защиты сохраненных данных от модификации, не требующий отдельного кода для HMAC/подписи

>  это механизм дополнения данных до размера, кратного блоку шифра (16 байт для AES). При сохранении данных алгоритм вычисляет, сколько байт не хватает до полного блока, и добавляет это количество байт, каждый из которых равен числу добавленных байт. При расшифровке приложение читает последний байт, определяет ожидаемую длину padding'а, затем проверяет, что все байты в этой позиции имеют одинаковое значение. Если хотя бы один байт не соответствует ожидаемому - данные считаются повреждёнными или подменёнными, и приложение инициирует ошибку, что служит защитой от модификации зашифрованных файлов



**Как тестировать:** 
|1|   найти файл данных приложения (обычно нечитаемый, бинарный)
|2|   Изменить **один байт** в зашифрованном файле
|3|   запустить приложение и наблюдать

**Ожидаемая реакция:**

- При расшифровке padding (например, PKCS#7) становится невалидным
   
- Приложение обнаруживает ошибку и **аварийно завершается** или отказывается читать данные
   
- В сложных реализациях - проверка магического числа в расшифрованных данных
   

**Как обойти:**

- Если файл просто зашифрован (без проверки целостности) - можно расшифровать, изменить, зашифровать обратно (при знании ключа)
   
- Если используется **аутентифицированное шифрование** (AES-GCM), изменение файла будет обнаружено на этапе расшифровки
   
- Найти ключ шифрования в памяти или в коде приложения
   

**Связь с HMAC/подписью:** Часто шифрование комбинируется с HMAC для обеспечения и конфиденциальности, и целостности.
