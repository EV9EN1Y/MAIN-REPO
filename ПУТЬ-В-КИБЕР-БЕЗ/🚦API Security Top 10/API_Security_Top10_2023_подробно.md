# OWASP API Security Top 10 – 2023 (API)

Версия: 2023 | Источник: https://owasp.org/API-Security | Дата: 04.08.2026

> OWASP API Security Top 10 – 10 самых критичных рисков безопасности именно **API**. Актуальная официальная версия – **2023** (2019 устарела). Подходит для REST, GraphQL, SOAP, gRPC.

---

##  (API Top 10 – 2023)

1. **API1:2023 – Broken Object Level Authorization (BOLA)** – нарушенная авторизация на уровне объектов (IDOR)
2. **API2:2023 – Broken Authentication** – нарушенная аутентификация
3. **API3:2023 – Broken Object Property Level Authorization** – нарушенная авторизация на уровне свойств объекта (mass assignment)
4. **API4:2023 – Unrestricted Resource Consumption** – неограниченное потребление ресурсов
5. **API5:2023 – Broken Function Level Authorization** – нарушенная авторизация на уровне функций
6. **API6:2023 – Unrestricted Access to Sensitive Business Flows** – неограниченный доступ к чувствительным бизнес-процессам
7. **API7:2023 – Server Side Request Forgery (SSRF)** – подделка серверных запросов
8. **API8:2023 – Security Misconfiguration** – небезопасная конфигурация
9. **API9:2023 – Improper Inventory Management** – неправильное управление инвентарём API
10. **API10:2023 – Unsafe Consumption of APIs** – небезопасное потребление сторонних API

##  API1:2023 – Broken Object Level Authorization (BOLA)

**Что это:** нарушенная авторизация на уровне объектов = классический **IDOR**. API доверяет ID из запроса и не проверяет, принадлежит ли объект пользователю. **Самый частый и опасный риск API.**

**Примеры:** `GET /users/12345/profile` – подмена 12345 на чужой ID; доступ к чужим заказам, сообщениям, файлам.

**Как найти:**
- Для каждого эндпоинта с ID-параметром (в URL, body, query): подставить ID другого пользователя
- Собирать ID: перебор (если инкрементальные), из чужих ответов, из ссылок
- Тестировать все методы: GET/PUT/DELETE к чужому объекту (например, удаление чужого поста)
- Автоматизация: Burp (Authorized/Unauthorized), ZAP, custom scripts
- GraphQL: проверять запросы к чужим объектам по ID

**Как защищаться:**
- Проверка владения (ownership) на **каждом** эндпоинте с объектом
- Использовать UUID вместо инкрементальных ID (усложняет перебор, но НЕ заменяет проверку прав!)
- Следовать OWASP ASVS V4.2 (объектный уровень), NIST SP 800-53
- Централизованная проверка прав (middleware/interceptor), а не в каждом методе
- Не раскрывать ID чужих объектов в ответах/ссылках без необходимости

**Дополнения:** BOLA = «IDOR для API». В веб-Top 10 это A01 (Broken Access Control). Самое первое, что проверяет пентестер в API.

## 🔑 API2:2023 – Broken Authentication

**Что это:** проблемы с аутентификацией: слабые механизмы, обход, перебор, слабые токены, отсутствие rate limit на логин, плохое управление сессиями.

**Примеры:** перебор паролей без лимита, JWT с alg=none или слабым секретом, отсутствие MFA, токены в URL, бесконечные сессии, восстановление пароля с утечками.

**Как найти:**
- Тест перебора: Burp Intruder на /login – есть ли rate limit/блокировка
- Анализ JWT: алгоритм, секрет (crack с hashcat), срок жизни, возможность подделки
- Проверка сессий: TTL, logout (инвалидация), смена пароля (сброс всех сессий)
- Проверка восстановления пароля: перечисление пользователей, утечки в ответах
- Проверка OAuth/SSO: redirect-uri, state-параметр

**Как защищаться:**
- Rate limit + CAPTCHA на логин/восстановление/OTP
- MFA (TOTP/WebAuthn) – обязательно для админов и чувствительных операций
- JWT: короткий TTL (15 мин), ротация refresh, сильный секрет, проверка всех claims
- Безопасное восстановление: одноразовые ссылки/коды, без раскрытия существования аккаунта
- Политика паролей + проверка по breached-спискам (haveibeenpwned API)
- Инвалидация всех сессий при смене пароля

**Дополнения:** credential stuffing – использование утечек паролей. В веб-Top 10 это A07. OWASP ASVS V2 (Authentication) и V3 (Session Management).

## 🧩 API3:2023 – Broken Object Property Level Authorization

**Что это:** нарушенная авторизация на уровне свойств: **mass assignment** (массовое присваивание) и чтение лишних полей. Пользователь передаёт/читает поля, которые не должен.

**Примеры:**
- Mass assignment: `PUT /users/me` с телом `{"role":"admin","balance":100000}` – сервер сохраняет лишние поля
- Чтение лишнего: ответ содержит `isAdmin`, `internalNote`, `passwordHash` – клиент их видит

**Как найти:**
- Mass assignment: в PUT/POST добавлять лишние поля (role, isAdmin, id, price) и смотреть, сохранились ли
- Чтение: анализировать ответы API на чувствительные/внутренние поля
- Проверять схемы: соответствуют ли поля запроса/ответа спецификации
- GraphQL: запрашивать лишние поля (introspection)

**Как защищаться:**
- Явные DTO (data transfer objects): принимать только разрешённые поля (allowlist)
- Маппинг вручную, а не «сохранить всё тело как есть»
- Не возвращать внутренние поля (роли, хэши, служебные флаги) в ответах
- Автоматическая валидация схем (OpenAPI, JSON Schema)
- Раздельные модели входа (input) и выхода (output)

**Дополнения:** новинка 2023 (в 2019 не было). Отличается от BOLA: там объект, здесь свойства. OWASP ASVS V5.3.

## ⚖️ API4:2023 – Unrestricted Resource Consumption

**Что это:** неограниченное потребление ресурсов: нет лимитов на запросы, размеры, сложность операций → DoS, исчерпание квот, дорогие счета за облако.

**Примеры:** нет rate limit, огромные payload (без лимита размера), пагинация без лимита (page_size=1000000), дорогие запросы (GraphQL depth), загрузка больших файлов, много попыток OTP/SMS (бомбинг).

**Как найти:**
- Тест rate limit: N запросов подряд – блокируется ли
- Запросы с огромными параметрами: размер body, page_size, лимиты
- GraphQL: depth/алиасы (billion laughs)
- Проверка лимитов на загрузку, экспорт, генерацию отчётов
- Тайминги: дорогие операции без ограничений

**Как защищаться:**
- Rate limiting везде: по пользователю и IP (login, OTP, поиск, экспорт)
- Лимиты на размер запроса/файла, на количество элементов
- Ограничение пагинации (max page size), таймауты на операции
- GraphQL: ограничение depth/complexity, запрет дорогих запросов
- Квоты и алерты на потребление ресурсов (облако)
- Анти-автоматизация: CAPTCHA для публичных операций

**Дополнения:** сюда же: SMS/email бомбинг, webhook-flood, экспорт огромных данных. В веб-Top 10 это частично A04 (Insecure Design) + DoS.

## 🚪 API5:2023 – Broken Function Level Authorization

**Что это:** нарушенная авторизация на уровне функций: обычный пользователь вызывает функции администратора/модератора (BFLA – Broken Function Level Authorization).

**Примеры:** `DELETE /admin/users/{id}` доступен обычному юзеру; смена роли, модерация, настройки – без проверки прав.

**Как найти:**
- Составить матрицу ролей × функций (user/mod/admin)
- Дёргать админ-эндпоинты с обычным токеном
- Искать эндпоинты: /admin, /internal, /moderate – и проверять права
- Тестировать все методы на одних URL
- Проверять горизонтальный доступ (пользователь к функциям другого пользователя с той же ролью)

**Как защищаться:**
- Серверная проверка ролей/прав на каждом эндпоинте (не скрытие кнопок в UI)
- RBAC/ABAC: централизованная политика, deny by default
- Разделение публичного и внутреннего API (отдельные хосты/сети)
- Тесты: негативные сценарии прав в CI/CD
- ASVS V4.3 (функциональный уровень)

**Дополнения:** BOLA (API1) = объекты, BFLA (API5) = функции. Оба – половина «Access Control» из веб-A01.

## 💼 API6:2023 – Unrestricted Access to Sensitive Business Flows

**Что это:** API позволяет автоматизировать «человеческие» процессы: покупку лимитированных товаров, бронирование, голосование, выдачу промокодов. Злоумышленник ботом выгребает всё.

**Примеры:** боты скупают лимитированные кроссовки, накрутка голосов, массовая генерация промокодов, автоматическое бронирование, парсинг данных.

**Как найти:**
- Найти бизнес-процессы с ценностью (покупка, голосование, бронь, регистрация)
- Проверить: есть ли защита от автоматизации (CAPTCHA, device fingerprint)
- Проверить лимиты: сколько раз можно выполнить операцию
- Запустить скрипт: N операций подряд – заблокирует ли
- Проверка rate limit на «ценных» эндпоинтах

**Как защищаться:**
- CAPTCHA (reCAPTCHA, hCaptcha) для публичных «ценных» операций
- Device fingerprinting + поведенческий анализ (аномалии)
- Лимиты на операцию: на пользователя, на IP, на устройство
- Многофакторные проверки для ценных процессов
- Мониторинг: аномальные паттерны (одна цель, много аккаунтов)
- Human-in-the-loop: подтверждение (email/SMS) для подозрительных

**Дополнения:** новинка 2023. Это про борьбу с ботами и фрод, а не про классические уязвимости. Связано с A04 (Insecure Design) в веб-Top 10.

## 🌐 API7:2023 – Server Side Request Forgery (SSRF)

**Что это:** API по указанию пользователя делает запросы на произвольные URL. Атакующий заставляет сервер обращаться к внутренним ресурсам: localhost, внутренняя сеть, метаданные облака (169.254.169.254 → кража IAM-токена).

**Примеры:** загрузка изображения по URL, импорт по ссылке, вебхуки, проверка URL, парсинг RSS/OG.

**Как найти:**
- Найти все места с вводом URL (импорт, загрузка по ссылке, webhook)
- Подать: `http://localhost`, `http://127.0.0.1`, `http://169.254.169.254/latest/meta-data/`, внутренние IP (10.x, 192.168.x)
- Наблюдать ответ/ошибки/тайминги; blind-SSRF через Burp Collaborator/Interactsh
- Проверить обработку redirect-ов

**Как защищаться:**
- Allowlist схем и доменов (только https, только свои домены)
- Запрет внутренних адресов: localhost, private-диапазоны, link-local, metadata (169.254.169.254)
- DNS-резолв + проверка IP после резолва (защита от DNS-rebinding)
- Egress-фильтрация: исходящие запросы через прокси/firewall в отдельной сети
- Запрет redirect-ов
- Не отдавать содержимое внутренних ответов клиенту

**Дополнения:** в веб-Top 10 2025 SSRF вынесен в отдельный A10 – признание важности. В облаке особенно критичен (IAM-токены).

## 🛠️ API8:2023 – Security Misconfiguration

**Что это:** небезопасные настройки API: CORS «*», verbose-ошибки, лишние методы, дефолтные конфиги, отсутствие security-заголовков, неправильная аутентификация по умолчанию.

**Примеры:** CORS `Access-Control-Allow-Origin: *` с credentials, стектрейсы в ответах, включённые TRACE/OPTIONS, дефолтные ключи, неправильные заголовки кэша (чужие данные в кэше), открытая документация API.

**Как найти:**
- Проверка CORS: заголовки в ответах, тест cross-origin запросов
- Вызов с неверными данными – что в ошибке (стектрейс?)
- Сканеры: ZAP, nuclei (CORS, headers, методы)
- Проверка: OPTIONS – какие методы разрешены
- Проверка кэша: Cache-Control на чувствительных ответах
- Аудит конфига: дефолтные ключи, debug-режим

**Как защищаться:**
- CORS: точный allowlist origin, без «*» при credentials
- Единый формат ошибок без внутренних деталей (trace ID вместо стектрейса)
- Отключить лишние методы и функции
- Security-заголовки: CSP, HSTS, X-Content-Type-Options, Cache-Control: no-store
- Hardening-базлайны (CIS), сканы конфигурации (Checkov, tfsec)
- Скрывать/защищать документацию API (Swagger) в проде

**Дополнения:** самая «легко находимая» категория: часто закрывается автоматизацией. В веб-Top 10 – A05.

## 📚 API9:2023 – Improper Inventory Management

**Что это:** неправильное управление инвентарём API: забытые/устаревшие версии API, недокументированные эндпоинты, тестовые/старые версии с уязвимостями, зоопарк интеграций без каталога.

**Примеры:** `/api/v1` устарел, но работает с дырами; `/api/test`, `/api/beta`, shadow API; документация не соответствует реальности; нет инвентаря всех эндпоинтов и их версий.

**Как найти:**
- Fuzzing путей: /api/v1, /api/v2, /api/test, /api/dev, /swagger, /docs
- Сравнение документации с реальными эндпоинтами
- Поиск скрытых эндпоинтов: dirsearch/ffuf по словарям
- Анализ мобильного приложения: вытащить все API-вызовы (Burp/из кода)
- Проверка версий: старые версии без патчей

**Как защищаться:**
- Полный инвентарь API: все эндпоинты, версии, владельцы, статус (каталог API)
- Жизненный цикл версий: deprecation-политика, сроки вывода, удаление старых
- Отключать/удалять неиспользуемые эндпоинты и окружения (test/dev не в проде)
- Документация в актуальном состоянии (OpenAPI), автоматическая генерация
- Мониторинг: обнаружение новых/неизвестных эндпоинтов
- Закрывать shadow API (забытые бэкенды, старые микросервисы)

**Дополнения:** «невидимая» категория: о ней вспоминают при атаках через забытые эндпоинты. Связано с SBOM и управлением активами.

## 🔗 API10:2023 – Unsafe Consumption of APIs

**Что это:** приложение небезопасно потребляет сторонние API (платёжные, карты, гео, соцсети): не проверяет данные, доверяет ответам, нет таймаутов, слабая аутентификация к третьим сторонам, утечка данных наружу.

**Примеры:** доверие ответу платёжного API без валидации (подделка суммы), передача PII сторонним сервисам без контроля, нет таймаутов (зависание), хранение ключей от сторонних API в коде, инъекции через данные от третьих сторон.

**Как найти:**
- Аудит интеграций: какие сторонние API используются, что им передаётся
- Проверка валидации ответов: подменить ответ (Burp) – примет ли
- Проверка таймаутов и обработки ошибок при недоступности стороннего сервиса
- Поиск ключей/токенов сторонних сервисов в коде (секрет-скан)
- Проверка: уходит ли лишний PII наружу (трафик-анализ)

**Как защищаться:**
- Валидировать ответы сторонних API (схемы, суммы, типы)
- Верифицировать цепочку доверия: mTLS, подписи ответов
- Таймауты, retry с ограничениями, изоляция сбоев (circuit breaker)
- Секреты сторонних сервисов – в Vault, не в коде
- Минимизация данных наружу: передавать только необходимое
- Whitelist доменов исходящих запросов, egress-контроль

**Дополнения:** «outbound»-сторона API-безопасности (все остальные – inbound). Связано с A06/A08 (компоненты и целостность) в веб-Top 10.

## 🧠 Итог

- **API1 (BOLA)** и **API2 (Auth)** – самые частые: проверяй первыми
- **API3 (mass assignment)** – особенность API: не принимай лишние поля
- **API4, API6** – про лимиты и ботов: rate limit + анти-автоматизация
- **API5 (BFLA)** – ролевые проверки на каждый эндпоинт
- **API7 (SSRF)** – критичен в облаке (IAM-токены)
- **API8** – автоматизация: конфиг-сканы
- **API9, API10** – про инвентарь и сторонние интеграции: порядок и контроль

**Связь с другими стандартами:** API1/API5 → ASVS V4 (Access Control), API2 → ASVS V2/V3, API3 → ASVS V5.3, API7 → веб-A10 (SSRF), API8 → веб-A05. Для общих веб-рисков смотри OWASP Top 10 (2025).
