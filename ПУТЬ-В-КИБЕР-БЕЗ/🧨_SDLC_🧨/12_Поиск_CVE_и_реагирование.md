# Как искать новые CVE и как реагировать на их появление

### 12.1 Где искать новые CVE

1. **NVD (National Vulnerability Database, nvd.nist.gov)** – официальная база NIST, обогащает CVE данными (CVSS, CWE, references)
2. **CVE.org (cve.org)** – официальный реестр CVE Program (MITRE)
3. **GitHub Advisory Database** – уязвимости в open-source (github.com/advisories)
4. **OSV.dev** – открытый реестр (Google), агрегирует базы
5. **Vulners, Exploit-DB, NVD feed** – агрегаторы и эксплойты
6. **Vendor advisories** – бюллетени производителей (Microsoft Security Response Center, Apache, Red Hat, Docker)
7. **БДУ ФСТЭК России (bdu.fstec.ru)** – российский банк данных угроз и уязвимостей
8. **NIST CPE feeds, RSS-подписки** – автоматизация мониторинга
> **БДУ** – Threat Data Bank (банк данных угроз (ФСТЭК))

> **ФСТЭК** – Federal Service for Technical and Export Control (Федеральная служба по техническому и экспортному контролю)

> **OSV** – Open Source Vulnerabilities (открытая база уязвимостей открытого ПО (Google))

> **MITRE** – (некоммерческая организация, управляющая реестром CVE) (организация-оператор реестра CVE)

> **NIST** – National Institute of Standards and Technology (Национальный институт стандартов и технологий (США))

> **NVD** – National Vulnerability Database (национальная база данных уязвимостей (США, NIST))

> **CVSS** – Common Vulnerability Scoring System (общая система оценки критичности уязвимостей (0-10))

> **CWE** – Common Weakness Enumeration (общий перечень слабостей (типов уязвимостей))

> **CVE** – Common Vulnerabilities and Exposures (общие уязвимости и факторы воздействия (реестр известных уязвимостей))


### 12.2 Как автоматизировать мониторинг

- **RSS/Atom подписки** на NVD, vendor advisories
- **NVD API (nvd.nist.gov/developers)** – программный доступ
- **GitHub Dependabot / Renovate** – автоматические алерты об уязвимых зависимостях в репозиториях
- **Trivy/Snyk/Grype в CI** – сканирование на каждой сборке
- **Сервисы threat intelligence:** Recorded Future, Vulners, CVE feeds в SIEM
> **SIEM** – Security Information and Event Management (управление событиями и информацией о безопасности)

> **API** – Application Programming Interface (программный интерфейс приложения)


**Пример NVD API:**
```bash
curl "https://services.nvd.nist.gov/rest/json/cves/2.0?keywordSearch=log4j"
```

### 12.3 Как реагировать на новую CVE (процесс)

**Пример: выход критичной CVE (как Log4Shell CVE-2021-44228):**

1. **Обнаружение (Detection)**
   - Мониторинг каналов, алерт от SCA-сканера
   - Определить: затрагивает ли наш стек?
> **SCA** – Software Composition Analysis (анализ состава программного обеспечения)


2. **Оценка воздействия (Triage)**
   - Какие компоненты/сервисы используют уязвимую библиотеку?
   - По **SBOM** определить затронутые артефакты за минуты
   - Оценить: эксплуатируется ли извне? Есть ли PoC/активная эксплуатация?
> **PoC** – Proof of Concept (доказательство концепции (работоспособности эксплойта))

> **SBOM** – Software Bill of Materials (ведомость (спецификация) состава программного обеспечения)


3. **Приоритизация (Prioritize)**
   - CVSS-оценка + EPSS + бизнес-контекст
   - Критично: интернет-facing сервисы с уязвимым компонентом
> **EPSS** – Exploit Prediction Scoring System (система прогнозирования вероятности эксплуатации уязвимостей)


4. **Реагирование (Response)**
   - **Немедленно:** временные контрмеры (WAF-правила, блокировка, отключение функции)
   - **Патч:** обновить библиотеку до исправленной версии (2.17.0 для Log4j)
   - **Митигация:** если патча нет – обходные меры (конфигурация, firewall)
> **WAF** – Web Application Firewall (межсетевой экран для веб-приложений)


5. **Верификация (Verify)**
   - Пересканировать (SCA/SAST), убедиться, что CVE ушла
   - Проверить, что не было эксплуатации (логи, EDR)
> **EDR** – Endpoint Detection and Response (обнаружение и реагирование на конечных точках)

> **SAST** – Static Application Security Testing (статическое тестирование безопасности приложений)


6. **Пост-анализ и документирование**
   - Записать в runbook, обновить SBOM, разобрать причины (почему зависимость была уязвимой)

**Runbook реагирования (шаблон):**
```
1. Подтвердить CVE и affected versions
2. Найти затронутые сервисы (SBOM/SCA)
3. Оценить эксплуатируемость (external? auth? PoC?)
4. Определить SLA реакции (Critical: 24-48ч на фикс)
5. Временные контрмеры -> патч -> верификация
6. Отчёт и пост-мортем
```

## 📎 Пример: Runbook реагирования на новую CVE (шаблон)

> Это готовый документ-инструкция, который можно распечатать/повесить.
> Заполняется при появлении критичной CVE (например, Log4Shell).

```markdown
# RUNBOOK: Реагирование на критичную CVE

CVE: ______________ | Severity: ______________ | Дата: ______________
Продукт: ______________ | Версии: ______________ | Fixed: ______________

## Шаг 1. Подтверждение (первые 15 минут)
- [ ] Прочитать advisory (ссылка: ______________)
- [ ] Подтвердить, что CVE затрагивает наш стек (версии совпадают?)
- [ ] Определить severity (CVSS) и эксплуатируемость (EPSS, есть ли PoC)
- Ответственный: AppSec on-call

## Шаг 2. Инвентаризация (первые 1-2 часа)
- [ ] Найти затронутые сервисы через SBOM:
      grep/jq по sbom-*.json
- [ ] Найти затронутые репозитории через SCA (Trivy/Dependabot)
- [ ] Определить, какие сервисы доступны извне (internet-facing)
- [ ] Составить список: сервис | версия | окружение | владелец
- Ответственный: AppSec + DevOps

## Шаг 3. Приоритизация
| Сервис | Эксплуатируем извне? | Данные | Риск | Очередь |
|--------|----------------------|--------|------|---------|
| api-gateway | ДА | все | Критический | 1 |
| auth-service | ДА | ПДн | Критический | 2 |
| worker | НЕТ | внутр. | Средний | 3 |

## Шаг 4. Реагирование
- [ ] Временные контрмеры (WAF-правило, блокировка endpoint, firewall):
      команда: ______________
- [ ] Патч: обновить до версии ______________
- [ ] Если патча нет - митигация (конфиг, отключение функции)
- [ ] Пересобрать и пересканировать (SCA = 0 Critical)
- Ответственный: владелец сервиса + DevOps

## Шаг 5. Верификация
- [ ] Пересканировать: trivy image ... (CVE ушла?)
- [ ] Проверить логи/EDR на признаки эксплуатации (до патча)
- [ ] Мониторинг алертов (24 часа после фикса)

## Шаг 6. Пост-мортем (в течение недели)
- [ ] Почему зависимость была уязвимой? (не обновляли? не сканировали?)
- [ ] Что улучшить: автообновление? SCA в CI? SBOM для всех сервисов?
- [ ] Завести задачи на улучшения
```

## 📎 Каналы мониторинга новых CVE (список)

| Канал | Что даёт | Как подписаться |
|-------|----------|-----------------|
| NVD (nvd.nist.gov) | Все CVE + CVSS + CWE | RSS, API |
| CVE.org | Официальный реестр | RSS |
| GitHub Advisory DB | Уязвимости OSS | Alerts в репо |
| OSV.dev | Агрегатор баз | API, RSS |
| БДУ ФСТЭК (bdu.fstec.ru) | Российская база | RSS, ручная проверка |
| Vendor advisories | Apache, Microsoft, Red Hat... | Рассылки |
| Exploit-DB / Metasploit | PoC/эксплойты | RSS (для оценки риска) |
| CISA KEV | Активно эксплуатируемые | JSON feed (cisa.gov/kev) |
