# Формирование требований безопасности к проекту

> Полное руководство: см. остальные файлы в папке SDLC


**Зачем нужны требования безопасности:** без них разработчики не знают, что строить, а тестировщики – что проверять. Требования – это фундамент SSDLC.
> **SSDLC** – Secure Software Development Life Cycle (безопасный жизненный цикл разработки программного обеспечения)


**Откуда берутся требования:**
1. **Регуляторные** – ФЗ-152, ГОСТы, PCI DSS, GDPR, отраслевые стандарты
2. **Бизнес-требования** – что нельзя потерять/сломать (данные, деньги, репутация)
3. **Технические** – архитектура, технологии, интеграции
4. **Из threat modeling** – выявленные угрозы порождают требования-контрмеры
> **ФЗ-152** – Federal Law No. 152 «On Personal Data» (федеральный закон №152 «О персональных данных»)

> **PCI DSS** – Payment Card Industry Data Security Standard (стандарт безопасности данных индустрии платёжных карт)

> **GDPR** – General Data Protection Regulation (Общий регламент по защите данных (ЕС))


**Как формировать security-требования (пошагово):**
1. **Определить данные** – какие данные обрабатывает система? Персональные? Платёжные? Медицинские? Это определяет уровень защиты.
2. **Определить активы** – что ценно: БД, ключи, исходники, пользователи?
3. **Классифицировать данные** – публичные / внутренние / конфиденциальные / секретные
4. **Определить регуляторные требования** – подпадает ли система под ФЗ-152, ГОСТ Р 57580, PCI DSS?
5. **Провести threat modeling** – какие угрозы актуальны?
6. **Сформулировать требования** – каждое требование должно быть измеримым и проверяемым
7. **Добавить в acceptance criteria** – чтобы разработчик не мог закрыть задачу без выполнения требований
> **БД** – Database (база данных)

> **ГОСТ** – State Standard (государственный стандарт (РФ))


**Примеры формулировок security-требований:**
- "Все пароли хранятся только в виде хэшей (bcrypt/argon2), plaintext запрещён"
- "Вся передача данных – только по TLS 1.2+"
- "Доступ к админ-функциям только для роли admin с MFA"
- "Логирование событий аутентификации и авторизации обязательно"
- "Зависимости сканируются SCA, критические CVE блокируют релиз"
- "Секреты (ключи, пароли) не хранятся в коде и git-истории"
> **MFA** – Multi-Factor Authentication (многофакторная аутентификация)

> **TLS** – Transport Layer Security (протокол безопасности транспортного уровня)

> **CVE** – Common Vulnerabilities and Exposures (общие уязвимости и факторы воздействия (реестр известных уязвимостей))

> **SCA** – Software Composition Analysis (анализ состава программного обеспечения)


**Требования должны быть SMART:**
- **S**pecific – конкретные
- **M**easurable – измеримые
- **A**chievable – достижимые
- **R**elevant – релевантные
- **T**ime-bound – с привязкой к срокам

## 📎 Пример: конкретный файл требований безопасности (шаблон)

> Документ: `Security_Requirements_ShopApp.md` – требования безопасности
> Проект: **интернет-магазин** (каталог, корзина, оплата, личный кабинет, ПДн клиентов).

```markdown
# Требования безопасности интернет-магазина "ShopApp"

Версия: 1.2 | Статус: утверждено | Владелец: AppSec-инженер
Соответствие: ФЗ-152, ГОСТ Р 57580 (частично), PCI DSS (для оплат)

## 1. Классификация данных
| Данные                 | Класс        | Где хранятся              |
|------------------------|--------------|---------------------------|
| ФИО, email, телефон    | ПДн          | БД клиентов               |
| Адрес доставки         | ПДн          | БД клиентов               |
| Номер карты, CVV       | Платёжные    | НЕ храним (только через ПС)|
| Пароли                 | Секретные    | Хэш bcrypt/argon2         |
| История заказов        | Конфиденц.   | БД заказов                |

## 2. Требования аутентификации и авторизации
- SEC-001: Пароли хранить только как bcrypt/argon2 (не plaintext, не MD5)
- SEC-002: Многофакторная аутентификация (MFA) для админов
- SEC-003: JWT access-token (TTL 15 мин) + refresh-token (ротация)
- SEC-004: Блокировка аккаунта после 5 неудачных попыток входа
- SEC-005: Доступ к админ-панели только из белого списка IP + MFA
- SEC-006: Проверка прав (authorization) на КАЖДОМ запросе к API (анти-IDOR)

## 3. Требования к данным и криптографии
- SEC-010: Передача данных только по TLS 1.2+
- SEC-011: Шифрование ПДн в БД (AES-256) для особых категорий
- SEC-012: Ключи шифрования в KMS/менеджере секретов, не в коде
- SEC-013: Логи не содержат ПДн и платёжные данные (маскирование)

## 4. Требования к приложению
- SEC-020: Валидация ВСЕХ входных данных (серверная, не только клиентская)
- SEC-021: Использовать параметризованные SQL-запросы (запрет конкатенации)
- SEC-022: Заголовки безопасности: CSP, HSTS, X-Frame-Options, X-Content-Type-Options
- SEC-023: Rate limiting: /login (5/мин), /api (100/мин на пользователя)
- SEC-024: Обработка ошибок без раскрытия деталей (не показывать стек-трейсы)

## 5. Требования к зависимостям
- SEC-030: SCA-сканирование в CI, блокировка при Critical CVE
- SEC-031: SBOM на каждую сборку (CycloneDX)
- SEC-032: Обновление зависимостей не реже 1 раза в месяц

## 6. Требования к логированию и мониторингу
- SEC-040: Логировать: входы, выходы, смену пароля, оплаты, админ-действия
- SEC-041: SIEM/алерты на подозрительную активность (брутфорс, массовый экспорт)
- SEC-042: Хранение логов >= 6 месяцев

## 7. Требования к деплою и инфраструктуре
- SEC-050: DEBUG=false в проде, отдельные окружения dev/stage/prod
- SEC-051: Секреты через переменные окружения/хранилище секретов
- SEC-052: Образы сканируются (Trivy), запуск от non-root
- SEC-053: Резервное копирование БД шифрованное

## 8. Соответствие ФЗ-152
- SEC-060: Политика обработки ПДн опубликована
- SEC-061: Согласие на обработку ПДн запрашивается и хранится
- SEC-062: Уведомление Роскомнадзора об обработке ПДн
- SEC-063: Ответственный за обработку ПДн назначен
- SEC-064: Обеспечены права субъекта (доступ, удаление, исправление)

## 9. Acceptance criteria (как проверить)
| Требование | Как проверить |
|------------|---------------|
| SEC-001 | Проверить БД: пароли в виде $2b$... (bcrypt) |
| SEC-003 | Перехватить трафик: JWT с exp 15 мин |
| SEC-006 | Изменить id в запросе: чужой объект недоступен |
| SEC-020 | Отправить вредоносный payload: отклонён сервером |
| SEC-030 | Запустить SCA: 0 Critical |
```

## 📎 Пример: user story с security acceptance criteria

```markdown
# User Story: US-42 "Смена пароля"

**Как** зарегистрированный пользователь,
**я хочу** сменить пароль,
**чтобы** защитить аккаунт при компрометации.

## Функциональные критерии
- Пользователь вводит старый пароль, новый + подтверждение
- После смены - выход из всех сессий

## Security Acceptance Criteria
- [ ] Новый пароль проверяется на сложность (мин 8 символов, буквы+цифры)
- [ ] Старый пароль проверяется перед сменой
- [ ] Пароль хранится как bcrypt
- [ ] Токены сессий инвалидируются после смены
- [ ] Событие логируется (user_id, IP, время)
- [ ] Rate limiting на endpoint смены пароля
- [ ] Нет раскрытия информации в ответе (не "пароль неверный" vs "юзер не найден")
```
