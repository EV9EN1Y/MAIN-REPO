### 🎯 Этап 0: Подготовка и разведка (Pre-engagement & Reconnaissance)

**Цель:** Понять, _что_ мы тестируем, прежде чем искать, _как_ его сломать.

1. **Определить границы (Scope):**
    
    - **iOS-приложение:** Meetway.app (бинарник, файлы `.ipa`).
        
    - **Бэкенд:** API на `api.meetway.yandexcloud.net` (или ваш домен).
        
    - **Инфраструктура:** Сервисы Yandex Cloud (YDB, YCF, Object Storage).
        
2. **Соберить информацию:**
    
    - **Для приложения:** Какие библиотеки использует? Есть ли чувствительные данные в коде? (`strings` команда, `MobSF`).
        
    - **Для API:** Карта всех эндпоинтов (`/auth`, `/users`, `/chats`, `/posts`). Используйте `Burp Suite` или `OWASP Amass`.
        
    - **Документация:** Есть ли API docs (Swagger/OpenAPI)?.
        



### 🗺️ Этап 1: Моделирование угроз (Threat Modeling)

**Цель:** Системно найти, _где_ могут быть уязвимости, до начала тестов. Использовать методику **STRIDE**.

- **S (Spoofing) – Подмена:** Как проходит аутентификация (Yandex ID/OAuth)? Можно ли подделать JWT-токен?
    
- **T (Tampering) – Изменение данных:** Можно ли изменить чужое сообщение, пост или профиль? (Проверка на отсутствие контроля доступа).
    
- **R (Repudiation) – Отказ от действий:** Ведутся ли логи действий пользователя? Можно ли удалить следы?
    
- **I (Information Disclosure) – Раскрытие информации:** Что хранится в локальной БД iOS (CoreData/Keychain)? Передаются ли данные в API в открытом виде?
    
- **D (Denial of Service) – Отказ в обслуживании:** Есть ли эндпоинты, которые могут "положить" сервер тяжелым запросом (например, загрузка файла)?
    
- **E (Elevation of Privilege) – Повышение привилегий:** Может ли обычный пользователь стать администратором?
    

> **Результат:**  Создать файл threat-model.md  с диаграммами и списком рисков. Это карта для атаки.

### 🔍 Этап 2: Динамическое тестирование (Dynamic Testing)

**Цель:** Проверить работающее приложение "извне". **Начать с самого критичного – аутентификации и управления сессиями.**

1. **Аутентификация и сессии (OWASP TOP 10: A2, A7):**
    
    - Механизм входа через Yandex ID/OAuth. Можно ли обойти?
        
    - JWT-токены: где хранятся (iOS Keychain)? Можно ли подделать (проверка алгоритма подписи)?
        
    - Выход из системы (logout): действительно ли уничтожается сессия?
        
2. **Контроль доступа (OWASP TOP 10: A1 – Брокен Access Control):**
    
    - **Горизонтальный:** Может ли пользователь A получить доступ к чатам/постам пользователя B? (**IDOR** — самая частая находка).
        
    - **Вертикальный:** Может ли пользователь получить доступ к админ-функциям (`/admin/...`)?
        
3. **Ввод пользователя и инъекции (OWASP TOP 10: A3):**
    
    - **SQLi:** Зная эндпоинты, ищием их в параметрах запросов (`.cloud.yandex.net/db?query=SELECT...`).
        
    - **XSS:** Поля ввода в чатах, постах, комментариях.
        
    - **Командная инъекция:** Если есть функционал "системных уведомлений" от админа.
        
4. **Безопасность API:**
    
    - Лишняя информация в ответах (например, пароли в JSON).
        
    - Отсутствие лимитов на запросы (rate limiting).
        
    - Неправильные настройки CORS.
        

### 📱 Этап 3: Мобильная безопасность (Mobile Security)

**Цель:** Проверить клиентскую часть.

1. **Анализ бинарника:**
    
    - **Дизассемблирование:** Есть ли хардкодные ключи/пароли в коде?
        
    - **Защита от реверс-инжиниринга:** Есть ли обфускация?
        
2. **Анализ хранения данных:**
    
    - Что хранится в `UserDefaults`? (Часто там токены).
        
    - Корректно ли используется Keychain для чувствительных данных?
        
3. **Межпроцессное взаимодействие (IPC):** Проверка кастомных URL-схем (`meetway://`).
    

### ☁️ Этап 4: Инфраструктура и облако (Cloud & Infrastructure)

**Цель:** Проверить окружение.

- **Yandex Cloud Functions:** Доступны ли логи? Не записывают ли они чувствительные данные?
    
- **Yandex Database (YDB):** Доступна ли БД из публичного интернета? Сильные пароли?
    
- **Object Storage:** Доступны ли файлы пользователей (аватары, вложения) напрямую по публичной ссылке? Можно ли загрузить исполняемый файл?
    

### 📝 Этап 5: Документирование (Reporting)

**Цель:** Сделать выводы, которые можно показать работодателю.

- **Для каждой найденной уязвимости** создать файл по шаблону: `уязвимость-тип_дата.md`(например, `idor-profile-read_2024-03-15.md`).
    
- **Структура отчёта:**
    
    1. **Название уязвимости** (например, "IDOR в эндпоинте `/api/v1/chats/{chat_id}`").
        
    2. **Критичность** (Critical/High/Medium/Low).
        
    3. **Описание и сценарий воспроизведения** (шаг за шагом).
        
    4. **Proof of Concept (PoC):** Скриншоты, видео, curl-запросы.
        
    5. **Риск:** Чем опасна эта уязвимость? (Раскрытие данных, порча данных и т.д.).
        
    6. **Рекомендации по исправлению** (например, "Добавить проверку прав пользователя на уровне бизнес-логики").
        
    7. **Ссылки:** CWE, OWASP.
