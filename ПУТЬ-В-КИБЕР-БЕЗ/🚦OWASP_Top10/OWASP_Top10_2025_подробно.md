# OWASP Top 10 – 2025 (веб-приложения)

Версия: 2025 | Источник: https://owasp.org/Top10 | Дата: 04.08.2026

> OWASP Top 10 – список 10 самых критичных рисков безопасности веб-приложений. Обновляется раз в ~3-4 года. Актуальная версия – **2025**.

---

## ( OWASP Top 10 – 2025)

1. **A01:2025 – Broken Access Control** – нарушенный контроль доступа
2. **A02:2025 – Cryptographic Failures** – сбои криптографии
3. **A03:2025 – Injection** – инъекции
4. **A04:2025 – Insecure Design** – небезопасный дизайн
5. **A05:2025 – Security Misconfiguration** – небезопасная конфигурация

7. **A07:2025 – Identification and Authentication Failures** – сбои идентификации и аутентификации
8. **A08:2025 – Software and Data Integrity Failures** – сбои целостности ПО и данных
9. **A09:2025 – Logging and Monitoring Failures** – сбои логирования и мониторинга
10. **A10:2025 – Server-Side Request Forgery (SSRF)** – подделка серверных запросов

## 🔍 A01:2025 – Broken Access Control (Нарушенный контроль доступа)

**Что это:** пользователь может получить доступ к данным/функциям, на которые у него нет прав. Самая частая и опасная категория.

**Примеры:** IDOR (подмена ID чужого объекта), повышение привилегий, обход проверок прав, доступ к чужим ресурсам, missing function-level access control (пользователь дёргает админский эндпоинт).

**Как найти:**
- Проверить каждый эндпоинт с ID-параметром: подменить свой ID на чужой (IDOR)
- Перебирать роли: дёргать админ-эндпоинты обычным пользователем
- Автоматизация: Burp (Authorized/Unauthorized сканирование), ZAP
- Проверка на уровне UI: скрыть кнопку ≠ защита (проверять API напрямую)
- Тестировать все HTTP-методы (GET/POST/PUT/DELETE) к одному URL

**Как защищаться:**
- Проверка прав на **каждом** запросе на сервере (deny by default)
- Объектные проверки владения (ownership) – не доверять ID из запроса
- Использовать непредсказуемые ID (UUID вместо инкрементальных)
- Следовать OWASP ASVS V4 (Access Control), NIST SP 800-63B
- Тесты: негативные сценарии доступа в CI/CD

**Дополнения:** BOLA/IDOR в API – это API1 в API Top 10. Разделение «доступ к функции» (BOLA) и «доступ к объекту» (BFLA).

## 🔐 A02:2025 – Cryptographic Failures (Сбои криптографии)

**Что это:** слабая/отсутствующая криптография: данные передаются или хранятся незашифрованными, используются слабые алгоритмы, плохое управление ключами. Раньше называлась «Sensitive Data Exposure».

**Примеры:** пароли в открытом виде, HTTP вместо HTTPS, слабые хэши (MD5/SHA1), короткие ключи, хранение PII в plaintext, нет шифрования at rest.

**Как найти:**
- Сканирование трафика: Burp/ZAP, mitmproxy – искать plaintext PII
- Проверка хранилищ: БД, бэкапы, файлы – искать открытые данные
- Сканеры: OWASP ZAP, nuclei, sslscan (слабые TLS)
- Аудит кода: поиск хэшей/шифрования (Semgrep-правила)
- Проверка TLS: SSL Labs (целевой уровень A+)

**Как защищаться:**
- Классифицировать данные (PII, финансы, здоровье) и применять шифрование по классу
- Шифровать при передаче (TLS 1.2+) и хранении (AES-256)
- Пароли: только argon2id/bcrypt/scrypt с солью
- Не хранить лишние данные (минимизация), маскировать в логах
- Ключи: управление жизненным циклом (генерация, ротация, хранение в HSM/Vault)

**Дополнения:** сюда же: слабые алгоритмы (DES, RC4, ECB-режим), отсутствие forward secrecy, устаревшие TLS-версии (1.0/1.1). См. OWASP ASVS V6 (Cryptography), V9 (Communications).

## 💉 A03:2025 – Injection (Инъекции)

**Что это:** вредоносный код/данные вставляются в интерпретатор (SQL, NoSQL, OS-команды, LDAP, XPath). Классика: SQL-инъекции.

**Примеры:** SQLi (классическая, blind, time-based), NoSQLi, command injection, LDAP injection, XXE.

**Как найти:**
- Автоматически: SQLMap, Burp Scanner, ZAP, nuclei
- Ручные тесты: ввод спецсимволов `' " OR 1=1 --` и наблюдение за ошибками/поведением
- Blind: time-based (`sleep(5)`) и boolean-тесты
- DAST на каждый параметр (GET/POST/headers/cookies)
- SAST: Semgrep/CodeQL – поиск конкатенации строк в запросах

**Как защищаться:**
- Параметризованные запросы (prepared statements) – железная защита от SQLi
- ORM с безопасными API
- Валидация ввода: whitelist по типам/длинам/форматам
- Экранирование контекста вывода (output encoding)
- Принцип наименьших привилегий для БД-аккаунтов приложения
- Запрет динамической сборки запросов из пользовательского ввода

**Дополнения:** XXE – инъекция XML, лечится отключением внешних сущностей (DTD). Command injection – через опасные функции (system, exec, shell). OWASP ASVS V5 (Validation).

## 🏗️ A04:2025 – Insecure Design (Небезопасный дизайн)

**Что это:** риски, заложенные в архитектуру и дизайн, а не в код. Недостатки модели угроз, отсутствие «secure by design». Отличается от остальных: лечится на этапе проектирования.

**Примеры:** нет лимитов и квот, доверие клиенту, бизнес-логика с уязвимостями (бесплатные товары, отрицательные суммы), отсутствие защиты от abuse.

**Как найти:**
- Threat modeling (STRIDE) на архитектуре
- Abuse-case тестирование (негативные сценарии использования)
- Проверка бизнес-логики: обходы лимитов, манипуляции ценой/количеством
- Ревью дизайна: где доверяем клиенту, где нет квот
- Тестирование последовательностей операций (многошаговые сценарии)

**Как защищаться:**
- Secure by design: threat modeling на этапе проектирования
- Лимиты и квоты на все ресурсоёмкие/бизнес-операции
- Никогда не доверять клиенту: цены, роли, лимиты – с сервера
- Сегментация, принцип наименьших привилегий
- Использовать шаблоны безопасного дизайна (OWASP SAMM, NIST SSDF)

**Дополнения:** A04 – «неудобная» категория: не ищется сканером, требует мышления. Это про то, ЧТО строится, а не как.

## ⚙️ A05:2025 – Security Misconfiguration (Небезопасная конфигурация)

**Что это:** небезопасные настройки по умолчанию, открытые панели, лишние функции, неправильные заголовки, verbose-ошибки, открытые бакеты.

**Примеры:** дефолтные пароли, CORS «*», раскрытие стектрейсов, включённый directory listing, лишние методы (TRACE), отсутствие security-заголовков (CSP, HSTS).

**Как найти:**
- Сканеры: nuclei, ZAP, Nikto, ScoutSuite (облако)
- Проверка заголовков: SecurityHeaders.com
- Проверка конфигов: серверов (nginx/Apache), фреймворков, облачных сервисов (бакеты, Security Groups)
- Перебор стандартных путей/панелей (dirsearch/ffuf)
- Аудит: отключены ли debug-режимы, лишние порты

**Как защищаться:**
- Hardening-базлайны: CIS Benchmarks, Docker Bench
- Отключить дефолтные аккаунты/пароли, лишние функции и модули
- Правильные security-заголовки: CSP, HSTS, X-Frame-Options, X-Content-Type-Options
- Минимальная конфигурация: закрытые порты, минимальные права
- Автоматизация: IaC-сканы (tfsec, Checkov), регулярные аудиты конфигурации
- Единые ошибки без внутренних деталей

**Дополнения:** сюда же: неправильные разрешения в облаке (S3 bucket public), устаревшие конфиги после обновлений.

## 📦 A06:2025 – Vulnerable and Outdated Components (Уязвимые и устаревшие компоненты)

**Что это:** использование библиотек/фреймворков с известными уязвимостями (CVE). Классика – log4shell (Log4j).

**Примеры:** устаревшие версии библиотек, непатченный софт, зависимости с критичными CVE, отсутствие SCA.

**Как найти:**
- SCA-инструменты: OWASP Dependency-Check, Dependabot, Snyk, Trivy (контейнеры)
- Сверка с базой CVE (NVD)
- Проверка: что реально используется в проде (не только в репо)
- Инвентаризация компонентов (SBOM)

**Как защищаться:**
- SCA на каждом билде, политика: критичные CVE блокируют релиз
- Мониторинг новых CVE (алерты)
- Регулярные обновления: Critical – 7 дней, High – 30
- Удалять неиспользуемые зависимости
- Формировать SBOM и отслеживать цепочку поставок
- Минимизировать поверхность: меньше зависимостей = меньше риска

**Дополнения:** эта категория выросла из-за атак на цепочку поставок. См. также A08 (целостность) и OWASP Dependency-Check.

## 🪪 A07:2025 – Identification and Authentication Failures (Сбои идентификации и аутентификации)

**Что это:** проблемы с логином/сессиями: слабые пароли, отсутствие MFA, перебор, захват сессий, неправильный logout. Раньше называлась «Broken Authentication».

**Примеры:** отсутствие rate limit на логин, слабые пароли, JWT без проверки, фиксированные сессии (session fixation), незащищённый восстановление пароля.

**Как найти:**
- Тест перебора логина (Burp Intruder) – сработает ли rate limit
- Проверка: есть ли MFA, как обрабатываются сессии, TTL
- Анализ JWT: алгоритм (alg=none?), секрет, срок жизни
- Проверка logout: инвалидируется ли сессия
- Проверка восстановления пароля: утечки через ответы

**Как защищаться:**
- MFA (TOTP) – обязательно для админов
- Rate limiting на логин/восстановление (5 попыток/15 мин + CAPTCHA)
- Политика паролей: 8+, проверка по спискам скомпрометированных
- Безопасные сессии: случайные ID, TTL, инвалидация при logout, смена пароля = сброс всех сессий
- JWT: короткий TTL, ротация refresh, правильная проверка подписи
- Не раскрывать, существует ли пользователь (одинаковые ответы)

**Дополнения:** сюда же: «credential stuffing» (использование утечек паролей), session timeouts, «запомнить меня» должно быть безопасным.

## 🔄 A08:2025 – Software and Data Integrity Failures (Сбои целостности ПО и данных)

**Что это:** нарушения целостности кода и данных: недоверенные обновления, десериализация недоверенных данных, отсутствие проверки целостности, CI/CD-компрометация.

**Примеры:** загрузка обновлений по HTTP, десериализация (pickle/Java serialization), недоверенные плагины, отсутствие подписей артефактов.

**Как найти:**
- Проверка цепочки обновлений: HTTPS? Подписи? Проверка?
- Тесты десериализации: подача сериализованных объектов (ysoserial для Java, pickle для Python)
- Аудит CI/CD: кто может менять пайплайн, защита веток
- Проверка подписей зависимостей/артефактов

**Как защищаться:**
- Проверка целостности: подписи, хэши (SHA-256) при получении артефактов
- Только безопасные форматы данных: JSON + schema validation вместо десериализации объектов
- Безопасная десериализация: allowlist классов, или отказ от неё
- Защита CI/CD: подписанные коммиты, code review, секреты в Vault, изоляция раннеров
- Обновления только по безопасным каналам (TLS + подпись)

**Дополнения:** сюда же: supply chain атаки, tampered обновления, незащищённые плагины браузера. Пересекается с A06 (компоненты) и SLSA-фреймворком.

## 📊 A09:2025 – Logging and Monitoring Failures (Сбои логирования и мониторинга)

**Что это:** атаки не обнаруживаются, потому что нет логов/мониторинга/алертов. Невозможно расследование инцидентов.

**Примеры:** нет логов логинов, логи не хранятся, нет алертов на аномалии, чувствительные данные в логах.

**Как найти:**
- Проверка: логируются ли критичные события (логин, смена пароля, админ-действия)
- Проверка хранения: срок, защита от изменения (append-only)
- Проверка алертов: сработают ли на перебор, аномальный трафик
- Поиск PII/секретов в логах

**Как защищаться:**
- Логировать: аутентификация, доступы, ошибки, админ-действия, валидация (OWASP ASVS V7)
- Формат: структурированные логи, trace ID для корреляции
- Защита логов: append-only, доступ по ролям, хранение по политике (не менее 1 года)
- Мониторинг + алерты: аномалии, всплеск ошибок, rate limit срабатывания
- НЕ логировать пароли, токены, OTP, PII (маскирование)
- SIEM/EDR для корреляции

**Дополнения:** без этой категории остальные 9 бессмысленны: атаку не увидят. См. OWASP ASVS V7, NIST SP 800-61.

## 🌐 A10:2025 – Server-Side Request Forgery (SSRF)

**Что это:** приложение по запросу пользователя делает запросы на произвольные URL, атакующий заставляет сервер обращаться к внутренним ресурсам (localhost, метаданные облака 169.254.169.254, внутренние сети).

**Примеры:** импорт по URL, загрузка файла по ссылке, вебхуки, парсинг URL → запрос к метаданным облака → кража IAM-токена.

**Как найти:**
- Найти все места, где вводится URL (загрузка по ссылке, импорт, вебхуки)
- Подать: `http://localhost`, `http://169.254.169.254/...`, `http://192.168.0.1`, DNS-ребinding
- Наблюдать ответы/ошибки/тайминги (blind SSRF)
- Burp Collaborator / Interactsh для blind-детекта

**Как защищаться:**
- Валидация URL: только разрешённые схемы (https) и домены (allowlist)
- Запрет обращения к внутренним адресам: localhost, private-диапазоны, link-local, метаданные облака
- Разрешение DNS и проверка, что IP не внутренний (защита от DNS-rebinding)
- Отдельная сеть/сегмент для исходящих запросов (egress proxy, firewall)
- Запрет redirect-ов при загрузке
- Не возвращать содержимое внутренних ответов пользователю

**Дополнения:** SSRF особенно опасен в облаке: доступ к 169.254.169.254 = кража IAM-кредов. Это A10 в Top 10 2025 и API7 в API Top 10 2023.

## 🧠 Итог

- A01 (Access Control) – самый частый и опасный: проверяй в первую очередь
- A02-A03 – криптография и инъекции: закрываются стандартными практиками + SAST/DAST
- A04 – лечится на этапе дизайна (threat modeling)
- A05-A06 – автоматизация: конфиг-сканы + SCA
- A07 – MFA + rate limit
- A08-A10 – целостность, мониторинг, SSRF: современные атаки (supply chain, облако)

**Связь с другими стандартами:** A01 → ASVS V4, A02 → ASVS V6/V9, A03 → ASVS V5, A07 → ASVS V2/V3, A09 → ASVS V7. Для API смотри отдельно API Security Top 10 (2023).
