## ЗДЕСЬ ТЕОРИЯ К ЛАБАМ ПО ОБМАНУ КЕША [[0_WCD_theory=Cache]]

**Web Cache Deception (WCD)** — это  уязвимость, связанная с **мисконфигурацией (неправильной настройкой) кэша**. Её суть в том, что кэш-сервер неправильно трактует запрос и сохраняет конфиденциальные данные, которые не должен был кэшировать, из-за чего их может получить атакующий.

Ключевая причина уязвимости — **расхождение в обработке URL** между кэш-сервером (например, CDN) и бэкенд-приложением.

### **Распространённость уязвимостей (по данным PortSwigger 2023):**

- 23% веб-приложений имеют ==неправильные Cache-Control== заголовки
Кеш может неправильно определить, _что_ и _на сколько_ ему сохранять, создавая условия для обмана или отравления

- 7% используют `public` для аутентифицированного контента
Грубая ошибка. Заголовок ==`Cache-Control: public`== явно разрешает кешу (включая CDN и прокси) сохранять ответ. Если он установлен для страницы с личным кабинетом или токеном, эта информация может быть доступна другим пользователям

- 41% не используют ==`Vary: Cookie`== для персонализированных ответов
Заголовок `Vary` указывает кешу, какие параметры запроса делают ответы уникальными. Без `Vary: Cookie`кеш может отдать закешированный ответ пользователя А (с его именем и балансом) пользователю Б, если они запрашивают один и тот же URL

### **Известные инциденты:**

1. **Uber (2017)**: Web Cache Deception раскрыл данные пользователей
2. **Facebook (2018)**: Кэширование preview ссылок с access tokens
3. **Multiple Banks (2019-2021)**: Statement PDFs кэшировались в CDN

кэширование  по умолчанию:
- ⚡ **Статический контент** (например, файлы `.css`, `.js`, `.jpg`) обычно **кэшируется**. Эти ресурсы общие для всех и часто не меняются
- 🔒 **Динамический контент** (например, личный кабинет или лента новостей) обычно **не кэшируется**, так как содержит уникальную для каждого пользователя (и часто чувствительную) информацию
------

Существует две основные причины, по которым используется веб-кэш:  
  
1. **Уменьшение времени ожидания** — так как данные по запросу берутся из кэша (который располагается “ближе” к клиенту), требуется меньше времени для получения и отображения контента на стороне клиента. Это делает Веб более отзывчивым (прим. переводчика — “отзывчивым” в контексте быстроты реакции на запрос, а не эмоционально).  
  
2. **Снижение сетевого трафика** — повторное использование контента снижает объем данных, передаваемых клиенту. Это, в свою очередь, экономит деньги, если клиент платит за трафик, и сохраняет низкими и более гибкими требования к пропускной способности канала.

если в кеш есть адреса сайтов (самая минималка) - тогда браузеру не приходится обращаться к DNS

Все виды кэшей обладают определенным набором правил, которые они используют, чтобы определить, когда брать контент из кэша, если он доступен. Некоторые из эти правил установлены протоколами (HTTP 1.0/HTTP 1.1), некоторые — администраторами кэша (пользователями браузера или администраторами прокси).

==общие правила==:  
  
1. Если заголовки ответа сообщают кэшу не сохранять их, он не сохранит.
2. Если запрос авторизованный (authorized) или безопасный (то есть, HTTPS), он не будет закэширован.
3. Кэшированный контент считается “свежим” (то есть, может быть отправлен клиенту без проверки с исходного сервера), если:  
    
    - У него установлено время истечения или другой заголовок, контролирующий время жизни, и он еще не истек.
    - Если кэш недавно проверял контент и тот был модифицирован достаточно давно.
    
    Свежий контент берется непосредственно из кэша, без проверки с сервера.
    
4. Если контент является устаревшим, исходному серверу будет предложено провалидировать его или сообщить кэшу, является ли имеющаяся копия по-прежнему актуальной.
5. При определенных обстоятельствах — например, когда он отключен от сети — кэш может сохранять устаревшие ответы без проверки с исходного сервера.

Если в ответе не присутствует валидатора (`ETag` или `Last-Modified` заголовок), и он не содержит никакой явной информации о свежести, контент, обычно (но не всегда) будет считаться некэшируемым.

# ==Expires==
- истек или нет, изменился или нет (показывает время истечения свежести )
`Expires` особенно хороши для кэширования статических изображений (таких как навигация и кнопки)

Они также полезны для управления кэшированием страниц, которые изменяются регулярно. Если вы обновляете страницу с новостями единоразово около шести часов утра, вы можете установить время истечения для контента на этот час - так кэш будет знать о том, когда необходимо получить свежую копию, без необходимости ручного обновления пользователями с помощью нажатия “Обновить”.

пример
```http
Expires: Fri, 10 Oct 2026 12:35:28 GMT
```

для правильной работы время на всех устройствах должно совпадать
есть спец протоколы [Network Time Protocol, NTP)] которые синхронизируют время.

# ==Cache-Control==
пример

```http
Cache-Control: max-age=3600, must-revalidate
```
Заголовки ответов `Cache-Control` включают:  

- **max-age**=[секунды] - описывает максимальный период времени, в течение которого контент остается свежим. Аналогично `Expires`, эта директива указывает время, относительное моменту запроса, а не абсолютную величину. [секунды] - количество секунд от момента запроса, в течение которых вы хотите, чтобы контент трактовался как свежий.
- 
- **s-maxage**=[секунды] - подобен **max-age**, отличаясь тем, что применяется только к общему кэша (т.е. прокси).
- 
- **public** - помечает авторизованные запросы, как кэшируемые; это нормально, если требуется HTTP-аутентификация, ответы автоматически становятся приватными.
- 
- **private** - позволяет кэшу, который действует для определенного пользователя (т.е. в браузере) хранить ответ; общему кэшу (т.е. прокси) - нет.
- 
- **no-cache** - принуждает кэш отправлять запрос на исходный сервер каждый раз для валидации, прежде чем выдать кэшированную копию. Это полезно, когда необходимо гарантировать, что аутентификация принята во внимание (в сочетании с **public**) или для поддержания жесткой свежести без потери преимуществ кэширования.
- 
- **no-store** - указывает кэшу не сохранять копию контента, ни при каких условиях.
- 
- **must-revalidate** - сообщает кэшу, что он должен подчиниться любой свежей информации, что вы ему предоставляете о контенте. HTTP позволяет кэшу хранить устаревший контент при определенных условиях; упомянув этот заголовок, вы сообщаете кэшу, что вы хотите, чтобы он строго следовал вашим правилам.
- 
- **proxy-revalidate** - подобен **must-revalidate**, кроме того, что применяется только к прокси.


# ==ETag==

это уникальные идентификаторы, которые генерируются сервером и изменяются каждый раз, когда запрашивается контент. Поскольку сервер управляет тем, как сгенерированы `ETag`, кэш может быть уверен в том, что, если `ETag` совпадают по результатам запроса `If-None-Match`, контент действительно совпадает.
Почти все кэши используют время из ==Last-Modified== как валидатор; `ETag` также становятся распространенными.

Большинство современных веб-серверов могут автоматически генерировать и `ETag`, и `Last-Modified` заголовки, чтобы использовать в качестве валидаторов для статического контента (т.е. файлов); вам не придется ничего делать. Однако, они не знают достаточно о динамическом контенте (таком, как ==CGI==, ==ASP==, базы данных сайтов)

# Как заставить браузер кэшировать чувствительные данные

### **1: Неправильная конфигурация Cache-Control*

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=3600  # ОШИБКА: приватные данные в public кэше
Content-Length: 512

{
  "user": "admin",
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9",
  "balance": 10000
}

---
Заголовок public разрешает кэширование в прокси/CDN.
```
**CDN (Content Delivery Network)** [Географически распределенный кеш] — это не один сервер, а глобальная сеть из сотен или тысяч серверов (также называемых _edge-серверами_ или _точками присутствия_). Их главная задача — максимально быстро доставлять контент пользователям по всему миру

### **2: Отсутствие заголовков кэширования**

```http
HTTP/1.1 200 OK
Content-Type: text/html
# Отсутствует Cache-Control!

<html>Личный кабинет пользователя...</html>

-----------

По умолчанию- Браузеры используют эвристическое кэширование (обычно 10% от времени since Last-Modified).
```

### **3: Использование Service Worker без проверок**

```js
// Опасный Service Worker - кэширует всё

  // Нет проверки URL или метода!
  event.respondWith(
    caches.match(event.request)
      .then(response => response || fetch(event.request))
  );
});
```

2) #### **Timing Attacks на кэш**

```js
// Измерение времени загрузки ресурса
function probeCache(url) {
  const start = performance.now();
  return fetch(url, {cache: 'force-cache', mode: 'no-cors'})
    .then(() => performance.now() - start);
}

// Если время < 10ms — ресурс в кэше (уже посещался)
// Если время > 100ms — ресурса нет в кэше
probeCache('https://target.com/private/image.jpg')
  .then(time => console.log('В кэше:', time < 50));
```

# как защитить сайт от атак в векторе кеша?

### **Правильные заголовки Cache-Control**

```http
# Для приватных данных
Cache-Control: private, no-store, no-cache, max-age=0, must-revalidate

# Для публичных статических данных
Cache-Control: public, max-age=31536000, immutable

# Для персонализированного, но кэшируемого контента
Cache-Control: private, max-age=600
Vary: Cookie, User-Agent
```

### **Защита Service Workers**

```js
// Безопасный Service Worker
self.addEventListener('fetch', event => {
  // Никогда не кэшируем API endpoints
  if (event.request.url.includes('/api/') ||
      event.request.url.includes('/private/')) {
    event.respondWith(fetch(event.request));
    return;
  }
  
  // Только GET запросы для статики
  if (event.request.method !== 'GET') {
    event.respondWith(fetch(event.request));
    return;
  }
  
  // Стандартная стратегия "сначала сеть, потом кэш"
  event.respondWith(
    fetch(event.request)
      .catch(() => caches.match(event.request))
  );
});
```

### **HTTP Strict Transport Security (HSTS)**
```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```
Предотвращает downgrade-атаки и cookie hijacking.

### **Content Security Policy (CSP)**

```http

Content-Security-Policy: default-src 'self'; 
                         script-src 'self' 'unsafe-inline';
                         style-src 'self';
                         img-src 'self' data:;
```
Защищает от XSS, которые могут эксплуатировать кэш.

### **Регулярный аудит кэша**

# Проверка заголовков через curl
curl -I https://yoursite.com/private/
# Должно возвращать: Cache-Control: private, no-store

### 💥 Известные инциденты: примеры в реальном мире

**Uber (2017) — классический Web Cache Deception**[](https://portswigger.net/web-security/web-cache-deception)

- **Что произошло**: Исследователи обнаружили, что при запросе к личному профилю с добавлением `.css` в конец URL (например, `/account/profile/style.css`) CDN кешировал ответ, так как видел расширение для статического файла. Основной же сервер игнорировал эту часть и отдавал HTML-страницу профиля.
 
- **Результат**: Злоумышленник мог заставить жертву перейти по такой ссылке, а затем получить её персональные данные (имя, email, телефон) из публичного кеша.
  
---
**Facebook (2018) — утечка через preview ссылок**

- **Что произошло**: Механизм предпросмотра ссылок в Messenger и Facebook использовал access-токен пользователя для доступа к защищенным изображениям. Ответы с этими изображениями (и токенами внутри URL) могли некорректно кешироваться CDN.

- **Результат**: Другие пользователи, запрашивая предпросмотр той же ссылки, могли получить закешированное изображение вместе с токеном первого пользователя, получая временный несанкционированный доступ к его ресурсам.
 
---
**Multiple Banks (2019-2021) — выписки в кеше**

- **Что произошло**: В нескольких банках PDF-файлы с банковскими выписками, генерируемые динамически для конкретного клиента, по ошибке маркировались как кешируемые (`Cache-Control: public`) или не использовали `Vary: Cookie`.
  
- **Результат**: Выписка одного клиента могла оказаться в кеше CDN и быть отдана другому клиенту, который запрашивал выписку по тому же пути (например, `/statements/2025-01.pdf`).
