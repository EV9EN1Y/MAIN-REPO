**WSTG-INFO-06: Identify Application Entry Points** (Выявление точек входа в приложение)

## 1. Описание теста

> Данный тест представляет собой процесс систематического картирования всех возможных точек взаимодействия с веб-приложением. Это не просто "походить по ссылкам", а тщательный анализ каждого HTTP-запроса и ответа, которые мое приложение отправляет и получает. 

> Цель - составить полную карту поверхности атаки: все URL, параметры (в URL, в теле запроса, в заголовках, в cookies), используемые HTTP-методы (GET, POST, PUT, DELETE и другие). Это основа, без которой дальнейшее тестирование будет слепым

В современном мире приложения могут иметь множество скрытых или неочевидных точек входа: параметры в куках, нестандартные заголовки (например, `debug: false`), WebSockets, RESTful-эндпоинты. Важно найти их все до начала активных атак

----
## 2. Для чего делается тест

- чтобы создать **актуальную карту атакующей поверхности** приложения. Без этого я могу пропустить критическую уязвимость. Зная все точки входа, я могу целенаправленно проверять их на инъекции, обход авторизации, логические ошибки и другие проблемы. По сути, это этап "разведки боем", который определяет план моих дальнейших действий

-------

## 3. Цели теста

1. **Идентифицировать все HTTP-методы**, поддерживаемые приложением (GET, POST, PUT, DELETE, PATCH, OPTIONS и др.)
   
2. **Выявить все параметры**, передаваемые приложению в URL (query string), теле запроса (POST-данные), заголовках (включая Cookie) и других частях HTTP-сообщения
   
3. **Обнаружить скрытые поля формы** и другие параметры, не предназначенные для прямого изменения пользователем
   
4. **Задокументировать контекст** каждой точки входа: требует ли она аутентификации, использует ли TLS, является ли частью многошагового процесса
   
5. **Создать базу** (например, в таблице Excel/Google Sheets) всех точек входа для последующего тестирования

-------

## 4. Примеры, демонстрирующие суть теста

**Пример 1: Параметры в разных местах запроса.**  
Запрос на логин:

```http
POST /authenticate.asp?service=login HTTP/1.1
Cookie: SESSIONID=...; CustomCookie=trustedIP=x.x.x.x
user=admin&pass=pass123&nihuiysebe=true&fromtrustIP=true
```

Здесь параметры находятся в трех местах: в строке запроса (`service`), в заголовке Cookie (`SESSIONID`, `CustomCookie`) и в теле запроса (`user`, `pass`, `debug`, `fromtrustIP`). Каждый из них - потенциальная точка для атаки или обхода

**Пример 2: Влияние скрытых параметров**  
На странице оплаты я нахожу скрытое поле:


```html
<input type="hidden" id="price" value="100.00" />
```

Изменяя значение этого параметра через прокси (с `100.00` на `1.00`), я могу попытаться купить товар по заниженной цене

**Пример 3: Нестандартные заголовки**  

Сервер возвращает заголовок `Server: BIG-IP`. Это говорит о том, что сайт находится за балансировщиком нагрузки F5. Это может быть важно, если я ищу уязвимости, специфичные для этой платформы, или пытаюсь обойти балансировку для доступа к конкретному бэкенд-серверу

#  Как выполнять тест 

 Главный инструмент - **прокси-сервер**(Burp Suite или OWASP ZAP)

### Шаг 1: Настройка и обход приложения

1. **Настраиваю прокси:** Убеждаюсь, что мой браузер настроен на использование Burp/ZAP, и что прокси перехватывает трафик (или хотя бы логирует его)

если нужно - обход ssl pinning


   
2. **Полный обход (Spidering/Crawling):** Начинаю использовать приложение как обычный пользователь. Прохожу по всем основным функциям: регистрация, логин, просмотр профиля, поиск, добавление товаров в корзину, оформление заказа, выход. **Цель:** заставить приложение генерировать как можно больше различных запросов, чтобы прокси их записал


   
3. **Ручное исследование:** Особое внимание уделяю "неочевидным" местам: формы с выпадающими списками, кнопки, которые ведут на разные страницы в зависимости от состояния (например, "Редактировать" и "Просмотреть")
   
4. **Использование паука:** Запускаю встроенный "паук" (Spider) в Burp/ZAP, чтобы автоматически обойти все ссылки, найденные на страницах
   можно использовать паука urlmap - вот пример в файле [[URL-map]]

--------


### Шаг 2: Анализ HTTP-запросов

Теперь я изучаю лог запросов в прокси. Меня интересует каждый запрос.

**Что я анализирую:**

- **Метод:** GET, POST, PUT, DELETE, PATCH, OPTIONS. Отмечаю все, кроме стандартных GET и POST
   
- **URL и Query String:** Записываю URL и все параметры после `?` (например, `?id=5&action=edit`)
   
- **Заголовки:** Проверяю все заголовки: `Cookie`, `Referer`, `User-Agent`, `X-Forwarded-For`, а также любые нестандартные, начинающиеся с `X-` или `Custom-`
   
- **Тело запроса (POST):** Анализирую данные формы (`application/x-www-form-urlencoded`), JSON (`application/json`) или XML. Выписываю все поля, включая скрытые (`hidden`)
   
- **Примечания:** Если запрос требует аутентификации, я это отмечаю. Если используется HTTPS - тоже


---------


### Шаг 3: Анализ HTTP-ответов

Ответы дают не меньше информации, чем запросы

**Что я анализирую:**

- **Коды состояния:** `200 OK` (стандарт), `302/301` (редиректы, обращаю внимание на Location), `403` (доступ запрещен - может указывать на скрытый ресурс), `500` (внутренняя ошибка - возможно, я нашел уязвимость уже на этом этапе)
   
- **Заголовки:**
   
    - `Set-Cookie`: Какие куки устанавливаются, есть ли у них флаги `HttpOnly`, `Secure`, `SameSite`
      
    - `Server`: Информация о серверном ПО
        
    - `X-Powered-By`: Информация о технологиях

    - Другие интересные заголовки (например, `Content-Security-Policy`, `Strict-Transport-Security`)

здесь в файле подробнее -  [[заголовки-безопасности]]

### Шаг 5: Продвинутый метод - Attack Surface Detector (ASD)

Если у меня есть доступ к исходному коду (в рамках White Box), я использую мощный инструмент **Attack Surface Detector (ASD)**. Он сканирует код и автоматически находит все эндпоинты и их параметры, включая те, на которые нет ссылок в интерфейсе

- **Инструмент:** ASD CLI (командная строка) или плагины для Burp/ZAP.
    
- **Пример использования CLI:**
    
   ```sh
   java -jar attack-surface-detector-cli-1.3.5.jar /путь/к/исходному/коду -json -o output.json
   ```
   
- **Анализ результатов:** На выходе я получаю JSON-файл со списком всех URL, методов и параметров. Этот файл я могу импортировать в Burp Suite для автоматического тестирования
   

## 6. Интерпретация результатов

**Что считать успехом?**

- **Полное покрытие:** У меня есть документ, в котором перечислены все (или почти все) точки входа в приложение. Это основа для всех последующих тестов
   
- **Находка скрытых параметров:** Например, параметр `debug=true`, который не отображается в интерфейсе, но может активировать отладочный режим
   
- **Обнаружение нестандартных методов:** Нахождение работающих PUT или DELETE методов, что может указывать на уязвимости в конфигурации веб-сервера
   

**Как я использую эту информацию:**  
Я не ищу уязвимости на этом этапе. Я создаю **рабочий документ**, который буду использовать в следующих тестах (WSTG-INPV-*). Например, для каждого параметра из таблицы я буду отдельно проверять SQL-инъекции, XSS, пути и другие уязвимости


 
 
 
 Инструменты

- **Burp Suite :** Основной перехватывающий прокси. Использую Proxy, Target (для составления карты), и Spider
   
- **OWASP ZAP (Zed Attack Proxy):** Бесплатная альтернатива. Включает Spider, Passive Scanner
   - **Attack Surface Detector (ASD):** Плагин для Burp/ZAP или CLI-версия для анализа исходного кода. Ссылка: [https://github.com/secdec/attack-surface-detector-cli](https://github.com/secdec/attack-surface-detector-cli)
   
- **Браузерные DevTools:** Вкладка Network - для быстрого просмотра запросов без настройки прокси
   
- **Таблицы :** Для документирования точек входа
   
- **Text Editors (VS Code, Notepad++)** для просмотра исходного кода страниц в поисках скрытых полей и JavaScript
