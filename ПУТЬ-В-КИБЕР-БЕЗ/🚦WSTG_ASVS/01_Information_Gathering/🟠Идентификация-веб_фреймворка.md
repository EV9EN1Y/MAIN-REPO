>	Этот тест посвящён определению того, на каком фреймворке или CMS (системе управления контентом) построено приложение. В современном мире почти каждый сайт использует готовые решения: WordPress, Joomla, Drupal, Laravel, [ASP.NET](https://asp.net/), Django и другие. Зная фреймворк, я автоматически знаю его типовые уязвимости, структуру каталогов, стандартные пути к админке и особенности конфигурации. Это позволяет мне точечно бить по слабым местам, а не тратить время на слепое тестирование

проводится этот тест, чтобы **точно определить стек технологий** приложения. Это критично, потому что:

- Каждый фреймворк имеет свои известные уязвимости (например, старые версии WordPress с уязвимостью в `wp-login.php`)
   
- Знание фреймворка помогает предсказать структуру URL, имена cookies, пути к статике и конфигурационные файлы
   
- Это позволяет сфокусироваться на специфичных для фреймворка атаках, а не тратить время на универсальные методы, которые могут не сработать

## ПОИСК ИНФЫ О ФРЕЙМВОРКЕ




### 4.1 HTTP-заголовки

Самый простой и очевидный способ - посмотреть на заголовок `X-Powered-By`
```http
X-Powered-By: PHP/5.4.16-1~dotdeb.1
```

Или специальный генератор:

```http
X-Generator: Swiftlet
```

**Важно!** Заголовки легко подделать или убрать. Но даже если они изменены, иногда разработчики оставляют другие специфичные заголовки, которые указывают на фреймворк (например, `X-Drupal-Dynamic-Cache`, `X-Varnish` и т.д.)

### 4.2 Cookies

Каждый популярный фреймворк устанавливает свои характерные cookies. Например:

- CakePHP - `CAKEPHP`
- Laravel - `laravel_session`
- WordPress - `wp-settings`
- Django - `django`
- TYPO3 - `fe_typo_user`
    

Изменить имя cookie сложнее, чем заголовок, поэтому этот метод надёжнее

### 4.3 HTML-код страницы

В исходном коде часто можно найти прямые указания:

- Мета-тег `generator`:
```html
<meta name="generator" content="WordPress 3.9.2" />
```

- Комментарии в HTML, специфичные для фреймворка:
```http
<!-- START headerTags.cfm -->  <!-- для Adobe ColdFusion -->
<!-- ZK -->                    <!-- для ZK Framework -->
```

- Пути к CSS/JS:
```html
<link rel="stylesheet" href="/wp-content/themes/twentyfifteen/style.css">
```

- Переменные JavaScript, характерные для фреймворка (например, `__VIEWSTATE` для [ASP.NET](https://asp.net/))
   

### 4.4 Специфичные файлы и папки

каждый фреймворк имеет свою структуру каталогов. Даже если она не видна в HTML, я могу попытаться обратиться к стандартным путям:

- WordPress: `/wp-admin/`, `/wp-includes/`, `/wp-content/`
    
- Joomla: `/administrator/`, `/components/`, `/modules/`
    
- Drupal: `/sites/`, `/core/`, `/modules/`
    
- Laravel: `/storage/`, `/vendor/`, `/public/`
    

Для перебора я использую инструменты типа `dirb` или Burp Suite Intruder со словарями популярных путей (например, из FuzzDB)

### 4.5 Расширения файлов

Расширения в URL прямо указывают на технологию:

- `.php` - PHP (WordPress, Drupal, Joomla, Laravel)
    
- `.aspx` - Microsoft [ASP.NET](https://asp.net/)
    
- `.jsp` - Java Server Pages
    
- `.do` - Java Struts
    

### 4.6 Ошибки приложения

Ошибки часто раскрывают полный путь к файлам и имя фреймворка

```q
Warning: include(/var/www/html/wp-content/themes/functions.php): failed to open stream...
```

## 5. Как выполнять тест 

### Шаг 1: Ручной анализ

1. **Открываю DevTools в браузере** и перехожу на вкладку Network. Смотрю все заголовки ответов (`X-Powered-By`, `Server`, `X-Generator`, специфичные заголовки типа `X-Drupal`)
    
2. **Просматриваю исходный код страницы** (Ctrl+U) в поиске:
    
    - Мета-тега `generator`
        
    - Комментариев, содержащих название фреймворка
        
    - Путей к CSS/JS, которые включают название фреймворка
        
    - Уникальных переменных JavaScript (например, `window.wpApiSettings` для WordPress)
        
3. **Проверяю cookies** в DevTools (вкладка Application → Cookies). Ищу характерные имена
    

### Шаг 2: Перебор каталогов (Dirbusting)

Использую инструмент **dirb** или **gobuster** для проверки существования стандартных папок:
или просто в интрудере бурп все это сделать!

```c
gobuster dir -u https://example.com -w /usr/share/wordlists/dirb/common.txt -t 50
```

Особое внимание уделяю путям типа `/admin`, `/wp-admin`, `/administrator`, `/wp-content`, `/sites`

### Шаг 3: Использование автоматических инструментов

Я использую специализированные инструменты для точной идентификации:

- **WhatWeb** (входит в Kali Linux): мощный сканер, который анализирует заголовки, HTML, структуру URL и даёт очень точный результат

 ```c
   whatweb https://example.com
 ```
   
- **Wappalyzer**: расширение для браузера (Firefox/Chrome), которое в реальном времени показывает стек технологий сайта прямо в адресной строке
   

### Шаг 4: Проверка уязвимых версий

Когда фреймворк и его версия определены, я проверяю наличие публичных уязвимостей для этой версии через базы данных CVE

Например, если я определил WordPress 4.7.0, то сразу знаю, что в нём есть известная уязвимость REST API, которая позволяет изменять содержимое страниц

## Инструменты

| Инструмент                      | Назначение                                                             |
| ------------------------------- | ---------------------------------------------------------------------- |
| **WhatWeb**                     | Самый точный CLI-инструмент для идентификации технологий и фреймворков |
| **Wappalyzer**                  | Расширение для браузера, показывает технологии прямо на странице       |
| **BuiltWith**                   | Онлайн-сервис, который анализирует сайт и показывает все компоненты    |
| **gobuster / dirb / dirbuster** | Инструменты для перебора (dirbusting) скрытых каталогов и файлов       |
| **Burp Suite / ZAP**            | Прокси для перехвата и анализа заголовков и cookies, для всего!!!      |
| **curl**                        | Для быстрой проверки заголовков из командной строки                    |

  Важные нюансы

1. **Не верьте одному маркеру**. Используйте 3–5 разных признаков для подтверждения
   
2. **Заголовки могут быть подделаны**. Если видите `X-Powered-By: Blood, sweat and tears` - это явная попытка скрыть фреймворк
   
3. **Используйте комбинацию методов**: заголовки + cookies + HTML + dirbusting
   
4. **Помните про CDN**. Если сайт использует Cloudflare, `Server` заголовок будет скрыт. В этом случае ищите другие признаки
   
5. **Следите за robots.txt**. Часто там можно найти пути к админ-панели или стандартным папкам
   

 ==Борьба с сокрытием (и почему она не работает)==

Разработчики пытаются скрыть фреймворк (меняют имена cookies, убирают заголовки, переименовывают папки). Это называется _security through obscurity_. Это бесполезно, потому что:

- Ошибки приложения всё равно могут раскрыть структуру
- Стандартные пути можно найти перебором
- Специфические CSS-классы и HTML-шаблоны не изменятся до неузнаваемости
   

Лучше потратить время на реальную безопасность, а не на маскировку
