
##  1. Описание теста

Данный тест посвящен выявлению конфиденциальной информации, которая может быть обнаружена при анализе содержимого веб-страниц и связанных с ними файлов. Разработчики часто оставляют в финальной версии приложения служебную информацию: комментарии в HTML-коде, отладочные данные в JavaScript, исходные карты (source maps) для упрощения отладки и метаданные в генерируемых документах. Задача тестировщика - найти эту информацию и оценить риски

В современном вебе с его сложными фронтенд-фреймворками (React, Angular, Vue) проблема усугубляется. Код на JavaScript может содержать ключи API, внутренние IP-адреса, пути к скрытым админ-панелям или даже логины и пароли. Всё это - ценные подсказки для злоумышленника

---------
## 2. Для чего делается тест

Я провожу этот тест, чтобы найти любую информацию, которая может помочь злоумышленнику на этапе разведки. Это могут быть прямые учетные данные, технические детали (версии библиотек, структура папок), скрытые конечные точки API, архитектурные особенности приложения. Подобная информация снижает порог входа для атакующего, позволяя ему точнее нацелить свои действия

----------
## 3. Цели теста

1. **Обнаружить утечки в комментариях и метаданных:** Найти в HTML-коде скрытые комментарии и мета-теги, раскрывающие внутреннюю структуру, логику работы, пути к файлам или данные для отладки
   
2. **Проанализировать JavaScript-код:** Выявить в JS-файлах или скриптах на странице жестко закодированные секреты: API-ключи, внутренние IP-адреса, учетные данные, ссылки на скрытые ресурсы
   
3. **Найти отладочные файлы:** Обнаружить наличие source map-файлов (`.map`), которые делают минифицированный код читаемым и помогают восстановить исходную структуру приложения
   
4. **Проанализировать ответы редиректов:** Проверить, не содержится ли информация в теле HTTP-ответов с кодом 3xx
   
5. **Проверить метаданные генерируемых файлов:** Найти информацию о технологиях и их версиях в метаданных файлов (PDF, DOCX), создаваемых приложением

-------------------


## 4. Примеры, демонстрирующие суть теста

**Пример 1: SQL-запрос в HTML-комментарии.**  
В исходном коде страницы я вижу:

```c
<!-- Query: SELECT id, name FROM app.users WHERE active='1' -->
```

Это дает мне информацию о структуре базы данных, именах таблиц и полей, что может помочь при проведении SQL-инъекций

**Пример 2: API-ключи в JavaScript.**  
В загружаемом JS-файле я нахожу:

```js
const GOOGLE_MAP_API_KEY = "AIzaSyDUEBnKgwiqMNpDplT6ozE4Z0XxuAbqDi4";
```

Если этот ключ не ограничен по IP или рефереру, я могу использовать его для отправки запросов к Google Maps API за счет владельца приложения

**Пример 3: Source Map-файлы

Если я обнаружу, что приложение загружает `main.chunk.js.map`, я смогу восстановить читаемый исходный код, что может открыть пути к новым уязвимостям

**Пример 4: Внутренний IP в JavaScript**  
Нахожу в коде:



```js
"BASE_BACKOFFICE_API":"https://10.10.10.2/api"
```

Утечка внутреннего IP-адреса дает информацию о внутренней инфраструктуре


## 5. Как выполнять тест 

Я буду действовать пошагово, комбинируя ручной анализ и автоматические инструменты

### Шаг 1: Анализ комментариев и метаданных HTML

1. **Просмотр исходного кода:** Я открою в браузере исходный код страницы (Ctrl+U или Cmd+Option+U). Пролистаю его в поиске HTML-комментариев `<!--`, обращая внимание на SQL-запросы, пароли, имена файлов, внутренние пути.
    
2. **Анализ `<meta>`-тегов:** Я просмотрю содержимое мета-тегов в `<head>`. Интерес могут представлять:
    
    - `<meta name="Author" ...>` - имя разработчика
        
    - `<meta name="keywords" ...>` - ключевые слова
        
    - `<meta http-equiv="Refresh" ...>` - информация о редиректах
        
    - `<meta name="robots" ...>` - директивы для поисковых роботов (иногда раскрывают скрытые разделы)


#### Wappalyzer

3. **Использование расширений браузера:** Для быстрого поиска по всем загруженным файлам я использую расширение **Wappalyzer** для идентификации технологий и **Retire.js** для поиска уязвимых JS-библиотек




------------



### Шаг 2: Анализ JavaScript-кода

1. **Поиск блоков `<script>`:** В исходном коде я найду все встроенные и внешние скрипты
   
2. **Просмотр JS-файлов:** Я вручную открою в браузере все загруженные `.js`-файлы (их имена можно найти в тегах `<script src="...">`). Прогляжу их в поиске:
   
    - `api`, `key`, `token`, `secret`, `password`, `config`, `baseURL`, `url`
   
    - IP-адресов (особенно внутренних, типа `10.`, `192.168.`, `172.`)
    
    - URL-адресов с нестандартными путями
   
3. **Быстрый grep в Терминале (через curl):** Чтобы не качать всё вручную, я могу использовать `curl` и `grep`:

   ```bash
   curl -s https://example.com/static/js/main.js | grep -E 'api|key|token|secret|password'
   ```

-------------

### Шаг 3: Поиск Source Map-файлов

1. **Проверка в DevTools:** Открою Инструменты разработчика в браузере (F12), перейду на вкладку Sources (Источники) и посмотрю, доступны ли там `.map`-файлы
   
2. **Ручной перебор:** Для каждого найденного JS- и CSS-файла я проверю, существует ли его source map. Если есть файл `/static/js/main.chunk.js`, то я попробую открыть `/static/js/main.chunk.js.map`. Если файл найден - значит, информация утекает
   
3. **Анализ `sources`:** Если `.map`-файл доступен, я загружу его и посмотрю в поле `"sources"`. Там часто содержатся абсолютные пути к файлам на сервере разработчика, что раскрывает внутреннюю структуру проекта

---------


### Шаг 4: Анализ ответов редиректов (3xx)

1. **Через Burp/ZAP:** Я настрою прокси (burp) и перехвачу все ответы от сервера, обращая особое внимание на коды 301, 302, 303. Я посмотрю на тело ответа - иногда там может быть текстовая информация, которая не отображается в браузере, но передается
   
2. **Через `curl -v`:** Для конкретного запроса я могу выполнить команду и изучить полный вывод:
   

   
   ```c
   curl -v https://example.com/admin
   ```
   

------

### Шаг 5: Проверка метаданных генерируемых файлов

1. **Определение генерируемых файлов:** Я нахожу на сайте примеры PDF, DOCX, XLSX-файлов, которые могут создаваться динамически (например, счета, отчеты).
    
2. **Скачивание и анализ:** Скачиваю несколько таких файлов.
    
3. **Просмотр метаданных:** Использую утилиты, чтобы извлечь метаданные.
    
    - Для PDF-файлов:

```c
exiftool file.pdf
pdfinfo file.pdf
strings file.pdf | grep -i producer
```
        
    - Для офисных документов:

        
```c
exiftool file.docx
```
        
    - Обращаю внимание на поля `Producer`, `Creator`, `Application Version`. Например, нахожу `Producer: iText 2.1.7` — это старая версия с известными уязвимостями (CVE)

## 6. Интерпретация результатов

**Что считать успехом?**

- **Любой чувствительный ключ или пароль:** Это критическая находка, требующая немедленной проверки и сообщения
   
- **Любая техническая информация, которая не должна быть публичной:** От внутренних IP-адресов до имен пользователей, путей к файлам, имен переменных и комментариев. Это облегчает дальнейшие атаки
   
- **Обнаружение source map-файлов:** Это прямое указание на то, что разработчики не соблюдают правила безопасной сборки проекта


**Как документировать?**  
Я зафиксирую:

1. Место находки (URL, конкретный файл)
   
2. Что именно найдено (фрагмент кода или комментарий)
   
3. Почему это опасно (как может быть использовано атакующим)
   
4. Уровень критичности (Low/Medium/High)
   
5. Рекомендацию по исправлению (удалить код, ограничить ключ, убрать `.map`-файлы)
   

## 7. Инструменты

- **burp Suite / ZAP:** Для перехвата трафика и анализа ответов

- **командная строка:** `curl`, `grep`, `exiftool`, `strings`, `pdfinfo`
   
- **онлайн-сервисы:** Для проверки API-ключей на ограничения можно использовать сервисы типа KeyHacks
