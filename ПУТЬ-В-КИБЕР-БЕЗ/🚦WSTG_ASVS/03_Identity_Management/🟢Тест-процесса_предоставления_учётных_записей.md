**WSTG-IDNT-03: Test Account Provisioning Process** (Тестирование процесса предоставления учётных записей)


-----


## Описание теста

Этот тест проверяет, как в приложении создаются и удаляются учётные записи, а также кто имеет на это право. Уязвимости в процессе provisioning (предоставления доступа) позволяют злоумышленнику создать себе учётную запись с неоправданно высокими привилегиями или, наоборот, заблокировать доступ легитимным пользователям

##  Цели теста

1. **Проверить, кто может создавать учётные записи** (только администраторы или обычные пользователи тоже)
   
2. **Проверить, можно ли создать учётную запись с правами выше, чем у создателя**
   
3. **Проверить, можно ли удалить (де-провижн) учётную запись без надлежащей проверки**
   
4. **Проверить, можно ли удалить самого себя** (если это не предусмотрено)
   
5. **Проверить, что происходит с данными удалённого пользователя** (удаляются, передаются другому пользователю)
   
--------

##  Как выполнять тест 


### Шаг 1: Идентификация ролей с правом provisioning

Я выясняю, какие роли в системе могут создавать и удалять учётные записи. Источники:

- Документация
   
- Интерфейс приложения (панель администратора)
   
- Код (если есть доступ)
   

### Шаг 2: Проверка создания учётных записей

**Что я проверяю:**

- Может ли обычный пользователь создать нового пользователя
   
- Может ли пользователь создать другого пользователя с правами выше своих (например, user → admin)
   
- Требуется ли утверждение (верификация) запроса на создание учётной записи
   
- Можно ли создать учётную запись с произвольным email (без подтверждения)
   

### Шаг 3: Проверка удаления учётных записей (де-провижн)

**Что я проверяю:**

- Может ли администратор удалить любого пользователя (включая других администраторов)
   
- Может ли администратор удалить самого себя

- Может ли обычный пользователь удалить свой аккаунт ??
- 
- Требуется ли утверждение для удаления
   
- Что происходит с данными удалённого пользователя (например, постами, файлами)
- - и че там по фз-152 ???
   

### Шаг 4: Проверка передачи прав и данных

Если пользователь удаляется, я проверяю:

- Можно ли передать его ресурсы (файлы, посты) другому пользователю
    
- Если передача не предусмотрена, удаляются ли данные без возможности восстановления
    
- Можно ли восстановить удалённую учётную запись
    
-------



##  Интерпретация результатов

**Что считать успехом (находкой):**

- Обычный пользователь может создать учётную запись с правами администратора
    
- Администратор может удалить другого администратора без дополнительной проверки
    
- Пользователь может удалить свой аккаунт, но его данные (например, файлы) остаются в системе без владельца
    
- Нет верификации запросов на создание/удаление учётных записей
    

**Как я документирую:**

- Роли, которые могут создавать и удалять учётные записи
   
- Возможность создания учётных записей с повышенными привилегиями
   
- Процесс де-провижна и управления данными    

- Потенциальное воздействие
  
- Рекомендации: ограничить круг лиц, имеющих право на provisioning, внедрить верификацию запросов

##  Примеры

**Пример 1: WordPress (из документации)**  
В WordPress администратор может создать нового пользователя, указав только имя и email. При удалении пользователя администратору предлагается выбрать: удалить все посты пользователя или передать их другому пользователю. Это правильный процесс, так как управление данными не теряется

**Пример 2: Создание администратора через скрытое поле**  
В форме создания пользователя есть скрытое поле `<input type="hidden" name="role" value="subscriber">`. Злоумышленник изменяет его на `administrator` и отправляет запрос. Если сервер не проверяет роль на бэкенде, создаётся учётная запись с правами администратора

**Пример 3: Удаление администратора без защиты**  
Администратор может удалить любого другого администратора, включая последнего. Это может привести к тому, что система останется без администраторов, и восстановить доступ будет невозможно





## тонкости

1. **Не все приложения имеют роли.** В некоторых системах есть только "администратор" и "пользователь". В этом случае проверяются только эти две роли
    
2. **Де-провижн должен быть безопасным.** Удаление учётной записи не должно приводить к потере данных или созданию "бесхозных" объектов (например, файлов, которые никто не может удалить или передать)
    
3. **Проверка на возможность удаления самого себя.** Если администратор может удалить свой аккаунт, это может быть использовано для сокрытия следов после атаки
