**WSTG-CONF-09: Test File Permission**


ест посвящен проверке прав доступа к файлам и каталогам на сервере. Если файл или директория имеют более широкие права, чем необходимо, это может привести к утечке конфиденциальной информации или несанкционированному изменению данных. Особенно опасны случаи, когда файлы конфигурации, исполняемые скрипты, логи или файлы с паролями доступны для чтения или записи неавторизованными пользователями

## Цели теста

1. **Выявить файлы и каталоги с избыточными правами** (например, world-readable или world-writable)
   
2. **Проверить права на критические ресурсы:** конфигурационные файлы, логи, исполняемые файлы, загружаемые пользователями файлы
   
3. **Убедиться, что чувствительные данные не доступны для чтения или записи посторонним**
------

## Как выполнять тест


Этот тест в основном выполняется при наличии доступа к файловой системе сервера (Gray-box или White-box тестирование)
При Black-box тестировании я могу лишь косвенно проверить доступность некоторых файлов через веб (см. тесты CONF-03 и CONF-04), либо при обнаружении узявимости уже...

------

# 🔵 🔵  Linux
##### Шаг 1: Проверка прав в Linux

#### Использование `ls -la`

Базовая команда для просмотра прав:


```q
ls -la /path/to/directory
```
Пример вывода:
```c
-rw-r--r-- 1 root root 1024 Apr 10 10:00 config.php
drwxr-xr-x 2 root root 4096 Apr 10 10:00 uploads
```

**Что я смотрю:**

- Первый символ: `-` (файл), `d` (директория)
- Следующие 9 символов: права для владельца, группы и всех остальных
- Владелец и группа (например, `root root`)
- Путь к файлу

---------

#### Использование `namei` для рекурсивной проверки

Более мощная команда, которая показывает права для всего пути:
```q
namei -l /var/www/html/config/database.php
```

# 🔵 🔵 Windows
##### Шаг 2: Проверка прав в Windows

Использую `icacls` или проверяю через GUI:
```c
icacls C:\inetpub\wwwroot\web.config
```

### Шаг 3: Какие права считаются опасными

#### Опасные права для Linux:

- **777 (rwxrwxrwx):** Полный доступ для всех. Критическая уязвимость для любого файла
   
- **666 (rw-rw-rw-):** Чтение и запись для всех. Опасно для конфигов и логов
   
- **644 (rw-r--r--):** Чтение для всех. Безопасно для статических веб-файлов, но **опасно** для конфигов с паролями
   
- **755 (rwxr-xr-x):** Чтение и выполнение для всех. Безопасно для каталогов, но **опасно** для скриптов с паролями
   

#### Опасные права для Windows:

- **Everyone - Full Control:** Полный доступ для всех
   
- **IIS_IUSRS - Write:** Запись для веб-сервера в каталогах с исполняемыми файлами




---------


### Шаг 4: Критические файлы и каталоги для проверки

|Тип ресурса|Примеры путей|Опасные права|
|---|---|---|
|**Веб-файлы**|`/var/www/html/`, `C:\inetpub\wwwroot\`|Чтение/запись для всех|
|**Конфигурационные файлы**|`/etc/nginx/nginx.conf`, `web.config`, `.env`, `config.inc`|Чтение для всех (если там есть пароли)|
|**Файлы с паролями и ключами**|`.htpasswd`, `id_rsa`, `credentials.json`|Любое чтение или запись для не-владельца|
|**Логи**|`/var/log/`, `logs/error.log`|Чтение для всех (может раскрыть пути и данные)|
|**Исполняемые файлы**|`.php`, `.asp`, `.jar`, `.exe` в веб-каталоге|Запись для всех (можно заменить шеллом)|
|**Базы данных**|`database.sqlite`, `data.mdb`|Чтение для всех (можно скачать БД)|
|**Временные файлы**|`/tmp/`, `temp/`|Чтение/запись для всех (может привести к XSS или RCE)|
|**Загружаемые файлы**|`/uploads/`, `/files/`|Выполнение для всех (если загружен шелл)|

### 🔵   🔵     🔵        🔵  Проверка прав через веб (Black-box)

Если у меня нет прямого доступа к серверу, я могу лишь косвенно проверить доступность некоторых файлов через веб. Это пересекается с тестами CONF-03 и CONF-04

**Что я делаю:**

1. Пытаюсь открыть в браузере файлы, которые не должны быть доступны: `/config/database.php`, `/wp-config.php`, `/.env`
   
2. Проверяю, не включен ли листинг каталогов (Directory Listing) в `/uploads/`, `/backup/`, `/logs/`
   
3. Если файл отдается браузером как текст или скачивается - это признак проблемы с правами или конфигурацией веб-сервера

## 7. Важные нюансы

1. **Права на файлы - это локальная проблема.** Для Black-box тестирования я могу проверить только то, что доступно через веб. Полную картину я получу только с доступом к серверу
    
2. **Неправильный владелец файла так же опасен, как и неправильные права.** Даже с правами 600, если файл принадлежит пользователю `nobody` или `www-data`, а не `root`, он может быть скомпрометирован через уязвимость в веб-сервере
    
3. **Каталоги с правами 777 - это красный флаг.** Они позволяют любому пользователю создавать, удалять и изменять файлы. Это частая проблема в каталогах для загрузки файлов
    
4. **Проверяй не только файлы, но и каталоги.** Каталог с правами 755 безопасен, но если он принадлежит не тому пользователю, это может быть проблемой

### 🌐🌐 Инструменты для "черного ящика" (поиск через URL) 🌐🌐

Это сканеры, которые эмулируют действия злоумышленника извне. Они перебирают пути и пытаются достать файлы через веб

- **Gobuster, dirb, DirBuster:** Классика для перебора каталогов и файлов. Ты даешь словарь, они стучатся по всем путям и смотрят на ответы сервера (200, 403, 404). Отлично подходят для поиска `admin.php`, `backup.zip` и т д

здесь подробнее - >  [[gobuster]] 


- **VulnProbe:** Более продвинутый модульный сканер. Он не просто перебирает пути, а имеет отдельный модуль для **Directory Enumeration (перебора каталогов)** с использованием словаря и многопоточности
- Также у него есть модуль для **Local File Inclusion (LFI) / Path Traversal**, где он подставляет пейлоады типа `../../etc/passwd` в параметры, пытаясь прочитать системные файлы 
   
- **path-checker:** Специализированный Python-инструмент как раз для тестирования **Path Traversal / Directory Traversal** . Он отправляет в параметр запроса кучу закодированных пейлоадов (`..%2f`, `%252e%252e%252f`) и отмечает подозрительные ответы, которые могут говорить об успешном чтении файлов 
   
- **Wapiti:** Черно-ящичный фаззер. Он сканирует страницы, находит формы и параметры, а затем автоматически подставляет в них пейлоады для разных типов атак, включая File Handling Errors (Local и Remote Include)
   

### 🌐🌐🌐  Инструменты для "белого ящика" (с доступом к серверу) 🌐🌐🌐

Здесь речь идет об анализе файловой системы, а не веб-запросов

- **Стандартные системные команды:** В первую очередь это `ls -la`, `find` и `namei` в Linux. Они позволяют рекурсивно просмотреть права на все файлы в каталоге. Например, команда `find /var/www/html -type f -perm 0777` найдет все файлы с правами 777, которые доступны на запись всем 
   
- **MCP Security Scanner:** Утилита для сканирования проектов (в основном JS/TS). У нее есть специальный инструмент `checkPermissions`, который находит **world-writable or overly permissive files** (мировые или излишне разрешенные файлы) 
   
- **Security Audit Skill (Bash):** Легковесный bash-скрипт для аудита безопасности. В его функции входит проверка прав на файлы: поиск world-writable файлов, SUID/SGID бинарников и небезопасных конфигов 
   
- **Observation (obacht):** Сканер безопасности для окружений разработки. Он проверяет в том числе и на **insecure file permissions** (небезопасные права доступа к файлам) с помощью встроенных правил 
   
- **Специализированные PHP-сканеры (например, Security Check Script):** Сканируют код приложения на наличие подозрительных функций (`eval`, `system`, `base64_decode`), потенциальных SQL-инъекций и даже проверяют права на файлы . Это уже больше похоже на анализ кода, а не только на проверку прав
