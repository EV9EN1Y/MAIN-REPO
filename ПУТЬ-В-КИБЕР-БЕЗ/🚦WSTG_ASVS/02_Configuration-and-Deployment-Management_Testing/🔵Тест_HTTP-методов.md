## 1. Описание теста

Этот тест посвящён анализу того, какие HTTP-методы поддерживает веб-сервер и как он на них реагирует. 
Кроме стандартных GET и POST, существуют и другие методы (PUT, DELETE, OPTIONS, TRACE, CONNECT, PATCH), которые могут быть включены по умолчанию или оставлены по небрежности. Некоторые из них могут быть использованы для загрузки файлов, удаления данных, обхода аутентификации или даже организации прокси-туннеля

## 2. Для чего делается тест

этот тест, чтобы найти потенциально опасные HTTP-методы, которые не должны быть доступны. Если сервер позволяет использовать PUT или DELETE, это может привести к загрузке вредоносных файлов или удалению критичных данных. Если разрешён TRACE - это может раскрыть информацию для атак (хотя сейчас это уже не так критично). Кроме того, нестандартные методы иногда помогают обойти ограничения WAF или авторизации

## 3. Цели теста

1. **Определить, какие HTTP-методы поддерживает сервер** для разных путей
   
2. **Выявить опасные методы** (PUT, DELETE, TRACE, CONNECT)
   
3. **Проверить, можно ли обойти контроль доступа**, используя нестандартные методы
   
4. **Протестировать механизмы переопределения HTTP-методов** (например, через заголовки X-HTTP-Method-Override)

# Как выполнять тест 


### Шаг 1: Обнаружение поддерживаемых методов

#### Способ 1: OPTIONS-запрос

Самый простой способ - отправить запрос OPTIONS:

```http
OPTIONS / HTTP/1.1
Host: example.org


 ответ:


HTTP/1.1 200 OK
Allow: OPTIONS, GET, HEAD, POST
```

**Ограничения:** Не все серверы отвечают на OPTIONS, а некоторые могут возвращать неполный список. Также методы могут различаться для разных путей (например, для `/api/` могут быть разрешены PUT и DELETE, а для `/` - нет)

-------------

#### Способ 2: Прямой запрос с методом

Более надёжный способ - просто отправить запрос с конкретным методом и посмотреть на ответ. Если метод запрещён, сервер вернёт `405 Method Not Allowed`:

```http
PUT /test.html HTTP/1.1
Host: example.org

Ответ:

HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD, POST, OPTIONS
```


-----------

#### Способ 3: Использование curl

Универсальный способ проверить любой метод:

```c
# Проверка OPTIONS
curl -X OPTIONS https://example.org -i

# Проверка конкретного метода
curl -X PUT https://example.org/test.html -d "test" -i
```
#### Способ 4: Автоматические инструменты

- **Nmap скрипт `http-methods`**: `nmap --script http-methods <target>`
   
- **Nikto**: автоматически проверяет опасные методы

подробнее здесь [[NMAP]]  и здесь [[Nikto]]

### Шаг 2: Тестирование метода PUT

##### ==Если PUT разрешён, это может позволить загрузить файл на сервер. 
##### Это очень опасно, если можно загрузить исполняемый код (например, PHP-шелл)==

#### Пример загрузки файла через PUT (старые серверы)

Запрос:
```q
PUT /test.html HTTP/1.1
Host: example.org
Content-Length: 25
<script>alert(1)</script>

Ответ 

201 Created` означает, что файл создан. Теперь он доступен по адресу https://example.org/test.html

```

**Команда curl:**
```q
curl -X PUT -d "<script>alert(1)</script>" https://example.org/test.html
```

#### Пример PUT в RESTful API

В современных API PUT используется для создания или полной замены объекта:
```http
PUT /api/users/foo HTTP/1.1
Host: example.org
Content-Type: application/json
{
    "role": "user"
}
```

Здесь PUT создаёт пользователя "foo" с ролью "user"

### Шаг 3: Тестирование метода DELETE

DELETE может удалить файл или объект. Это деструктивный тест, выполняй его с осторожностью и только с разрешения заказчика

#### Пример удаления файла (старые серверы)


```http
DELETE /test.html HTTP/1.1
Host: example.org

Ответ `200 OK` или `204 No Content` означает, что файл удалён

Команда curl:
curl -X DELETE https://example.org/test.html

------------
#### Пример DELETE в RESTful API

DELETE /api/users/foo HTTP/1.1
Host: example.org


смысл предельно понятен
```


-------
### Шаг 4: Тестирование метода TRACE

TRACE заставляет сервер вернуть полученный запрос в теле ответа. Это может раскрыть заголовки, включая Cookie, что ранее использовалось для атак XST

**Запрос:**

```http
TRACE / HTTP/1.1
Host: example.org

Ответ:
HTTP/1.1 200 OK
Content-Type: message/http
TRACE / HTTP/1.1
Host: example.org

Если сервер вернул тело с эхом запроса - TRACE включён. Это указывает на слабую конфигурацию, хотя в современных браузерах XST уже не работает
```

---------

### Шаг 5: Тестирование метода CONNECT

CONNECT позволяет использовать сервер как прокси для подключения к другому хосту. Это может быть использовано для доступа к внутренним системам или обхода сетевых ограничений:

```http
CONNECT 192.168.0.1:443 HTTP/1.1
Host: example.org

Если сервер ответил `200 Connection Established` — он работает как прокси
```


---------
### Шаг 6: Тестирование метода PATCH

PATCH используется для частичного обновления объекта (в отличие от PUT, который заменяет его целиком)

#### Пример JSON Patch (RFC 6902)

```http
PATCH /api/users/foo HTTP/1.1
Host: example.org
Content-Type: application/json-patch+json
[
    { "op": "replace", "path": "/role", "value": "admin" }
]
```
#### Распространённое (неправильное) использование PATCH

Многие API используют PATCH как "частичное обновление", передавая только изменяемые поля:
```http
PATCH /api/users/foo HTTP/1.1
Host: example.org
Content-Type: application/json
{
    "role": "admin"
}
```

### Шаг 7: Тестирование обхода контроля доступа

Иногда можно обойти редирект на страницу логина (302), используя нестандартный метод:

**Обычный GET (редирект):**

```http

GET /admin/ HTTP/1.1
Host: example.org

HTTP/1.1 302 Found
Location: /login.php

HEAD-запрос (может не сработать редирект):



HEAD /admin/ HTTP/1.1
Host: example.org



HTTP/1.1 200 OK
Set-Cookie: adminSessionCookie=...

**Произвольный метод (FOO):**



FOO /admin/createUser.php?username=foo&password=bar&role=admin HTTP/1.1
Host: example.org

Если сервер обрабатывает FOO как GET и создаёт пользователя — это критическая уязвимость

**Команда curl:**



curl -X FOO "https://example.org/admin/createUser.php?username=foo&password=bar&role=admin" -i
```


----------

### Шаг 8: Тестирование переопределения HTTP-методов

```http
Некоторые фреймворки позволяют "подменять" метод через специальные заголовки, чтобы обойти ограничения WAF или прокси. Это называется **HTTP Method Overriding

Цель: Обойти запрет метода (например, `405 Method Not Allowed` для DELETE) с помощью заголовка-обманки.

Пример:  
Обычный DELETE запрещён:


DELETE /resource.html HTTP/1.1
Host: example.org


HTTP/1.1 405 Method Not Allowed

Но если добавить заголовок `X-HTTP-Method: DELETE` к GET-запросу, сервер может обработать его как DELETE:


GET /resource.html HTTP/1.1
Host: example.org
X-HTTP-Method: DELETE

HTTP/1.1 200 OK

#### Проверяемые заголовки:

- `X-HTTP-Method`
    
- `X-HTTP-Method-Override`
    
- `X-Method-Override`
    

Как тестировать:

1. Выбери метод, который запрещён (например, PUT или DELETE) и получи `405`
    
2. Повтори запрос с тем же методом, но добавь один из заголовков, указав целевой метод
    
3. Смотри на ответ: если вместо `405` пришёл `200` или другой успешный код - переопределение работает
    
```

##  нюансы

1. **Методы могут отличаться для разных путей.** Проверять не только корень, но и все важные каталоги (`/admin/`, `/api/`, `/uploads/`)
   
2. **Некоторые серверы обрабатывают неизвестные методы как GET.** Это может привести к неожиданным результатам и обходу защиты
    
3. **PUT и DELETE в RESTful API - это нормально.** Их наличие не является уязвимостью само по себе. Опасность - в недостатке контроля доступа
    
4. **Тестирование DELETE может быть деструктивным.** Согласуй это с заказчиком и используй тестовые данные
    
5. **Метод TRACE - это скорее индикатор плохой конфигурации, чем реальная угроза** (из-за защиты браузеров), но его лучше отключить
