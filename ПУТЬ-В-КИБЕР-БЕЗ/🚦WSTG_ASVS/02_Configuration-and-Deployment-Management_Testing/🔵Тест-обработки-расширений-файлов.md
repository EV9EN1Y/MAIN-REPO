**WSTG-CONF-03: Test File Extensions Handling for Sensitive Information**

тест посвящён тому, как веб-сервер обрабатывает запросы к файлам с разными расширениями. Расширения файлов напрямую влияют на то, как сервер их интерпретирует: 

одни он обрабатывает как исполняемый код (PHP, ASP, JSP),
другие отдаёт как есть (текст, картинки), а 
третьи могут быть вообще не предназначены для публичного доступа (конфиги, бэкапы, исходники). 

Если сервер неправильно настроен или разработчики оставили служебные файлы, это может привести к утечке исходного кода, паролей или другой критичной информации

Этот тест, чтобы найти файлы, которые не должны быть доступны извне, и проверить, не раскрывает ли сервер информацию через обработку расширений. 

Например, если сервер отдаёт файл `config.inc` как простой текст, а не как PHP-скрипт, я могу увидеть пароль от базы данных. Также я проверяю, не остались ли на сервере бэкапы, архивы, временные файлы или файлы с "нестандартными" расширениями, которые случайно открыты для доступа

------

## Цели теста

1. **Обнаружить файлы с расширениями, которые могут содержать чувствительную информацию**(например, `.inc`, `.config`, `.bak`, `.old`)
   
2. **Проверить, как сервер обрабатывает запросы к этим файлам** - отдаёт их как текст, скачивает или выполняет
   
3. **Выявить файлы, которые не должны быть доступны извне** (исходный код, архивы, документация)
   
4. **Проверить, не используются ли файлы с расширениями, позволяющими обойти ограничения доступа** (например, старые Windows 8.3 имена, двойные расширения)


-------


## как выполнить тест:



### Шаг 1: Перебор расширений (Forced Browsing)

Я использую технику принудительного просмотра (forced browsing), чтобы проверить, какие файлы и расширения доступны на сервере

**Что я делаю:**

1. Беру известные имена файлов (например, из `robots.txt`, из HTML-кода, из результатов предыдущих тестов), или смотрю на файлы с которыми работает сайт/сервер
   
2. Подставляю к ним разные расширения и смотрю на ответ сервера:
   
   - `index.php`, `index.html`, `index.asp`, `index.jsp`
   
   - `config.inc`, `config.php`, `config.asp`, `config.ini`, `config.txt`, `config.bak`

   - `wp-config.php`, `web.config`, `.htaccess`, `web.xml`

3. Проверяю стандартные каталоги на наличие файлов с такими расширениями
   

**Инструменты:**

- **Gobuster / dirb** с масками расширений (`-x php,txt,log,bak,old,inc`)
[[gobuster]]  - тут файл 

- **Burp Intruder** - подстановка разных расширений к одному имени файла
у меня тут есть много решенных лаб - где уязвимости в загружаемых файлах

- **Nikto** - у него есть база известных опасных файлов
[[Nikto]] - тут файл 

-------

### Шаг 2: Анализ расширений, которые никогда не должны быть доступны

По умолчанию я проверяю, доступны ли файлы со следующими расширениями:

**Опасные расширения (никогда не должны быть доступны):* *
то есть сервер должен сразу блокировать эти расширения не пропуская запрос дальше

- `.inc` - файлы включений (часто содержат пароли и пути)
   
- `.config` - файлы конфигурации
   
- `.asa` - файлы глобальной конфигурации для IIS (содержат пароли и строки подключения)
   
- `.ini`- инициализационные файлы
   
- `.yml`, `.yaml` - файлы конфигурации в формате YAML
   
- `.json` - могут содержать секреты
   

**Расширения, которые сервер не должен выполнять, но может отдавать на скачивание (тоже риск):**

- `.bak`, `.old`, `.backup` - бэкапы (могут содержать исходный код или конфиги)
   
- `.zip`, `.tar`, `.gz`, `.rar` - архивы (могут содержать всю файловую структуру)
   
- `.txt` - текстовые файлы (могут содержать логи, заметки разработчиков)
   
- `.docx`, `.xlsx`, `.pptx`, `.pdf` - офисные документы (могут содержать служебную информацию)
   
- `.sql` - дампы баз данных
   
- `.java`, `.py`, `.c` - исходный код
   
- `~` или `#` (файлы, создаваемые редакторами как временные копии)

---------

### Шаг 3: Проверка обработки расширений на уровне каталогов

Я проверяю, как сервер обрабатывает расширения в разных каталогах. Например:

- В каталоге `/uploads/` файл `shell.php` может быть выполнен, а в `/images/` - нет
   
- Я проверяю, разрешено ли выполнение скриптов в каталогах, где лежат загруженные пользователями файлы

------

### Шаг 4: Проверка на legacy-имена Windows (8.3 формат)

На серверах Windows, если включена поддержка старых 8.3 имён, файл с длинным именем, например, `file.phtml`, может быть доступен по сокращённому имени типа `FILE~1.PHT`. Это может позволить обойти ограничения доступа, если они построены на основе расширения

**Что я делаю:**

- Пробую обращаться к файлам по их сокращённым именам, если знаю длинное имя
   
- Особенно актуально для файлов, которые администратор пытался скрыть (например, `.htaccess`не имеет 8.3 эквивалента, а `web.config` имеет)

**Пример 1:**  
Длинное имя: `config.inc`  
8.3-имя: `CONFIG~1.INC`

**Пример 2:**  
Длинное имя: `web.config`  
8.3-имя: `WEB~1.CON` (обрати внимание, расширение тоже обрезается до 3 символов)

**Пример 3:**  
Длинное имя: `very_long_filename.xml`  
8.3-имя: `VERY_L~1.XML`

примеры
```q
https://example.com/WEB~1.CON

https://example.com/CONFIG~2.INC

https://example.com/INDEX~1.HTM

https://example.com/HTACCE~1.HTA
```

### Шаг 5: Проверка файлов с двойными расширениями

Иногда сервер обрабатывает файл по последнему расширению. Например, `file.jpg.php` будет выполнен как PHP, а не показан как картинка. Я проверяю, можно ли обмануть сервер, загрузив или обратившись к файлу с двойным расширение


-------


**Что считать успехом (находкой):**

- Обнаружен файл `.inc` или `.config`, который можно прочитать из браузера
   
- Найден бэкап (`.bak`, `.old`), содержащий исходный код или пароли
   
- Сервер отдаёт файлы с расширениями, которые должны быть защищены (например, `.sql`, `.java`)
   
- Каталог с загружаемыми файлами позволяет выполнять скрипты (например, загруженный `shell.php` выполняется)
   
- Доступен файл `web.config` (в IIS) или `.htaccess` (в Apache) - это может раскрыть логику редиректов и ограничений
