DNS-разведка - это **первый этап сбора информации (Reconnaissance)**. Она не даёт тебе прямого доступа к серверу, но **открывает двери** для следующих этапов пентеста

**Простыми словами:** Ты как разведчик перед штурмом - сначала изучаешь карту местности, ищешь все входы, калитки, подвальные люки и чёрные ходы, а только потом пытаешься их открыть

---

### 1. **Расширение поверхности атаки**

ищешь всё, что привязано к целевому домену/IP, чтобы не пропустить ни одной уязвимой точки

| Что ищешь                    | Пример                                                            | Почему это важно                                                            |
| ---------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Скрытые поддомены**        | `admin.example.com`, `dev-api.example.com`, `staging.example.com` | Часто на них слабая защита, старые версии ПО, тестовые данные               |
| **Нестандартные порты**      | `example.com:8080`, `example.com:8443`, `example.com:9000`        | Могут быть панели управления, админки, сервисы без аутентификации           |
| **Другие виртуальные хосты** | `webmail.example.com`, `helpdesk.example.com`                     | Дополнительные приложения, о которых ты мог не знать                        |
| **Сторонние сервисы**        | `example.com` → `cdn.cloudflare.net` (CNAME)                      | Приложение может хоститься у провайдера, который нужно тестировать отдельно |

### 2. **Идентификация технологий**

Через DNS-записи  понимаешь, на чём всё построено

| Что ищешь             | Как понять                                                         | Зачем                                                                                     |
| --------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| **Хостинг-провайдер** | `ns12.wixdns.net` → Wix, `awsdns` → AWS, `cloudflare` → Cloudflare | Если это Wix - пентест будет ограничен (SaaS). Если AWS - можно искать открытые S3-бакеты |
| **Почтовые сервисы**  | MX-записи на `google.com` → Gmail, `outlook.com` → Office 365      | Можно проверить настройки SPF/DKIM/DMARC (защита от фишинга)                              |
| **CDN и прокси**      | CNAME на `cloudfront.net`, `fastly.net`                            | Нужно тестировать не IP, а сам домен. CDN может скрывать реальный сервер                  |

### 3. **Оценка защищённости**

Некоторые DNS-записи напрямую показывают, насколько хорошо настроена безопасность

|Что ищешь|Что должно быть|Что плохо|
|---|---|---|
|**SPF, DKIM, DMARC** (в TXT)|Настроены и валидны|Если нет — можно подделать письма от имени компании (спуфинг)|
|**DNSSEC** (DS, DNSKEY, RRSIG)|Есть подписи|Если нет — DNS-ответы можно подменить (MITM-атака)|
|**CAA-записи**|Указаны только доверенные CA|Если нет — любой CA может выпустить SSL-сертификат на этот домен|

## 🚀 Что ДАЛЬШЕ (после DNS-разведки)

Ты нашел все IP-адреса, поддомены, порты и сервисы. Теперь начинается **активное тестирование**:

### Этап 1: Сканирование портов (Nmap)

bash

nmap -p- -sV 185.230.63.172

Ты сканируешь **все 65535 портов** и смотришь, что открыто.

**Что ты можешь найти:**

- **22/tcp** — SSH (можно попробовать подобрать пароль)
    
- **80/tcp, 443/tcp** — Веб-сервер (обычно)
    
- **8080/tcp, 8443/tcp** — Админки, прокси, альтернативные веб-сервисы
    
- **3306/tcp** — MySQL (если открыт наружу — это критическая уязвимость)
    
- **3389/tcp** — RDP (Windows Remote Desktop)
    
- **21/tcp** — FTP (может быть анонимный доступ)
    

### Этап 2: Проверка сервисов

Для каждого найденного порта ты проверяешь:

1. **Веб-серверы (80, 443, 8080, 8443):**
    
    - Версия ПО (старая = уязвимости)
        
    - Открытые директории (`/admin`, `/backup`, `/phpmyadmin`)
        
    - SSL-сертификат (просрочен? самоподписанный?)
        
2. **SSH (22):**
    
    - Версия OpenSSH (известные уязвимости?)
        
    - Можно ли войти с пустым паролем или стандартными кредами (`root:root`)?
        
3. **Базы данных (3306, 5432, 27017):**
    
    - Можно ли подключиться без пароля?
        
    - Доступен ли снаружи вообще?
        

### Этап 3: Получение доступа (если повезёт)

**Цель всего процесса** — найти способ **получить доступ к серверу** (shell) или к данным.

Возможные пути:

1. **Старая версия веб-сервера** → эксплуатация известной уязвимости → удалённое выполнение кода (RCE) → shell.
    
2. **Открытая админка с дефолтным паролем** → залогиниться → загрузить веб-шелл → shell.
    
3. **SQL-инъекция в веб-приложении** → получить доступ к базе → найти пароли → SSH.
    
4. **Открытый порт SSH с слабым паролем** → брутфорс → доступ к серверу.

## ⚠️ Важно: Что ТЫ ищешь как AppSec-инженер

На этом этапе ты не пытаешься взломать сервер любой ценой. Твоя задача — **документировать каждую найденную уязвимость** и оценить риски.

Твой отчёт должен содержать:

1. **Список всех найденных активов** (IP, порты, поддомены).
    
2. **Список открытых портов и сервисов** с их версиями.
    
3. **Список уязвимостей** (по каждой — описание, CVSS-оценка, рекомендации по исправлению).
    
4. **Доказательства** (скриншоты, логи, выводы команд).
